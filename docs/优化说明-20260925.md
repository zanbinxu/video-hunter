# Video Hunter 抓流与播放优化说明文档（2026-09-25）

本文档记录本次针对 Chrome 插件 `video-hunter` 在真实环境（尤其是 YouTube 4K 等 MSE 高清流）抓流测试中暴露出的核心问题、根因剖析、解决方案与测试验证。

---

## 一、问题背景

在对 YouTube 4K 超高清视频进行真实抓流测试时，前期修复了片头片尾卡死停顿的问题后，进一步暴露了以下两个关键体验与功能缺陷：

1. **缺陷 A（音轨后半段完全无声）：**
   - **现象：** 产物视频画面全程正常播放，但**只有开头有一小段声音，后面大部分时长完全没有声音**（整段静音）。
2. **缺陷 B（点击「抓流」时油管页面卡死/转圈/黑屏）：**
   - **现象：** 在视频播放时点击插件弹窗的「抓流」，YouTube 播放器画面出现长时间卡死、转圈加载（Loading Spinner）甚至黑屏，需等待十余秒甚至更久后才能恢复正常播放。
3. **缺陷 C（页面重载缝隙导致 177MB 视频轨被全部丢弃，产物只剩音频）：**
   - **现象：** YouTube 抓流时提示 `有一组没能用上（fmp4/video，177MB）：第 11 个 box（2Î f）声明的长度不合法：在偏移 140138 处声称 3250241911 字节... 这一组没有进产物`，最终产物变成了仅有 4MB 音频的无画面文件。

---

## 二、根本原因深度分析

### 1. 缺陷 A：音频后半段无声的根因

- **多编码混并时对主音轨的误伤裁剪：**
  - 在 YouTube 等大型流媒体站点播放 4K 视频时，播放器在初始起播、自适应清晰度升阶或拖动时，常会下载一小段低清晰度的 WebM (VP9) 视频块（例如 42MB），随后主视频轨稳定在 fMP4 (AV1) 超高清流（例如 176MB，覆盖全程 02:58）。
  - 在 `src/offscreen/offscreen.js` 的 `finishAssembly` 流程中，当同时检测到 `video`（fMP4）和 `webmVideoTracks`（WebM）时，旧代码试图将 WebM 作为附属产物（`-2.webm`）另存。
  - **严重误区代码：** 旧代码在行 1151 处写道：
    ```javascript
    if (from <= 3 * 1e6) {
      webmAudioTracks = webmAudioTracks.map(t => ({ ...t, frames: t.frames.filter(f => f.timeUs >= to) }));
    } else {
      webmAudioTracks = webmAudioTracks.map(t => ({ ...t, frames: t.frames.filter(f => f.timeUs < from) }));
    }
    ```
  - 因为 WebM 视频块的时间起点 `from` 落在视频某处（`> 3s`），旧逻辑误以为“主产物音轨只能要 WebM 之前的那一段”，从而**直接就地删除了所有 `timeUs >= from` 的全部音频帧**！
  - 实际上，音频在 YouTube MSE 中是一条**自始至终连续的 WebM/Opus 单独音轨**，主产物（fMP4 4K 视频）全长近 3 分钟，但送入转码器 `transcodeOpusToAac` 的音轨帧却被直接腰斩。转码后的 AAC 只有开头几十秒，导致封入 MP4 后后半段完全失去音频。

### 2. 缺陷 B：点击抓流后页面卡死、黑屏与长时转圈的根因

- **原因 1：内容脚本起播看护（`guardStart`）对 `currentTime` 的高频强行重设引发死循环**
  - 用户点击「从当前进度开始抓流」（默认开启）后，后台通知标签页在指定时间（如第 47 秒）开始抓取，并刷新页面。
  - 页面重载后，`src/content/content.js` 启动起播看护器 `guardStart(47)`，以每 400ms（`GUARD_POLL_MS`）轮询检查 `<video>`。
  - 页面刚加载时，`<video>` 还处于元数据加载或网络分片拉取阶段，此时 `m.currentTime` 读数为 0 或处于 `m.seeking = true` 状态。
  - 看护器在判断 `t < guardTarget - 2.5` 为真后，立即触发 `seekTo(m, guardTarget)` 执行 `m.currentTime = target`。
  - **致命时序冲突：** 400ms 后下一次轮询到达时，由于网络下载和寻道尚未完成，`t` 仍然未达到 47 秒，看护器**再次调用 `m.currentTime = target`**！
  - 这导致原生播放器的寻道与分片请求**每 400 毫秒就被强行打断并从头重试一次**，播放器陷入了长达 15 秒（`GUARD_MS = 15000`）的连续打断-重试死循环，直到 15 秒看护超时停止后，播放器才终于有机会完成一次完整的缓冲并开始播放。
- **原因 2：MSE 钩子中同步 base64 序列化严重阻塞播放器主线程**
  - 在 `src/content/mse-hook.js` 的 `SourceBuffer.prototype.appendBuffer` 拦截中，旧代码在调用原生 `origAppend` **之前**，直接在主线程对传入的 `data` 执行了同步的 chunked `toBase64`。
  - 对于 4K 视频而言，单次 `appendBuffer` 的分片体积可达 5MB~10MB，在主线程同步进行字符拼接与 base64 编码耗时达 50ms~150ms，直接拖慢了原生 MSE 解码管道的数据入库，造成播放器丢帧和缓冲迟滞。

### 3. 缺陷 C：页面刷新缝隙导致 177MB 视频被弃用、只剩音频的根因

- **时序分析与确切数据印证：**
  - 当用户在弹窗点击「抓流」时，后台将录制状态置为 `RECORDING`，随后延迟约 900ms 调用 `chrome.tabs.reload(state.tabId)` 刷新标签页。
  - 在这 900ms 内，旧的 YouTube 页面尚未销毁且已收到 `MSE_ARM: true` 命令，旧页面中的 MSE 钩子抓取了旧播放器最后送入的切片：
    - 1 个视频切片（大小恰好为 **140,138 字节**，`seq = 0`）；
    - 1 个音频切片（大小恰好为 **137,214 字节**，`seq = 0`）。
  - 随后页面刷新，新页面从 `seq = 0` 重新开始流式推送（包含完整 `moov` 和媒体分片：视频 176MB，音频 4MB）。
  - `mse-assemble.js` 的 `groupBuffers` 按照 `seq` 排序拼接：旧的 140,138 字节视频切片被排在了开头，新流的字节紧随其后拼接在 140,138 处！
  - **为什么音频活下来了，而视频被整个扔掉？**
    - 音频是 WebM/Opus：`webm-demux.js` 内部拥有 `resyncToNextCluster` 容错扫描机制，跳过了开头的 137,214 字节错位，成功搜寻到了新页面的下一个有效 Cluster，救回了后续全部音频；
    - 视频是 fMP4/AV1：`mse-assemble.js` 使用严格的 `splitSelfContainedFmp4` 遍历 box。在读取到偏移 140,138 时，遇到了旧切片与新流拼接的截断缝隙，试图解析为一个非法长度（3,250,241,911 字节）的 box，当场抛出异常。
    - 抛错后的简单兜底要求 `boxChainOk`（box 必须自始至终无缝连续到末尾）。因为 140,138 处断裂，`boxChainOk` 校验不通过，**整组高达 177MB 的视频被视为"无法识别"而直接丢弃**！导致最终只有音频进入产物，时长为 04:04 的无画面 MP4。

## 三、修改思路与实现方案

### 1. 修复主产物音轨完整性（解决无声缺陷）

- **文件：** `src/offscreen/offscreen.js`
- **思路：**
  - 将额外产物（`-2.webm`）所需的音轨切片与主产物彻底解耦。额外产物使用独立的 `extraAudio`，**绝不修改、过滤主音轨数组 `webmAudioTracks`**。
  - 让主产物（fMP4 4K 视频）使用全量的 `webmAudioTracks` 进行 Opus → AAC 异步转码，生成覆盖全时段的完整音轨。
  - 音画起点的对齐由 `mp4-merge.js` 中的 `applyEditLists`（已设 `MAX_PLAUSIBLE_ORIGIN_GAP_SECONDS = 1.5s`）保驾护航；尾部若音频比视频略长，由 `mp4-merge.js` 的 `maxAudioEndUs = videoEndUs + 500_000` 安全修剪，杜绝首尾卡顿的同时保证全程有声。

### 2. 优化起播看护与寻道状态机（解决卡死转圈）

- **文件：** `src/content/content.js`
- **思路：**
  - **尊重原生寻道状态：** 在 `pullBack` 轮询中增加 `if (m.seeking) continue;`。如果原生播放器当前正在寻道中，严禁再次赋值 `m.currentTime` 打断原生管线。
  - **引入状态机与寻道冷却：**
    - 为每个媒体元素跟踪 `seekState`（`{ target, requestedAt, reached }`）。
    - 针对 `guardTarget > 0` 的定位请求，触发一次 `seekTo` 后记录 `requestedAt = now`，给予至少 3.5 秒的缓冲与网络拉取窗口，期间绝不重复触发 `seekTo`。
    - 监听 `m.addEventListener('seeked')`，寻道完成后若处于暂停状态自动尝试触发一次 `m.play().catch(...)` 协助恢复起播，避免黑屏停顿。
    - 仅当媒体位置曾经成功到达过目标区域（`reached = true`），后续又被站点脚本异常拉回开头时，才再次执行回拉。

### 3. MSE 缓冲区快照与微任务解耦（消除主线程卡顿）

- **文件：** `src/content/mse-hook.js`
- **思路：**
  - **同步极速快照：** 使用原生的 `Uint8Array.prototype.slice()`（纯 C++ 内存拷贝，5MB 耗时 `< 0.2ms`）对 `data` 做一份不可变快照，杜绝页面后续篡改。
  - **原生调用零等待：** 立即执行 `origAppend.call(this, data, ...rest)` 放行原生调用，让浏览器解码器第一时间拿到数据，实现真正的“零延迟”。
  - **转码后置到微任务：** 将 base64 转码与 `postMessage` 移入 `queueMicrotask` 执行，不在原生 `appendBuffer` 同步周期内消耗时间。

### 4. 刷新缝隙旧片清理 + fMP4 深度容错救援（双保险解决视频轨被弃用）

- **文件：** `src/background/service-worker.js`, `src/offscreen/offscreen.js`, `src/parser/mse-assemble.js`
- **思路：**
  - **防线一（智能容错与边界对齐）：**
    - 页面刷新后，由 `mse-assemble.js` 的 `salvageFmp4Group` 精确识别并跳过刷新前的残余坏切片，确保不误杀新页面在重载瞬间已推入的合法切片。
  - **防线二（容错救援算法 `salvageFmp4Group`，对标 WebM）：**
    - 在 `mse-assemble.js` 中新增 `salvageFmp4Group(merged, fromMime)` 函数。
    - 当 `splitSelfContainedFmp4` 因 box 损坏报错或 `boxChainOk` 断裂时，不再直接丢弃整组数据；
    - 算法提取 `moov` 初始化段，然后向后遍历寻找合法分片。若遇到损坏、非法长度或乱码区域，以字节为步长向后搜寻合法的 `moof` 特征头（验证 `moof` 大小且内部第一个子 box 必须是 `mfhd` 签名）；
    - 跳过损坏断裂区，将后续所有完整的 `moof` + `mdat` 媒体分片全部救回拼装（记录 `skippedBytes` 并标记 `salvaged: true`），绝不让上百兆的高清画面付诸东流。

### 5. 换编码分段时序精准判定与语义化命名（解决 `-2` 倒挂认知）

- **文件：** `src/offscreen/offscreen.js`, `src/core/capture-limits.js`, `src/recorder/recorder.js`, `src/popup/popup.js`, `src/parser/mp4-merge.js`
- **思路：**
  - **精准判定时序：** 结合 fMP4 视频首片解码时间戳与 MSE 切片到达序号（`firstWebmSeq < firstFmp4Seq`），准确识别 WebM 是起播缓冲段（前段）还是切换后段，废弃不准确的 `from <= 3s` 猜测；
  - **语义化命名：** 扩展 `captureFileName` 支持字符串分段后缀，起播缓冲段直接存为 `-前段.webm`，彻底消除 `-2` 带来的“第 2 段”认知倒挂；
  - **产物规格可见：** 在管理页收尾通报与弹出面板 Toast 中直接展示产物实际体积（如 `147 MB`），让用户对超清数据规格一目了然；
  - **列表标签细化：** 管理页文件列表中明确标注 `起播缓冲段（前段）` 与 `完整核心产物`，让用户清晰分辨主副产物；
  - **提示文案安抚：** 对两条轨时间基不同（绝对时间戳与相对时间戳）自动按 0 对齐的提示进一步优化，明确告知“已自动按起播原点精确对齐，确保音画严格同步”，消除用户不必要的疑虑。

## 六、本地测试操作说明

修改已全部应用至本地源码目录。你可以直接进行测试：

1. 打开 Chrome 浏览器，访问：`chrome://extensions/`
2. 找到 **Video Hunter** 插件（已解压目录 `dist/video-hunter-0.2.6` 或源码根目录）。
3. 点击卡片右下角的 **⟳（重新加载）** 按钮。
4. 打开 YouTube 任意 4K 视频，播放过程中点击插件弹窗的 **「抓流」**。
5. **预期效果：**
   - 页面刷新后，视频能迅速定位并正常起播，不会长时间转圈卡死或黑屏。
   - 不再出现“第 11 个 box 长度不合法在偏移 140138 处…这一组没有进产物”的错误；
   - 抓流完成后，超清主视频（标明体积）与起播缓冲段（标明 `-前段.webm`）清晰呈现，**视频画面流畅清晰、音画同步且全程有声**。
