## 验证分四层

之所以分四层，是因为每一层能证明的东西不一样，而它们之间**没有重叠**：

| 层 | 工具 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 1. 静态体检 | `npm run check` | 语法正确、manifest 引用的文件都存在、跨文件引用没断链 | 运行时行为 |
| 2. 单元测试 | `npm test` | 解析逻辑对边界输入的处理正确 | 真实媒体文件能不能播 |
| 3. Node 端到端 | `npm test` | 真实流 → 解密 → 重封装 → **产物经 ffprobe 验证** | 浏览器里的 fetch / WebCrypto 会不会不一样 |
| 4. 浏览器端到端 | `npm run browser-check` | 扩展能在真 Chrome 加载、页面无报错、**浏览器内跑完整管线且产物经 ffprobe 验证** | 真实站点的怪异行为 |

第 3 层和第 4 层用的是**同一份源码**（`src/parser/*.js`），但跑在不同的运行时里。第 4 层的价值就在于它不是"再跑一遍"，而是证明这份源码在浏览器环境（真实的 `fetch`、真实的 `crypto.subtle`、真实的 mux.js UMD 包）里同样成立。

几个值得单独说的用例：

**「解密后第一个字节必须是 0x47」** —— 这是"解密真的成功了"最硬的证据。MPEG-TS 的包同步字节固定是 `0x47`，用错 key 解出来的数据不可能恰好以它开头。

**「用错 key 解密必须失败」** —— 反向验证。如果解密函数实际上没在做事（比如直接返回原文），这个用例就会失败。

**「把 TS 分片直接首尾相接得到的仍然是 TS」** —— 这是一个对照实验，用来证明重封装**不是多余的**。裸拼接出来的 `.mp4` 扩展名文件 ffprobe 读不出音视频轨。

**「vendor/mux.min.js 能加载」** —— 测的是**真正会发布的那个文件**（`vendor/mux.min.js`），不是 `node_modules` 里的另一份构建。加载方式是给它一个 `require` 垫片后用 `vm` 执行，因为那个 bundle 对 `global/window` 有外部依赖。

**直播那 11 个用例**针对的是一类特别的 bug：短时间跑完全看不出来，跑半小时才开始丢片。所以它们用**合成的时间线**（手工构造的滑动窗口快照序列）来压，包括"窗口前移两片只该返回新片"、"窗口跳过头必须记下漏了哪几片"、"单次拉取失败不该终止整个直播"、"abort 后不能卡在一个轮询周期上"。

其中一个用例直接暴露了实现问题：拉取失败后轮询间隔被打回了默认 2 秒（而不是沿用算好的节拍），表现是测试莫名慢了 2 秒。这是真行为缺陷，已修。

**DASH 合并那 22 个用例**除了 ffprobe 层面的断言，作者还额外做了一次比 ffprobe 更硬的验证：把「源 fMP4 直接拼接」和「合并产物」都跑 `ffmpeg -f framemd5` 逐帧比对 md5 —— 视频 300 帧、音频 563 帧**全部一致**。这证明产物是源素材的忠实重封装，样本数据一个字节没变。这一步验证比「时长对得上」强得多。

测试样本是 `tools/make-fixtures.mjs` 用本机 ffmpeg **真实生成**的：多码率 TS 版 HLS、AES-128 加密版、fMP4 版、**直播形态版**（无 `#EXT-X-ENDLIST` + `MEDIA-SEQUENCE:3` 的滑动窗口）、音视频分离的 DASH。不是手写的假数据。

### 一个踩过的坑（留在这里当作记录）

第一版加密样本是错的。`ffmpeg -hls_enc_key` **不接受十六进制**——它取字符串的前 16 个字符当原始字节用。我按十六进制传了 32 个字符，结果 key 文件里的字节和实际加密用的字节对不上。

这个错误很隐蔽：加密照样成功，测试照样"跑完"，只是解密出来是垃圾。发现它靠的是**断言解密后的第一个字节是 0x47**。现在 fixture 脚本会校验 key 文件必须是 16 字节，并打印出来。

**「无清单 DASH」那条是用户实测反馈逼出来的。** B 站不提供 m3u8/mpd，它通过 API 直接返回两条完整 fMP4 文件的地址（一条纯视频、一条纯音频），所以嗅探到的只是两个 `.m4s`。第一版把它们当成"某个播放列表的分片"折叠掉了，于是用户看到的是"什么都没嗅探到"——实际上是**分类假设错了**：没有清单时，分片本身就是下载目标。

修法分两层：面板在没有播放列表时把 `.m4s` 当主项列出来并提供「合并下载」；解析器页整份下载后，**靠 moov 里的 handler box 判断轨道类型**（不靠文件名——B 站的命名规则不是通用知识），再合并。

验证用的数据不是构造的：`dash-split` 那个真实样本里本来就有分开的视频轨和音频轨，把 init 和分片按顺序接起来，得到的就是和 B 站同一种形态的文件。

**「MSE 抓流」那条也是用户反馈逼出来的。** 用户明确指出「屏幕录制不是我想要的」——他要的是播放器**已经解密好的那条流**，而不是抓屏幕像素。这两件事差别很大：

| | 抓流（钩 `appendBuffer`） | 录制（`chrome.tabCapture`） |
| --- | --- | --- |
| 抓到的是 | 原始码流 | 渲染后的画面 |
| 网页水印 | 不带（水印是叠在视频上的 DOM） | 一起录进去 |
| 画质 | 原始 | 受屏幕分辨率限制 |
| 编码 | 不重编码 | 要重编码 |

**产物 1128804 字节，和纯下载合并那条路的产物一模一样大** —— 抓流拿到的是逐字节相同的原始流，这一条比任何文字描述都更能说明"无损"。

验证用的是真的 MSE 测试页：开两个 `SourceBuffer`，把 init 和分片依次 append（15 次），并且刷新一次以验证钩子注册成持久脚本后能在页面重载时自动就位。

值得单独说的四点：

**1. Referer 注入真的生效了。** 这条链路在代码里成立、静态检查也过得去，但「Chrome 到底会不会给**扩展页面自己发起的 fetch** 改写 Referer」是个只能实测的问题——代码审查时它被明确标为"不确定"（MDN 说非导航请求除请求 URL 外还需要**发起方**的 host 权限，而发起方是 `chrome-extension://<id>`）。现在的做法是让 fixture 服务把收到的请求头回显出来，扩展页面真发一次请求，服务端确认收到的就是改写后的 Referer。**结论：生效。**

**2. 嗅探、内容脚本、页面内按钮三条链路打通了。** 打开一个真的在播视频的页面，扩展侧能查到：
- 嗅探层捕获到 `source.mp4`，并且**记下了 Referer**（重新抓分片时靠它）
- 内容脚本扫描到页面上的 `<video>`（这条同时验证了 `MSG.PAGE_SCAN` 缺失那个修复）
- 页面内下载按钮真的注入进了 DOM（用 `data-vh-badge` 标记从页面侧确认）

**3. 录制管线验到的是"编码与封装"，不含"拿采集源"。** 用一个 `canvas.captureStream(0) + requestFrame()` 合成的流（外加振荡器音轨）喂进 `src/offscreen/pipeline.js`，产出 MP4、落进 OPFS、读回、交给 ffprobe：

```
avc1.640028 / mp4a.40.2 · 640×360｜产出 92 帧 / 编码 91 帧（丢 0）
ffprobe：h264 640x360｜aac｜2.97 秒
```

帧数对得上这一点是有意断言的：录制这条链路最容易出的错就是"帧悄悄丢了但文件照样能生成"。

为此专门把管线从 `offscreen.js` 抽成了 `pipeline.js` —— **为了可测**。原本它和 `chrome.tabCapture` 绑死，而 tabCapture 在自动化环境里拿不到（见下），结果就是整条录制链路一行都验不了。抽开之后，"编码封装对不对"和"能不能拿到 tab 流"成了两件独立的事。

**4. `chrome.tabCapture` 的采集源获取，自动化验证不了。** 报错原文：

```
Extension has not been invoked for the current page (see activeTab permission).
```

这是 Chrome 的安全边界：tabCapture 要求扩展被**用户主动调用**过（点工具栏图标），自动化加载（`Extensions.loadUnpacked`）给不了这个授权。查过 CDP 的全部 35 个域，**没有任何授予扩展调用权限的命令**。所以这一条不是"还没测"，是"在无人操作的前提下不可测"。

不过这次尝试也不是白费：
- 失败路径的行为被验证了——代码没有崩，而是返回了明确的错误、关掉了离屏文档、把状态置为 ERROR
- 一个测试环境上的坑被暴露并修掉：headless 默认对后台标签页做定时器节流，`setInterval(…, 33)` 被压到约 1 次/秒，合成流 3 秒只产出 **3 帧**。加 `--disable-background-timer-throttling` 等参数后变成 92 帧。**不查这一步，我就会拿着"3 帧也算通过"的结果当验收。**

## 拿真实 CDN 上的公开流再压一次

自己用 ffmpeg 造的样本有个天然缺陷：**它只会出现我预料到的情况**。所以额外加了一个 `--real` 模式，直接拿公开的参考流跑。

用的是一条业界常用的参考流：Apple 的 `img_bipbop_adv_example_ts`（HLS 作者自己维护的示例，包含多码率、独立音轨、IFrame 变体、字幕）。

```
· 真实 CDN 上的公开流

  · 合并路径（音频组 aud1）
    · 视频列表 100 片（取 4）｜音轨列表 101 片（取 4）

✓ 浏览器验证通过
```

**解析层全部正确**：24 个码率、5 条 `#EXT-X-MEDIA`、音频组归属、IFrame 变体的过滤，都对。

**更重要的是它先抓出了一个真实缺口，然后证实缺口被补上了**：

第一轮跑的时候，产物是这样的：

```
· ffprobe：h264 480x270｜无音频轨｜24.00 秒
✗ ffprobe 读不到音频轨
```

这条流的每个码率都带 `AUDIO="aud1"` 之类的属性 —— 也就是说**视频和音频是两条独立的流**。视频播放列表里只有视频轨，音频在 `#EXT-X-MEDIA:TYPE=AUDIO` 指向的另一条播放列表里。当时的实现只下了视频那一半。

这条检查现在**保持失败即报错**（不会放宽断言）：它是当前实现状态的真实反映。

## 这一层抓到的真 bug：整个后台是死的，但一切"看起来正常"

这是本次开发中最值得记录的一次发现，因为它说明**"扩展能加载、页面不报错"离"能用"有多远**。

### 现象

第一版浏览器检查（只验"页面有没有控制台报错"）全绿：

```
✓ popup   无控制台报错 · bodyLen 2732
✓ 解析器  无控制台报错 · bodyLen 2288
✓ 录制台  无控制台报错 · bodyLen 1962
✓ 离屏文档 无控制台报错 · bodyLen 309
✓ 浏览器验证通过
```

但我把检查从"没报错"加强成"**确实渲染出了预期内容**"之后，录制台立刻失败：

```
✗ 录制台 渲染不符合预期：文件列表节点=0 计时=00:00:00 OPFS=ok 日志=""
```

`#recordings` 是 0 个子节点——`renderRecordings()` 根本没跑；日志是空的——也没有抛错。**既不完成也不报错**，这只有一种可能：`init()` 卡在某个 `await` 上。

### 定位

在页面里单独探一次"页面 → service worker"的消息往返：

```
消息=TIMEOUT(3s)
```

消息发出去没人回。顺着查 Chrome 的日志文件，一行就说明白了：

```
INFO:CONSOLE "Uncaught SyntaxError: The requested module '../core/constants.js'
does not provide an export named 'IGNORED_REQUEST_TYPES'",
source: chrome-extension://…/src/background/sniffer.js (16)
```

`IGNORED_REQUEST_TYPES` 定义在 `classify.js`，而 `sniffer.js` 从 `constants.js` import 它。**service worker 的模块图在启动时就解析失败了**——嗅探、下载、录制、网络规则，整个后台全是死的。

而扩展照样加载成功、四个页面照样渲染正常、控制台一条错都没有（那条错误只出现在 Chrome 内部日志里，不在任何页面上下文）。

### 修完之后加的两道防线

1. **`check-syntax.mjs` 增加「模块导入导出一致性」**：对每条相对 import，解析目标模块真实的导出名集合逐个比对。这个错误 50 毫秒就能查出来——`node --check` 只验语法，永远看不见它。

2. **`browser-check.mjs` 增加明确的 service worker 存活探测**：主动发一条消息并等回应（5 秒超时），而不是只看 `Target.getTargets` 里有没有那个 target。MV3 的 service worker 是懒启动的，"没有 target"是正常状态，所以不能用它当判据——但"发了消息没人回"一定是出事了。

顺带修掉的另外两个问题：

- **浏览器检查的日志采集时机错了**。原来先创建目标页再 `Runtime.enable`，页面初始化阶段抛的异常和打的日志全发生在监听器就位之前，会被静默漏掉。现在改成：先开 `about:blank` → 挂上 `Runtime/Log/Page` 监听 → 再 `Page.navigate` 过去。
- **Referer 会话规则的 ID 会碰撞**。原来用 `9000 + tabId % 2000` 直接算，看着很巧妙（service worker 重启后不用查表就能清理），但**同时开着的 1000 号标签页和 5000 号标签页会落到同一个 ID**，后一个把前一个的规则顶掉，表现为"其中一个页面突然开始 403"且完全看不出原因。现在改成从 64 个 ID 的池子里分配，映射持久化到 session storage。

---

### 两个实现上的坑（留作记录）

**Chrome 137 之后命令行 `--load-extension` 已被禁用**（防恶意侧载），日志里只留一句 `load-extension is not allowed in Google Chrome, ignoring`，浏览器照样启动，只是扩展没加载——非常容易误判成"扩展有问题"。现在的做法是走 CDP 的 `Extensions.loadUnpacked`，需要浏览器带 `--enable-unsafe-extension-debugging` 启动。

**本地沙箱禁止管道式 stdio**（Chrome 的 IPC 走命名管道，两种受限模式都拦）。所以：
- ffprobe 的输出走 `-o <文件>` 而不是捕获 stdout
- 子进程一律 `stdio: ['ignore','inherit','inherit']`
- `node --test test/` 会因为 spawn EPERM 失败，必须用 `--test-isolation=none`

这些约束反过来影响了工具设计——`browser-check.mjs` 之所以是个 CDP 客户端而不是 shell 脚本，就是因为 shell 管道用不了。

## 这一层抓到的第二个真 bug：文件能播，但拖不动进度条

这条值得单独记，因为**所有自动化检查当时都是绿的**——ffprobe 认得它、时长正确、轨道正确、有画面有声音、文件大小合理。唯一的问题是用户的播放器（PotPlayer）里拖不动进度条：播到 2 秒拖到 2 分钟，立刻弹回 2 秒。

**这个现象有两个互不相关的成因，我先把第一个当成全部、修完就宣布好了，结果用户回来说还是不行。** 两个成因都记在下面。

### 根因（第一种：没有样本表）

早期 HLS 路线是把分片重封装成 **fragmented MP4**，再交给 mux.js 直接吐出来。真正的文件头长这样：

```
mvhd  timescale=90000  duration=4294967295  → 47721.86 秒
mvex  present
（没有 sidx，也没有 mfra）
```

`duration=0xFFFFFFFF` 是 fMP4 规范里表示"时长未知"的写法，而这个文件既没有 `sidx` 索引也没有 `mfra` 随机访问表。于是播放器**只能顺序读**：它不知道总时长，无法建立时间轴，任何 seek 都只能退回已解码的位置。ffprobe 之所以"看起来没问题"，是因为它是全文件扫一遍算出来的时长，不依赖这些索引——**这就是"ffprobe 通过"不能等价于"播放器能用"的地方**。

### 修法（第一种）

不再直接输出 mux.js 的分片 MP4，而是把分片当作输入，走 `mp4-merge.js` 的 `mergeFmp4()` 重建一份**标准 MP4**：从每片的 `moof` 里抽出样本，重新生成 `stts / stsz / stco / stss / ctts` 和正确的 `mvhd` 时长。HLS、DASH、无清单合并三条路线现在都走这条路。

用真实 UI 路径（解析器页 → 点下载）重跑一遍，产物：

```
mvhd 时长 12.09 秒｜轨道 2 条｜mvex false｜样本表 stsd,stts,stss,stsc,stsz,stco,ctts
```

`mvex false` + 完整样本表 = 普通可随机访问 MP4。

### 但是用户回了「还是不能拖」—— 于是有了第二种根因

这一条比上面更值得记：**上面那次修复是真的，但它修的不是用户遇到的那个问题。**

用户第二次反馈拖不动之后，才去翻他磁盘上真实的产物。在 `~/Downloads` 里找到 7 个 `vh-rec-*.mp4`（录制路线导出的），用 `tools/seek-diag.mjs` 一查，四个长录制全都长这样：

```
mvhd 662.52 秒
  轨 vide：12250 个样本｜662.50 秒｜49 个关键帧
    关键帧时间点：0.00, 4.17, 8.33, 470.83, 475.00, …     ← 8.33 秒之后直接跳到 470 秒
  轨 soun：9571 个样本｜662.53 秒
```

把 stts 展开就是一句话：

```
stts: 749×960  1×35040960  12000×960     ← 中间那一"帧"占了 608 秒
```

**样本表完整、mvhd 时长正确、关键帧索引在、ffprobe 读得出来、文件能播。** 唯一的毛病是：时间轴中间有一段几百秒完全没有样本。播放器拖到那一段时，按样本表只能定位到空洞**之前**那一帧 —— 用户看到的就是「拖到两分钟立刻跳回几秒」。

这个用 ffprobe 是查不出来的（它只报"时长 662 秒"，而那确实没错），必须把每条轨的 stts 展开、按常规帧间隔找出"某个样本的时长异常大"才看得见。

**成因**：tabCapture 的时间戳来自**源**。标签页被切到后台、被遮挡、屏幕锁定、机器休眠时 Chrome 一帧都不给，时间戳却照走；录制器老实照抄，就把这几百秒写进了样本表。

**修法（两层）**：

1. **录制端当场压掉**（`createTimelineCompressor`）：采集停摆超过 1.5 秒就把这段死气从时间轴上剔掉，产物是一段连续视频。
2. **已经录好的文件能补救**（`src/parser/seek-check.js` + 管理页的「体检 / 一键修复」）：把那个超长的 stts 时长改回常规帧间隔，同步改 `mdhd` / `mvhd` / `elst`。**只改元数据的几个 u32，box 长度不变、样本数据一个字节不动**，所以不重编码、不搬数据、文件大小不变。

### 这一步里最危险的一个决定：什么才叫"空洞"

第一版把"某个样本时长异常大"一律当成空洞来压。跑用户那 7 个文件时立刻发现其中一个是错的：

```
vh-rec-20260920-011618.mp4   vide timescale=30  第一条 stts 条目 = 1×42（1.40 秒）
                             soun 单条 stts，完全没有断
```

这不是空洞，是**这条轨开头被拉长了**（编码器预热，第一帧顶了 1.4 秒）。音频从头到尾连着——压掉它，视频轨后面所有内容会整体前移 1.4 秒，**音画立刻错位**。那比拖不动严重得多。

所以现在的规则是：

- **第一条件目超长** → 是起播延迟，不是空洞，永远不动。
- **只有一条轨断** → 说明那一刻这条轨确实没抓到画面（音频还在走），压了会音画错位 → **拒绝修，并说明理由**。
- **每条有内容的轨都在同一段时间断** → 整条采集停摆过，那段谁都没有内容 → 压掉，各轨相对关系不变。

录制端的压洞器用同一套判据：某条轨自己往前跳了超过阈值时，回头看**另一条轨最新的时间戳**——另一条轨已经走过这段窗口就是单轨缺口，不动。

### 这里还炸了一次，原因值得记

压洞器第一版是"两条轨共用一个 frontier（已写到的最大时间）"，在真实浏览器里第一次跑就抛：

```
addVideoChunk's third argument (timestamp), when provided, must be a non-negative real number.
```

**两个编码器的输出进度天然不一样**：音频队列可以积到 800 毫秒，视频积到 200 毫秒。于是音频把 frontier 推到了视频还没到的地方，视频随后补上来就被误判成"跳了 2 秒"而压了一刀；紧接着视频队列里那些时间戳更早的帧按新 shift 一算就成了负数，封装器直接抛错、整段录制全废。

改成**每个轨各记自己的进度**（跳跃只在同一条轨内部比较）之后，跨轨的进度差再也构不成"跳跃"。这条路径现在有专门的用例：`压洞器：两条轨各自输出进度不同（音频队列更长）不该被误判成停摆`。

### 教训

**验证必须包含"用户实际点的那条路"。** 两条都栽在同一个地方：

- 第一次修复：模块级测试全绿（`remuxer` 能产出、`mergeFmp4` 能合并、ffprobe 都读），但没把产物交给一个真的会 seek 的播放器。
- 第二次才发现：真正的证据在**用户磁盘上他自己的产物**里，而不在我造的样本里。我造的样本永远只有我预料到的形状。

所以现在的做法是：

- `browser-check.mjs --real` 走完整 UI 下载路径，产物交给 ffprobe 反验，并额外断言 `mvhd.duration` 是有限值且 `mvex` 不存在。
- `browser-check.mjs --extras` 里加了一个**制造 3 秒采集停摆**的录制用例：挂钟 6.1 秒 → 产物必须只剩 2.93 秒且没有空洞。
- 体检 / 修复做成了界面上的按钮（`src/parser/seek-check.js`，纯函数、有测试），用户能自己把任何一个 MP4 拖进去看结论 —— 不用再靠我猜他手上是什么文件。

## 第三个真 bug（用户报的）：`抓流` 没有管理界面，而且显示的时长是"我操作了多久"

两条都来自同一个根子：**产物落在浏览器的私有存储（OPFS）里，而界面对它的交代是缺失的。**

### 现象

1. 抓流结束后，产物只是静静躺在 OPFS 里。唯一的入口是"停止并保存"时顺手打开的那个页面，而那个页面叫「录制控制台」、内容全是录制相关的措辞和按钮 —— 用户看不出自己的抓流产物在哪。
2. 显示出来的时长是**这次操作持续了多久**。抓流期间暂停、拖动、切标签页都会把挂钟时间拉长，跟视频长度能差出几倍。

### 修法

**管理界面**：页面改名「**抓流 / 录制管理**」，产物按来源分成两组（抓流文件 / 录制文件），每行给 **时长 · 体积 · 时间** 和 **保存到磁盘 / 体检 / 删除**。抓流结束由 service worker **自动跳过去**（`stopMseCapture` 里调 `openRecorderPage`），并**复用已经开着的那个标签页** —— 每抓一次多开一个标签页，一晚上标签栏就没法看了。面板底部也加了「管理」按钮，任何时候都能进。

**真实时长**：时长一律从产物自己的 `mvhd` 读（`readMovieDurationSeconds`），不再用挂钟：

- 抓流：合并完在内存里就能读，写完盘顺手记进索引。
- 录制：由编码时间轴算出来（`createTimelineCompressor` 记下最早的样本时间戳和最晚的结束时间），所以停摆被压掉之后得到的是**产物时长**，不是录制时长。
- 管理页列目录：先查索引；索引里没有（老产物、换过 profile）才去读文件，读完回填 —— 而且**只读文件头或末尾几 MB**（录制的 moov 在文件末尾，一个两小时的录制光 moov 就可能上兆），不会为了显示个时长把几 GB 读进内存。

挂钟时间没有删掉，它降级成了"解释"：只有当它和真实时长差出 2 秒以上时才出现，措辞是「抓取过程用了 00:00:07，中间的暂停和拖动不算在文件时长里」。

### 顺带修掉的一处误导

抓流产物原来和录制产物**共用 `vh-rec-` 前缀**，混在同一个列表里分不出来。现在抓流用 `vh-mse-`。
但老产物改不了名，所以管理页不只看前缀：抓流产物由合并器写出、带 fastStart，是 `ftyp` 紧跟 `moov`；录制产物顺序写盘做不到快启动，`ftyp` 后面直接是 `mdat`。读 32 个字节就能把老文件正确归类。

### 这一轮的验证

| 断言 | 结果 |
| --- | --- |
| 抓流状态里的 `mediaSeconds` | **12.011**（挂钟 `durationMs` 是 **7023** —— 两个数差一倍，正是这条用例的区分度所在） |
| 产物前缀 | `vh-mse-20260920-101532.mp4` ✓ |

## 第四个：从 CocoCut 学到的三件事（以及为什么没有第四件）

用户贴了 CocoCut 的界面截图和它的运行日志，要求"借鉴它优秀的地方"。**先明确一条边界**：CocoCut 是
闭源商业插件（官网只有 Chrome/Edge 商店链接和 Freemium 定价，没有任何源码入口）。网上能搜到的几个
`*-CocoCut` GitHub 仓库描述是 `[Extension files Chrome]`，也就是**把打包好的扩展文件原样倒出来**的镜像，
不是官方源码 —— 那个我不看、也不抄（版权是一回事，抄了会直接推翻本项目"原创实现"这句话是另一回事）。

但**界面和可观察行为**是可以学的：用户自己截的图和官网 FAQ 已经把它的交互讲清楚了。下面三条是从里
面挑出来的、真正能改善体验的。

### 1. 「两种模式怎么选」摊开在面板上（而不是塞进 tooltip）

CocoCut 给「录制模式」「抓取模式」各做了一个 ⓘ 悬浮说明，把**优点/缺点**都写出来，包括"某些视频无法
录制""可能出现视频或音频片段丢失"这种自曝其短的条目。

我的面板上原来只有两个按钮「抓流」「录制」，`title` 里一句干巴巴的说明。**用户根本不知道这两个的代价
差多少** —— 一个是无损拿原始码流，一个是重新编码还会把播放器 UI 录进去。所以照它的思路做了一个展开面板
（`ⓘ 该选哪个`），两栏对照：原理 / 画质 / 速度 / 前提，最后一句「拿不准就先点抓流，失败了再点录制」。

顺带把最容易误解的那句写进 README：**抓流不是录屏**。它拿的是播放器解出来的原始码流，弹幕、广告、
推荐位一概不进产物。

### 2. 「直接保存已缓存好部分」→ 「先保存已录到的部分」

CocoCut 的任务页上有这个按钮，而且它还有「暂停 / 继续」。

**暂停我没有做，这是刻意的。** 它的数据模型是"下载分片"，暂停就是停下 HTTP 请求，恢复接着下。
我的抓流是**钩播放器的 `appendBuffer`** —— 数据是播放器边解码边喂过来的，挂起钩子等于把那段时间的
码流**丢掉**，产物里会留下一个真空洞（正是前面那个"拖进度条跳回去"的形态）。所以对这个架构来说，
"暂停"不是省事，是产出坏文件。

正确的等价物是"写出去接着抓"：`MSG.MSE_SNAPSHOT` → 离屏文档把**此刻**的缓冲组装成
`vh-mse-<时间戳>-部分.mp4` 落盘，**缓冲不清空、抓流不中断**。想留几个节点就留几个。

录制路线连这个都做不到：它的 `moov` 写在文件末尾（顺序写盘做不到快启动），不收尾就产不出能播的文件。
所以按钮只对抓流出现 —— 给录制也放一个，那是骗人。

### 3. 让"它还在动"看得见

CocoCut 的任务行上有 `HLS_491.4KB 0.39%` 这样的实时进度。我原来在抓流时只显示一个走秒的计时器 ——
**没法区分"在收"和"卡死了"**。

现在离屏文档每秒上报一次 `{chunks, bytes}` 心跳（走的还是那条 `OFFSCREEN_STATE` 通道），
面板上显示成「抓流中 00:12 · 15 段 · 1.1 MB」，管理页显示「15 段数据」。

### 没有学的：ffmpeg.wasm

CocoCut 用 ffmpeg-core.wasm 做重封装和"MP4 修复工具"（用户贴的日志里能看到它的加载过程）。
这条路我仍然不走：TS→MP4 在浏览器里本来就是**重封装**，mux.js 112 KB 就够；分片 MP4 重建样本表
我自己写了 `mergeFmp4`；"修复工具"对应本项目的**体检 / 一键修复**，而且更彻底 ——
它只改样本表里的几个 u32，不重编码、不搬数据、文件大小不变。为一个边缘场景背 25~32 MB 的 wasm
（还要 SharedArrayBuffer + 跨域隔离）不划算，这个取舍写在 README 的"技术选择"里。

用户贴的 CocoCut 日志里有一行：


这正是我在某个课程站上撞到的同一堵墙 —— **它在用和我一样的方式校验解密结果**（解密出来是不是合法
TS），也失败了。所以不是我的工具更差：那个站点的 key 服务返回的字节里根本没有有效密钥，
两家都只能退到"读播放器已经解出来的码流"（它的"录制模式"，我的"抓流"）。

## 第五个真 bug（用户报的）：抓流产物「前 12 分钟怎么拖都拖不动」

用户的原话：「无论是通过拖进度条还是通过键盘上的左右键，都不能正常播放前 12 分钟的视频。
你一拖或者一按键，它就自动跳到 12 分钟之后了。」

这次没猜 —— 直接去他 `~/Downloads` 里找到了刚导出的那个产物（`vh-mse-20260920-110400.mp4`，
33.4 MB），一量就看清了：

```
总时长：1391.69 秒（23 分钟）
  轨 vide：41000 个样本｜关键帧时间点 0.00, 4.17, 8.33, 720.83, 725.00, …
                                          └── 8.33 秒之后直接跳到 720.83 秒 ──┘
  ⚠️ 空洞（所有轨一起断）：12.48 秒处断了 708.35 秒
  轨 soun：⚠️ 空洞：12.50 秒处断了 708.37 秒
```

**12.5 秒之后横着 708 秒空洞（11.8 分钟）**，两条轨一起断。播放器拖进度条时要找
「最近的、在这个时间点之前的关键帧」，而 12 分钟之前根本没有可用样本，
只能落到空洞之后那一帧 —— 用户看到的「一拖就跳到 12 分钟之后」就是这么来的。

### 两个成因，缺一不可

**成因一：抓流是实时的，而播放器的位置往前跳了。**

抓流钩的是 `appendBuffer`，只看得见播放器**此刻**送进去的数据。它不像下载那样能
自己决定取哪一段。而这次的位置跳变来自一个很具体的地方：

> 抓流会**刷新一次页面**（让钩子从头收数据）。而很多站点会**记住你上次看到哪儿**，
> 页面加载完之后自己把 `currentTime` 设回去 —— 用户当时正好看到 12:00。

于是采集到的时间轴就断了：先抓到 0~12.5 秒，站点把位置设到 720 秒，接着抓到 720.8 秒以后。
分片里带的解码时间戳（`tfdt`）是连续的，所以合并出来的文件里就横着那段空洞。

**录制路线本来就有这个防护**（`armOne` 会把 `currentTime` 归零），**抓流路线没有** ——
这是漏掉的一处对称性。

**成因二：抓流产物落盘前没有任何时间轴检查。**

录制有 `createTimelineCompressor` 实时压死气；下载路线有 `mergeFmp4` 报空洞；
只有抓流是"合并完直接写文件"。所以哪怕空洞已经产生了，也没人管。

### 两道防线

**防线一：起播看护（从源头避免）。** 抓流/录制武装时开始 15 秒的看护，发现播放位置
**被往前设走**就扳回开头。

这里的判据值得单独说，因为**第一版写错了**：我一开始写成「`currentTime > 2` 就扳回 0」。
那是个严重错误 —— 正常播放在 2 秒之后位置当然大于 2，结果是把视频每 400 毫秒按回开头、
连按 15 秒。正确的判据是**两次观察之间的跳变**：轮询间隔 400 毫秒，正常播放这期间最多
前进 0.4 秒左右，超过 2 秒就一定是被谁设了位置。看护只持续 15 秒，之后交还给用户
（用户自己要拖进度条时不该被我们按住）。

**防线二：落盘前压死气（兜底）。** 新增 `finalizeCaptureBytes()`，产物写盘前先跑一遍
时间轴体检。判据复用修复工具那一套，不另写一份：

- 每条有内容的轨**都在同一段时间断** → 那段时间确实什么都没抓到 → 压掉，各轨相对关系不变
- 只有一条轨断 → 压了会让这条轨的内容整体前移、**音画错位** → 原样保留，并说明原因

"抓流产出的文件"和"修复工具修过的文件"现在走的是同一份 `repairTimelineGaps`，
不会出现两套规则慢慢跑偏。

### 验证：直接跑用户那个真实产物

```
处理前：1391.69 秒｜vide 空洞 708.4；soun 空洞 708.4
压缩掉：708.35 秒
提示：抓流过程中有 708.4 秒没有抓到任何数据（那段时间播放器的位置往前跳了 ——
      站点恢复了上次的观看位置，或者拖过进度条），已经从时间轴里去掉…
处理后：683.34 秒｜空洞 0 处｜结论 ✅ 索引完整，进度条应该能正常拖
视频关键帧：164 个｜前 6 个 0.00, 4.17, 8.33, 12.50, 16.67, 20.83｜最大间隔 4.17 秒
```

修好的文件已经放到用户 Downloads 里（`vh-mse-20260920-110400-可拖动.mp4`）。

（`/__page/resume`，加载 1.5 秒后把 `currentTime` 设成 8 秒，模拟真实站点），

```
· 扩展武装之后再设一次位置，1.5 秒后实际停在 0.00 秒
✓ 起播看护把"续播"扳回了开头，抓流不会因此断成两截
```

## 第六个：一集一个文件（用户报的"别把播放列表连成一个视频"）

用户的原话：「播放完它不就会跳下一个视频嘛……它会变成一个视频了，就是这个意思，要分开，
要能知道这个视频切换到下一个视频的这个断点。」

这是抓流这条路的最后一个结构性缺口：钩子只看得见 `appendBuffer`，**它不知道"这一集播完了"**。
所以播放列表和自动连播会被抓成一条连续时间轴，合并出来是**一个**装着好几集的文件。

### 三个边界信号

站点换集的姿势不止一种，所以盯三个（任何一个出现就报一次边界）：

| 信号 | 覆盖的情况 |
| --- | --- |
| `ended` | 最准的"这一集播完了" |
| `emptied` / `loadstart` | 媒体元素换了资源（用户点了下一集、站点切集） |
| 新的 `addSourceBuffer` | 播放器重建了 MediaSource（换集常见做法） |

第三个信号是现成的：钩子里早就把每次 `addSourceBuffer` 报出来了（用来记 mime）。
用 `mseSeq > 0` 把它和"开头那两个 SourceBuffer"区分开 —— 视频一条、音频一条，
它们建起来的时候还没抓到任何数据，不算边界。

### 切开：收尾成完整文件 + 清空缓冲

`OFFSCREEN_MSE_CUT` 把当前这段写成一个**完整文件**（不是 `-部分`），然后
**清空缓冲继续抓**。为什么必须清空：分片自带的解码时间戳在换视频时通常从 0 重新开始，
攒在一起会让时间轴倒着走，合并出来是一团乱。

### 三个容易踩的地方

**一、重复信号要去重。** 站点换一集往往在几秒内连发 `ended` + `emptied` + 新建 SourceBuffer。
不去重的话第一刀切走了数据，后面几刀会切出**空文件**。所以后台有 4 秒的静默窗口，
离屏文档那边还有一道"至少要有初始化段 + 一段媒体才切"的底线。

**二、文件名必须带序号。** 时间戳只精确到秒，而"一集播完"和"手动再切一次"完全可能落在同一秒里；
不带序号的话 `writeOpfsFile` 会把前一个文件**覆盖掉**，用户莫名少一个文件。
现在第 1 段不带序号、之后是 `-2`、`-3`。

### 产物存在哪、能放多久（用户问的，实测答案）

用户看着管理页问：「这里是临时保存在哪里了吗，为什么隔几分钟点击保存到磁盘依旧可以正常保存？」

**答：不在内存里，是磁盘上的真文件。** 抓流/录制收尾时走
`navigator.storage.getDirectory()` → `getFileHandle(name, {create:true})` → `createWritable()`
写进扩展自己的 **OPFS**（源私有文件系统）。实测落点（Windows，Chrome 153）：

```
<user-data-dir>\Default\File System\000\t\00\00000001     ← 文件名被存储层改成了编号
<user-data-dir>\Default\File System\Origins\              ← 哪个源对应哪个目录
```

`File System\000\t\00\00000001` 就是实验里写进去的那个 31 字节标记文件 ——
和扩展页面里看到的文件名无关（存储层用编号管理，名字记在元数据里）。

**能放多久**：跟着浏览器 profile 走。实测过程（同一 profile 跑两轮）：

```
把标记文件写进扩展的 OPFS → 完全关掉 Chrome（端口释放）→ 用同一个 profile 重启
  → 再读 OPFS：opfs-durability-marker.bin｜31 字节｜修改时间未变 ✓
```

所以用户"隔几分钟再点保存到磁盘"当然没问题 —— 那一步只是
`showSaveFilePicker` + `file.stream()` **分块拷贝**，和抓流结束多久没有关系。
会丢的情况只有：清掉浏览器数据、卸载扩展、或删掉那个 profile 目录
（`unlimitedStorage` 权限让扩展不受普通站点的配额驱逐，但救不了手动清理）。

**⚠️ 一个要说清的副作用**：「先保存已录到的部分」**每次写的是当前整个缓冲**，
而且**不清空**。所以连点三次会得到三份内容高度重合的文件（用户截图里
`003616-部分` / `003630-部分` / `003641-部分` 都是 09:27 / 56.4 MB，就是这个原因）。
文件名只带时间戳，看不出来它们是同一段的重叠快照 —— 想省空间就只留最后一份。

**三、换集之后收尾不能报错。** 缓冲被切空了，`mseStop` 会返回"没有捕获到任何数据" ——
那是**正常结束**，不是失败。报成 ERROR 会让用户以为抓流出错了，而前面几集好好地躺在管理页里。
现在这种情况走一条干净的路：READY + 「最后一段没有新数据」，管理页照常交代「一共自动存了 N 个文件」。

### 顺带修掉的一个竞态（这条是端到端测试逼出来的）

`vh:offscreen-status` 是**发给离屏文档**的请求，但 `chrome.runtime.sendMessage` 是广播 ——
service worker 也会收到。而 SW 的 `handleMessage` 没有这个分支，落到 `default` 就回一句
`{ok:false, 未知消息}`。**谁先回是不确定的**，于是"问离屏文档状态"变成看运气的操作：

```
这次跑：· 收尾之后：抓流仍在进行 是｜缓冲已清空 是
下次跑：· 收尾之后：抓流仍在进行 否｜缓冲已清空 否（还有 -1 段）   ← SW 抢先回了
```

这个竞态在端到端里表现为"时好时坏"，我一开始以为是测试不稳；查下去发现是**产品代码的问题**：
一个消息类型不能同时被两个方向接。现在 SW 把所有 `vh:offscreen-*` 请求都早退掉
（和早先 `MSE_BUFFER` 那条是同一个道理），发送方拿到的回答就确定了。

### 还有一个是我自己写的 bug

换集之后如果一直没新数据（60 秒）就自动收尾。第一版把"**拿不到段数**"也当成"没有新数据"：

```js
if (chunks === null || (chunks <= baseline && ...)) { 停 }
```

结果上一轮会话留下的定时器在新一轮抓流期间醒来，恰逢离屏文档一时没响应，
就把用户**正在进行**的抓流给结束了。现在只有**确认段数没涨**才收尾。

```
  · 紧接着再发一次同样的信号：已忽略（去重生效）
✓ 换集之后收尾是干净的（不报错）：最后一段没有新数据｜共 1 段
```

## 第七个真 bug（用户报的）：B 站换成了 AV1，合并直接翻车

用户的原始报错（他把日志整段贴过来了）：

```
第 1/3 条：41655603101-1-100026.m4s
  → 这条解析不了：视频样本描述项 av01（232 字节）里没有 avcC/hvcC，
    拿不到 H.264/H.265 解码器配置记录。按固定偏移读到的是：av1C, colr, btrt
失败：这些轨道里没有可用的视频轨
```

他同时贴了完整的 box 树，一眼就能定位：

```
stsd (256)
  av01 (240)
    av1C (115)      ← 解码器配置记录在这里
```

### 根因：编码换了名字，代码把名字写死在分支里

B 站（以及越来越多站点）的视频轨已经从 H.264 换成了 **AV1**。在 fMP4 里这只是
**同一个结构换了个名字**：

| | H.264 | H.265 | AV1 |
| --- | --- | --- | --- |
| 样本描述项 | `avc1` / `avc3` | `hvc1` / `hev1` | `av01` |
| 解码器配置记录 | `avcC` | `hvcC` | `av1C` |

而 `parseInitSegment` 里写的是 `kids.find((b) => b.type === 'avcC' || b.type === 'hvcC')`
—— 遇到 `av01` 就找不到配置记录，抛错，然后整条合并失败，退化成
"只存最大的一条轨道"。**用户拿到一个 88.9 MB、没有声音的视频**，这正是他说的
「依旧有问题」。

顺带说：`mp4-muxer` 本来就支持 AV1（`"av1": "av01"` + av1C 写入器），
缺的只是我这边没把配置记录认出来。

### 修法：把名字写成一张表，而不是写进分支

```js
const VIDEO_SAMPLE_ENTRIES = {
  avc1: { config: 'avcC', vendor: 'avc' },
  avc3: { config: 'avcC', vendor: 'avc' },
  hvc1: { config: 'hvcC', vendor: 'hevc' },
  hev1: { config: 'hvcC', vendor: 'hevc' },
  av01: { config: 'av1C', vendor: 'av1' },
};
```

解析和"该用哪个编码名交给封装器"都查这张表。**以后再加编码只要加一行**，
不会再出现"两个地方各写一遍、然后慢慢跑偏"。

编码串也跟着一起修：AV1 要的是 `av01.<profile>.<level><tier>.<bitDepth>`
（从 `av1C` 的头 4 个字节按 AV1-ISOBMFF §2.3.3 推），拿 `avc1.PPCCLL` 去套会被播放器当成坏文件。

### 验证：不只看 ffprobe，要真的解出来

这条路有个陷阱：**ffprobe 只读容器和样本表**，一个解码器配置记录写错的文件
它照样能报出「av1 / 320x180 / 6 秒」。所以除了 ffprobe，还加了一条更硬的断言
——把每个视频包真的送进解码器，数解出来多少帧：

```
视频轨：av01 / 配置记录 av1C / vendor=av1 / 320x180
av1C 前 4 字节：81 00 0c 00
合并产物 236009 字节
ffprobe：av1,video,320,180,150 帧,6.000000 秒｜aac,audio,283 帧,6.016000 秒
真的解一遍：解出视频帧数 = 150（6 秒 × 25fps = 150 帧）
```

一帧不多、一帧不少。这套断言进了两层：

- `test/merge.test.mjs`：新增 3 条 AV1 用例（认出来 / ffprobe 读到 av1+aac / **真的能解码**）
- `browser-check --extras`：在真 Chrome 里合一遍 AV1 轨道
  → `✓ AV1 合并产物 ffprobe：av1｜aac｜6.02 秒`

### 顺手修掉的重复轨道

用户日志里同一条音频轨出现了两次：

```
第 2/3 条：41655603101-1-30280.m4s
第 3/3 条：41655603101-1-30280.m4s
```

B 站的播放器会对同一个 `.m4s` 发多次请求（预取、Range 分段、重试），嗅探层就记下了
多条**完全相同的 URL**。后果不只是"数目报错"（2 条报成 3 条）：合并时同一条 URL
会**白下载两遍**，88 MB 的文件就是白下 88 MB。现在面板和解析器页各有一道按 URL 去重
（解析器页那道是兜底：旧版本写下的任务也不该重复下载）。

### 新增的夹具

`test/fixtures/av1-tracks/`（AV1 视频轨 + AAC 音频轨，各一份自包含 fMP4，
形状和 B 站给的一模一样），由 `npm run fixtures` 用 SVT-AV1 生成。

## 第八个：YouTube 到底支不支持（用户问的）

用户贴了两张图：一张是 B 站合并成功（AV1 那个修复生效了），另一张是 YouTube 页面上面板
只列出两条音频、问「YouTube 的这个支持吗」。

**这种问题不能靠读代码回答。** 所以我给浏览器检查加了一个模式 —— 打开真实页面、等它播，
然后如实报告四件事：页面在不在播、扩展嗅到了什么、**Chrome 实际发了哪些媒体请求**、
抓流能不能收到数据。第三个是关键：只看扩展嗅到了什么，分不清
「站点没用普通请求取媒体」和「我的嗅探层有 bug」。

```
$ node tools/browser-check.mjs --port 9333 --site "https://www.youtube.com/watch?v=..."
· 页面：<video> 1 个｜currentTime 11.11 秒｜时长 213 秒｜src=blob:https://www.youtube.com/...
· 嗅探到 4 条：audio×4
  - [audio] 0.0 MB audio/mpeg https://www.youtube.com/s/search/audio/success.mp3
  - [audio] 0.0 MB audio/mpeg https://www.youtube.com/s/search/audio/open.mp3
  （四条都是页面 UI 音效，视频一条都没有）
· Chrome 实际发出的媒体请求：15 个（MIME 是 video/audio 的只有 4 个，全是那几个音效）
  - [Image] 204 text/plain  https://rr4---sn-...googlevideo.com/generate_204
  - [Fetch] 200 application/vnd.yt-ump  https://rr2---sn-...googlevideo.com/videoplayback?...
  - [Fetch] 403 text/plain  https://rr3---sn-...googlevideo.com/videoplayback?...
· 抓流：收到 136 段｜2.59 MB｜钩子抓到了数据 ✓
```

### 结论：YouTube 支持，但只能走抓流

YouTube 的媒体响应回来的是 **`application/vnd.yt-ump`** —— 它自己的容器，通过 `fetch` 取回，
不是 `video/mp4`。所以：

- **嗅探这条路在 YouTube 上天生没用**。这不是 bug，是它故意的：地址在 `blob:` 里、
  响应是私有容器，`webRequest` 看得见请求但拿不到能直接下载的东西。
  （顺带说明：那几个 `videoplayback` 请求还经常返回 403，那是 YouTube 的正常反爬。）
- **抓流完全能用**：钩子挂的是播放器的 `appendBuffer`，和地址、容器格式都无关。
  实测 14 秒收到 136 段 / 2.59 MB，而且是无损的（不重编码、不带播放器 UI）。
- 代价是**实时**：视频多长就得播多长。这是"读播放器已解出的码流"这条路的固有代价，
  没有捷径。

> 补记（第十三个 bug）：这一节当时只验到"抓流能收到数据"。后来用户报
> 「能抓到画面，但是抓不到声音」—— 因为 YouTube 的**音频轨是 WebM/Opus**，
> 而合并器只认 fMP4。修好之后在同一个站点复验：产物 `av1 640x360 ｜ aac ｜ 40.00 秒`，
> 两条轨起点都对齐在 0。详见上面「第十三个真 bug」。

### 但用户会觉得"不支持"，所以这里有两处必须改

用户看到的面板上只有 4 条音效，自然会以为这个站不行。**问题不在能力，在交代。**

**一、加一条 MSE 提示条。** 只要页面在播 MSE（`blob:` 源）又没嗅到真正的视频，面板顶部
就顶一条：「这个视频用 MSE 播放，真实地址不是普通请求拿得到的」+ 一个「抓流」按钮。

判据这里踩了一次：第一版写成"没有任何可下载的媒体就提示"，结果 YouTube 那几个按钮音效
（几 KB 的 `audio/mpeg`）**本身就可下载**，于是提示条永远不出现。现在判据只看
**视频文件和播放列表**，音频条目一律不参与 —— 因为这条提示回答的是"我的视频呢"，
跟音效无关。纯音频页面用的是 `<audio>`，不会被当成"页面视频"，所以也不会误报。

**二、MSE 页面里每行的首选按钮改成「抓流」。** 原来这里只给一个「录制」按钮 ——
那等于把用户往最差的那条路上推：录制是采标签页画面重新编码（有损、会带上播放器 UI、
必须实时），抓流是无损拿原始码流。现在「抓流」是主按钮，「录制」降为次选。

### 顺带修的可测试性问题

面板原来只会看"当前活动标签页"（`tabs.query({active:true,currentWindow:true})`）。
以整页方式打开时（自动化里只能这么开），它看到的**是它自己** —— 于是计数永远是 0，
这一层根本没法验。现在支持 `popup.html?tabId=123` 显式指定，
和 `parser.html` / `recorder.html` 的既有约定一致，手动排查某个标签页时也好用。

## 第九个真 bug（用户报的）：点「停止并保存」，它说「当前没有在录制」

用户的原话：「我点这个页面上的录制之后，插件也提示正在录制。然后我点上面那个『停止并保存』，
它就提示没有正在录制。」

这句话里有两个互相矛盾的事实：**面板上写着「录制中」（截图里还有实时帧数 00:04 · 82 帧），
而状态机说没有在录。** 矛盾本身就是线索 —— 它们读的是同一份状态，所以中间一定有个时间窗。

### 根因：两个问题叠在一起

**一、页面上任何一个 `<video>` 播完都会停掉录制。**

`armRecording` 原来的做法是：把 `ended` 监听挂到**每一个** `video,audio` 上，谁结束都发
`MEDIA_ENDED`，后台收到就自动收尾。而真实页面上不止一个视频 —— 广告、预览、背景动画、
花絮小窗，随便哪个播完都会把用户真正的录制打断。那个课程站上，录制在 4 秒左右就被停了。

**二、收尾不是瞬间的，而这期间的第二次点击被当成错误。**

收尾要 flush 编码器、封 muxer、写 OPFS，大文件要好几秒。这期间状态是 `FINALIZING`，
但面板上还写着「录制中」—— 用户很自然地再点一次「停止并保存」，而 `stopRecording()`
的第一行是：

```js
if (cur?.stage !== RECORD_STAGE.RECORDING) return { ok: false, error: '当前没有在录制' };
```

于是一个刚点了"保存"的用户，得到的回答是"你没在录"。**他以为白录了，其实第一次点击
正在把文件写完。**

### 修法

**针对一：只认那个"录制目标"的结束。** 内容脚本每次扫描时挑出**页面上最大的可见视频**
（`pickRecordingTarget`），只有它的 `ended` 才算数，而且要求它**真的播到了头**
（`currentTime >= duration - 1.5`）；来自别的视频的结束会带上 `fromTarget: false`，
后台收到只记一条日志、不打断录制。

**针对二：收尾要做成"可以重复点"的。**

- 收尾进行中再点一次 → **复用第一次的 promise**，拿到同一个结果（`stopInFlight` / `stopMseInFlight`）。
- 已经收完尾了再点 → 返回 `{ok:true, action:'already-finalized'}`，并且**把管理页打开** ——
  文件就在那儿，这比一句错误有用得多。
- 卡在 `FINALIZING`（比如收尾途中 service worker 被系统杀掉）→ 返回 `action:'finalizing'`，
  面板提示「正在收尾，稍等一下…」，而不是红色报错。

**一句话原则：点了「保存」就永远要给用户一个关于文件的交代，不能只回一句"你什么都没在做"。**

### 顺带删掉一个"看起来是优化、实际是隐患"的东西

查这个问题时发现 `getRecording()` 有一份**模块级内存缓存** `recordingCache`，只在
`setRecording` 里更新。于是任何绕过它写进 storage 的状态都读不到 —— 而 service worker
随时可能被系统杀掉重启、缓存跟着清空，"谁是最新的"就变得不可推理了。

`chrome.storage.session` 本来就是内存存储（不落盘），每秒读一次的开销可以忽略。
删掉缓存之后**只有一个数据源**：读到的和写进去的永远是同一份。

> 这个东西还是测试逼出来的。我第一版断言一直"奇怪地失败"：明明往 storage 写了
> `finalizing`，SW 却回 `already-finalized`。查下去先发现是**我的测试键名写错了**
> （写 `vh:record`，真名是 `vh:recording`），改成从模块里 import 之后就暴露出真正的原因
> —— 缓存让外部写入不可见。**测试读自己写的键、代码读另一个键，是"断言假通过"的经典形态**，
> 现在键名也从模块取，不会再漂。

### 验证

tabCapture 在自动化环境里点不起来，所以录制本身没法整链路验；但**状态机这一半可以**
（三条断言都在真浏览器里跑）：

```
· 非目标视频播完：ignored
· 收尾中再点停止：ok=true action=finalizing｜写入的 stage=finalizing，之后 stage=finalizing
· 已收尾后再点停止：ok=true action=already-finalized
```

第一条正是用户遇到的那个 bug：页面上随便一个视频播完，不再把录制停掉。

## 第十个真 bug（用户报的）：抓流到 166 MB 时，保存 / 停止 / 自动分片**同时**失败

用户的截图里有一行红字：**`Maximum call stack size exceeded`** —— 而且出现了两次：
一次是点「先保存已录到的部分」，一次是点「停止并保存」。状态卡上写着 1384 段数据、
194 MB、**已存 0 个**。

「已存 0 个」说明连换视频时的自动分片也没成功过。所以这不是三个 bug，是**一个**。

### 根因：`push(...arr)` 把栈用光了

```js
samples.push(...result.samples);   // ← mp4-merge.js 的 collectTrack
```

展开运算符传参是**按函数实参**走的，实参数量受栈空间限制（V8 大约 12 万）。
而抓流这条路把所有分片**拼成一段**再交给合并器（见 offscreen 的 `assembleMseCapture`），
所以 `result.samples` 一次就是整条视频的样本数：

| 产物 | 视频样本数 | 结果 |
| --- | --- | --- |
| 12 秒的测试流 | 300 | ✅ |
| 用户的 23 分钟课程产物（33 MB） | 41000 | ✅ |
| 这次（166 MB） | ~20 万 | ❌ `Maximum call stack size exceeded` |
| 这次（194 MB） | 更多 | ❌ |

**几十 MB 以下恰好卡在上限之内，所以这个问题一直没露头。**

### 为什么三条路一起失败

`assembleMseCapture` 是**共用的**：手动保存（快照）、换视频自动分片、停止收尾
三条路都要经过它。它一炸，三条一起炸 —— 用户看到的就是"点了没反应 / 保存失败 / 停止失败"，
而屏幕上还显示着"1192 段数据 · 166 MB"。

### 修法

一行的事：把展开换成循环。

```js
for (const s of result.samples) samples.push(s);
```

**顺带修掉一个会让它更难查的问题**：`cutMseCapture` 原来在**切之前**就记下了
静默窗口的时间戳，于是"切失败"也把 4 秒的窗口吃掉，后续几秒的重复信号全被忽略 ——
表现就是"明明换了视频，却什么都没存，也不报错"。现在只有**真的切成功**才启动窗口。

### 验证：先证明测试能抓住它

新加的用例直接造一个含 **15 万个样本**的 fMP4 分片（按 ISO/IEC 14496-12 手写
moof/traf/trun，样本表逐字段填好）：

```
# 把修复退回去
✖ 大产物：15 万个样本能真的封出来（不是只到取样本那一步）
  RangeError: Maximum call stack size exceeded
# 修复之后
✔ ✔ 147/147
```

**测试先在 bug 上失败，才说明它测的是真的东西。** 顺带确认了 mp4-muxer 本身没问题
（直接喂它 12 万个样本，产物正常）—— 问题在我自己的代码里，这一点不能靠"换个库"糊过去。

### 顺带把用户要的「自动保存」开关做出来

用户的诉求：抓流是实时的，一集接一集自动连播**来不及点保存**，希望有个能开能关的自动保存。

- 新增设置 `autoSaveCapture`，**默认开**：一个视频播完（`ended` / `emptied` / 新建 SourceBuffer）
  就自动把这一段存成独立文件，抓流继续。
- 开关放在**两个地方**，改哪个都算数（同一个设置值）：
  面板的「设置」里，以及管理页抓流状态卡上 —— 用户是在看着这段抓流的时候才想起来要开/关它。
- 关掉之后边界仍然识别，但**不落盘**，并明确说出代价：
  「上一段会和下一段攒在同一个缓冲里（下一段时间戳从 0 重新开始，时间轴会乱），
  换视频前请自己点一次『先保存已录到的部分』」。
  —— 这个代价是真的，所以不能只说"已关闭"就完事。

浏览器里的断言：

```
✓ 检测到视频切换：第 1 段已自动保存 vh-mse-....mp4｜1128804 字节｜时长 12.01 秒
  · 关掉自动保存后再来一次切换信号：action=auto-save-off（没有落盘，符合预期）
```

## 第十一个真 bug（用户报的）：换个倍速，抓流就被打断了

用户的原话：「我在抓流的过程中，通过插件切换倍速……它就立马刷新，把进度条拉到头，
然后就出现这个报错（只抓到了媒体分片，没有初始化段）。」

### 根因：起播看护把「快进播放」当成了「页面把位置设走了」

这是我**自己上一轮引入的 bug**。为了让抓流不被站点"续播上次位置"打断，我加了一段起播看护：
在开始的 15 秒里盯着播放位置，发现"跳变"就扳回开头。判据写成了：

```js
const jumped = prev === undefined ? t > 3 : (t - prev) > GUARD_JUMP;  // GUARD_JUMP = 2
```

**它完全没有考虑播放倍速。** 轮询间隔 400 毫秒，12 倍速下播放位置本来就会前进 **4.8 秒** ——
远超 2 秒的阈值。于是用户一开倍速，看护就认定"页面把位置设走了"，把视频扳回 0：

- 用户看到的就是「我点一下 12 倍速，它就把进度条拉回头顶」
- 那一跳对 MSE 播放器来说是一次真的 seek，播放器会清缓冲、重新取数据 ——
  抓流的时间轴因此断掉，最后报「只抓到了媒体分片，没有初始化段」

**判据现在按倍速算**：记录每次观察的墙钟时间，预期前进量 = 间隔 × `playbackRate`，
只有"比正常播放多跑了 2.5 秒以上"才算跳变。站点把位置设到 12 分钟仍然一眼认得出，
而 12 倍速、32 倍速的正常播放都不会被误判。

### 验证：先证明测试能抓住它

浏览器里让视频以 6 倍速播 1.5 秒，采样播放位置，断言**绝不回退**：

```
# 退回旧判据（前进 > 2 秒就算跳变）
· 6 倍速播放 1.5 秒：位置 0.31 → 1.88 秒｜最大回退 4.01 秒
✗ 快进播放被看护当成了"页面设位置"，把视频扳回去 4.01 秒 —— 用户就是被这一下打断的
# 修好之后
· 6 倍速播放 1.5 秒：位置 0.31 → 9.21 秒｜最大回退 0.00 秒
✓ 换倍速不会打断播放（看护按倍速算预期前进量）
```

**旧判据下位置被拽回 4 秒、最终停在 1.88 秒** —— 和用户的描述一模一样。
同一个用例里还保留了对照：站点式续播（一次性把位置设到 8 秒）仍然会被扳回开头 ✓。

### 顺带：那种失败不该把 21 MB 判死

用户那次失败时已经抓到 200 段 / 21.4 MB，报错内容却是"没有初始化段" ——
而那个初始化段**本次会话早就收到过了**（播放器重建 SourceBuffer 之后只补了分片）。

查这个问题时发现两处：

1. `analyzeGroup` 把「只有初始化段」（`ftyp+moov`，没有媒体）和「只有分片」都当成失败吞掉。
   前者其实是**有用的东西** —— 上层要能记住它。现在单独认出来并交出去。
2. 抓流会话现在记着"这次见过的初始化段"（按大类）。遇到只有分片的组时复用它，
   产物里并注明「初始化段用的是本次抓流里先前收到的那一份」。
   复用是安全的：合并器按 init 里的 `trackId` 挑样本，对不上会明确报错，不会产出坏文件。

顺带修掉一个小的：快照这条路原来只把**落盘阶段**的提示带回去，
组装阶段的（比如这条复用说明）被丢掉了 —— 用户在界面上看不到任何解释。

浏览器里的断言：

```
· 只有分片、没有 init 的那一组：ok=true 产物 vh-mse-....mp4｜时长 2.00 秒
  提示：这份抓流中途播放器重建过缓冲区（只补了分片），初始化段用的是本次抓流里先前收到的那一份（video）
```

## 第十二个真 bug（用户报的）：录制中途报 `Timestamps must be monotonically increasing`

用户截的是扩展错误页上的这一行（`pipeline.js:377`）：

```
[vh/rec] 编码出错： Error: Timestamps must be monotonically increasing
(DTS went from 4928000 to 3499590).
```

这是 **mp4-muxer 的硬检查**：同一条轨的下一个样本时间戳比上一个还早，它直接抛错，
**整场录制作废**。视频轨的 DTS 从 4.928 秒退回到了 3.49959 秒。

### 根因：判断"整条采集停了"用错了判据

录制防空洞（把采集停摆的时段从时间轴里压掉）要回答一个问题：
**这次跳跃是"整条采集停了"还是"只有这一条轨没出帧"？**
前者可以压（各轨相对关系不变），后者压了会让音画错位。

我的判据是："另一条轨最新的**媒体时间戳**有没有走过这段窗口"。**这个判据是错的**，
错在一个不明显的地方：**编码器的输出进度和采集进度不是一回事** ——
音频队列能积 800 毫秒、视频 200 毫秒，机器慢的时候差得更多。

于是：音频停摆 2.5 秒 → 回头看视频，视频的输出本来就落后（它的队列还没吐出来）→
"没走过这段窗口" → 判定成整条采集停了 → **按音频的时间轴压了一刀**。
而那一刀对视频是错的：视频随后送进来的帧减去这个位移就成了更早的时间戳 → 撞上硬检查。

### 修法：判据改成**墙钟空档**

记下"最后一次收到**任何一条轨**输出的时刻"。只有**所有轨**都超过阈值没有输出，
才算整条采集停过 —— 这才是物理上正确的"采集停了"，而且和编码器队列积压无关。

另外加一道兜底：**每条轨的时间戳只允许前进**。上面那个错误是硬失败（整场录制作废），
宁可让两个样本时间戳相同（产物里一帧零时长，无害），也不能炸。
`backSteps` 计数器专门盯着这件事，正常应该恒为 0。

### 验证：先证明测试能抓住它

新用例模拟真实的那个交错：音频每 20 毫秒一个包；视频编码器慢，出帧频率只有音频的
1/8、时间戳还落后 2.5 秒；然后**音频停摆 2.5 秒，而视频一直在出帧**（所以采集没停）。

```
# 换回旧的媒体时间戳判据
✖ 压洞器：音频停摆、视频只是输出落后 —— 绝不能把视频的时间戳拉回去
  AssertionError: 视频一直在出帧，就该一个字都不压（实际压了 2480 毫秒）
# 现在的墙钟判据
✔ 151/151
```

**旧判据下确实压了 2480 毫秒** —— 和用户日志里"被拉回 1.43 秒"是同一个形状。

### 测试本身的改动值得记一笔

压洞器的测试原来全是同步调用 `adjust()`。判据改成墙钟之后，同步代码里**没有时间流逝**，
于是"停摆"根本造不出来 —— 4 条老用例立刻红了。这不是坏事：它说明原来的测试
**测的是实现细节，不是物理事实**。现在给压缩器注入了可替换的时钟
（`createTimelineCompressor({ now })`），测试里喂假时钟，语义变成
"媒体时间跟着墙钟走，中间断了一段" —— 读起来也更接近真实发生的事情。

## 第十三个真 bug（用户报的）：抓 YouTube 能抓到画面，但是抓不到声音

用户原话：「抓流的功能在抓 YouTube 的视频中可以抓到画面，但是抓不到声音。」

### 第一步不是猜，是把现场打出来

`--site` 探针以前只报"收到 N 段 / 多少 MB"，而**这恰恰是这个 bug 唯一看不出来的东西**。
所以先给探针加了两件事，再去看 YouTube：

1. 按 mime 分开报（`stats.tracks`）—— 音频那条轨到底收到没有；
2. 收尾之后把**每一组**都列出来（采纳的和没采纳的），并把产物落盘交给 ffprobe
   （`detail.groups` + `detail.audioTranscode`）。

打出来的现场：

```
· 抓流：收到 105 段｜2.94 MB
  - （播放器没给 mime）｜35 段｜0.84 MB
  - video/mp4; codecs="av01.0.01M.08"｜51 段｜1.31 MB
  - audio/webm; codecs="opus"｜19 段｜0.80 MB
· 抓到的一组：mime=video/mp4; codecs="av01.0.01M.08"｜容器=fmp4｜类型=video/av01｜1.31 MB
· 抓到的一组：mime=audio/webm; codecs="opus"｜容器=unknown｜类型=audio｜0.80 MB
  ｜没收进产物：认不出容器（开头字节：1a 45 df a3 9f 42 86 81）
· 产物 ffprobe：av1 640x360｜无音频轨 ✗｜41.23 秒
```

`1a 45 df a3` 是 EBML 头 —— **音频是 WebM/Opus，而合并器只认 fMP4**，
那 0.80 MB 被静默跳过。根因到此为止，一句猜测都不需要。

### 为什么必须转码，而不是"换个封装"

抓流拿到的是播放器**已经解密好的原始码流**，站点给什么就是什么：

- MP4 装得下 Opus（有 `Opus` sample entry 这个标准），但 **Windows 自带播放器、
  手机、剪辑软件都不认**，只有 ffmpeg/VLC 这类能放。用户要的是"下载下来能正常播放"；
- 所以音频必须**解码成 PCM、再编码成 AAC**（192 kbps），视频一个字节不动。
  这是整条抓流链路上**唯一**一处有损，界面里也如实说了。

### 修法

| 新东西 | 干什么 |
| --- | --- |
| `src/parser/webm-demux.js` | EBML/Matroska 拆包：Segment、Tracks、Cluster、SimpleBlock/BlockGroup、**四种 lacing**、长度未知的 Segment（流式 WebM 就是这形态） |
| `src/offscreen/audio-transcode.js` | WebCodecs：Opus 解码 → PCM → AAC 编码；带背压（队列超了就等 `dequeue`），不把整条音轨读进内存 |
| `mp4-merge.js` 的 `{ audio: { aac } }` 入口 | 转码好的 AAC 帧当成一条音频轨，和 fMP4 视频合成一个 MP4 |
| `sniffContainer` 认 `webm` / `webm-no-init` | 只有 Cluster 没有头部时，提示还是那句「点抓流之后刷新页面」 |
| `mse-hook` 给每条 SourceBuffer 编号（`sbId`） | 站点上有一批 append **没有 mime**；以前它们全落进同一个空 mime 组，几条流混着拼，字节头尾不接 → 整组被当"认不出容器"丢掉。现在按编号分组，各归各的 |

### 音频起点对齐这件事，绕了一圈才做对

第一版的想法是"两边都保留绝对时间戳，让 muxer 一起减掉最小起点"
（mp4-muxer 正好有 `firstTimestampBehavior: 'cross-track-offset'`）。**用例当场打脸**：

```
✖ 混装：音频起点比视频晚时，两条轨的相对位置要保住（不能各归各的零）
  AssertionError: 音频应该从约 1 秒处开始，实际 0
```

原因是 mp4-muxer 的 `stts` 只记「样本之间的间隔」，**一条轨自己"比影片晚 1 秒开始"
这件事它记不下来** —— 那 1 秒会被悄悄吃掉，变成音画不同步。MP4 里只有 `edts/elst`
能表达这件事。所以最终走的是和 fMP4 音频**完全相同**的那条路：
每条轨各自归零，轨道之间的差量交给 elst；转码音频的"影片时间 0"按视频 elst 的
`media_time` 换算（两条流在 MSE 里本来就在同一条呈现时间轴上）。

同一个用例改完就绿了 —— 也就是说，这个设计错误是被**测试抓住的**，不是被用户抓住的。

### 验证

单元（`test/webm-demux.test.mjs`，15 条，用 ffmpeg 造的真 Opus 样本 + 手写的
EBML 合成样本）：

```
✔ 真 WebM/Opus 样本：帧数、时间戳、时长都对得上      ← 601 帧 / 12.02 秒 / pre-skip 21 ms 对得上
✔ lacing：Xiph 形态能拆出一个 Block 里的多帧（最后一帧靠剩余字节推）
✔ lacing：固定长度和 EBML 差值两种形态也要能拆
✔ 合成样本里的"长度未知的 Segment"要能解析
✔ 混装：fMP4 视频 + 转码 AAC，产物里两条轨都在        ← ffprobe：aac / 48000 Hz / 2ch
✔ 混装：音频起点比视频晚时，两条轨的相对位置要保住     ← 音频 start_time ≈ 1 秒
```

浏览器（`--extras` 里新增 8c：测试页真的开一条 `audio/webm; codecs="opus"` 的 SourceBuffer）：

```
· 抓到的一组：mime=audio/webm; codecs="opus"｜容器=webm｜audio#1 A_OPUS 2 声道 48000 Hz｜0.17 MB
· WebM 音频转码：Opus → AAC｜564 帧｜48000 Hz 2ch
✓ WebM 音频抓流产物 ffprobe：h264 640x360｜aac 48000Hz 2ch｜12.00 秒
```

真实站点（就是用户报的那个站）：

```
· 抓到的一组：mime=audio/webm; codecs="opus"｜容器=webm｜类型=audio/opus｜0.63 MB
· 抓到的一组：mime=video/mp4; codecs="av01.0.01M.08"｜容器=fmp4｜类型=video/av01｜0.97 MB
· 产物 ffprobe：av1 640x360｜aac｜40.00 秒
  · 两条轨的起点：视频 0.000000｜音频 0.000000（差 0.000 秒）
```

### 音频不只是"有条轨"，而是**真的有声音**

ffprobe 只能证明"有一条 aac 轨"。要证明它装的是**正确的声音**，得真解出来看：

```
测试页抓流（fixture 是 440 Hz 正弦，解出 PCM 后按过零率估频）
  解出 8.00 秒｜RMS 0.0626｜峰值 0.089｜过零估频 440 Hz    ← 和素材一模一样
真实 YouTube 抓流
  解出 15.00 秒｜RMS 0.0390｜峰值 0.342｜过零估频 1362 Hz   ← 宽带内容（人声/音乐），不是静音
```

440 Hz 那个数字是这一步的关键：转码链路（WebM 拆包 → Opus 解码 → AAC 编码 → 封进 MP4）
只要有一环错位，解出来就不会正好是素材的那个正弦频率。

### 顺带说清一件没做的事

**WebM 的*画面*轨（VP9/AV1 in WebM）还没支援**：装进 MP4 需要 `vpcC`（VP9 还要
颜色信息，WebM 的 CodecPrivate 里没有）或 `av1C`，这一轮没做。真遇到时会明确报
「抓到的画面轨是 WebM/…」，而不是给你一个半成品。Chrome 上的 YouTube 走的是
MP4 里的 AV1，不受影响。

## 之后加的三样东西（都不是"用户报 bug"，但都按同一套规矩验）

用户问「整体还有可以优化的地方吗」。挑了三件做，其中**两件在实现过程中被用例
抓出了真 bug** —— 这两条比功能本身更值得记。

### 一、写盘失败不再丢数据（最该修的一件）

`mseStop()` 原来一进来就 `mse = null`，之后才写盘。所以配额一满：

```
用户等了四十分钟 → 收尾 → QuotaExceededError → 内存里的缓冲已经先被清掉了
界面上只剩一句原始错误，连"重试"都没得点
```

而这不是假设：管理页实测配额 5.6 GB，用户的产物已经 200 MB+（还因为重复快照
白占了三份 56 MB）。

**改法**：先合并、先写，**写成功了才收摊**；写失败就把**合并好的字节**留在
`s.pending` 里（原始分块丢掉，内存反而降下来），停掉每秒心跳，状态转成
`ERROR + retryable`，界面给两个出口：**重试保存 / 放弃这一份**。
SW 侧在 `retryable` 失败时**不关离屏文档**（那份字节只存在于它内存里），
并且终态之后**只接受终态消息**，否则晚到一秒的心跳会把 ERROR 刷回"正在录制"。

**验证**（`--extras` 第 8d 节，确定性用例）：配额在真机上要占 5.6 GB 才复现得了，
所以把**离屏文档**的 `navigator.storage.getDirectory` 换成抛 `QuotaExceededError`
的版本（我们 hook 页面本来就这么干），然后走完整停止流程：

```
· 收尾结果：ok=false｜retryable=true｜storageFull=true｜待保存 1128804 字节
  提示：浏览器的存储空间不够了（这次要写 1.1 MB），文件没能写出来。
        这次抓到的数据**还在内存里，没有丢** —— 别关这个标签页…然后点「重试保存」。
· 离屏文档：active=true｜待保存 1128804 字节｜目标文件名 vh-mse-…-20260921-012506.mp4
· 等待 2.5 秒后状态：error｜retryable=true      ← 心跳没有把错误刷回去
· 清出空间后重试：ok=true｜1128804 字节｜时长 12.011 秒
  ✓ 写盘失败 → 数据留在内存 → 清出空间 → 重试成功，全链路走通
```

顺带把「已导出」做成清理的凭据：管理页显示 `产物存储已用 17.1 MB / 配额 5.3 GB · 已导出 1 个可以清理`，
点「清理已导出的」真的删掉（用例断言文件从 OPFS 消失、列表刷新、那行文字变回去）。
**绝不按体积/时长猜哪几个重复** —— 那有删错的风险，而"已导出"是用户自己确认过的。

### 二、文件名带标题 + 收尾看得到进度 + 重复快照不再白写

- `vh-mse-20260921-003641.mp4` → `vh-mse-Big Buck Bunny-20260921-003641.mp4`。
  三条硬约束：**前缀必须还在最前面**（管理页靠它分组）、标题走 `sanitizeSegment`、
  长度压到 48 字。站点后缀（` - YouTube` / ` - 哔哩哔哩`）按**白名单**剥掉 ——
  通用规则会把《星球大战 - 新希望》削成《星球大战》。
- 长音频转码（WebM/Opus → AAC）要几十秒，原来那段时间界面只写"正在收尾"。
  现在把 `transcodeOpusToAac` 的 `onProgress` 接到界面上（进度条 + 百分比），
  免得用户以为卡死去点第二次停止。
- 「先保存已录到的部分」连点两次、中间没有新数据时，第二份和第一份**内容完全一样**
  （用户实测攒了三份 56 MB）。现在这种情况直接回 `identical`：
  「和刚存的那份（…）内容完全一样，没有重复写」。

### 三、画面也是 WebM 的站点：出 `.webm`，零转码

原来碰到 VP8/VP9/AV1 in WebM 只能回一句"暂不支持"。把 VP9 塞进 MP4 划不来
（要写 `vp09` 样本描述项、还要从 `Colour` 元素凑颜色信息），所以改成**出 `.webm`**：

| 新东西 | 干什么 |
| --- | --- |
| `src/parser/webm-merge.js` | 画面 + Opus 音频 → 一个 `.webm`。Matroska 用**绝对时间戳**表达"音频比画面晚 1 秒开始"，不用像 MP4 那样绕 elst |
| `vendor/webm-muxer.mjs` | 复用器（MIT / 63 KB，上游已 deprecated，见 README 已知限制里那条说明） |
| 组装结果分两种 `kind`（mp4 / webm），落盘走同一个 `saveBuilt` | 文件名、扩展名、"写不进去时保住数据"只有一份实现，不会两条路各漏一处 |

**验证**：单元 7 条（真 VP9+Opus 素材）+ 浏览器 `--extras` 第 8f 节
（测试页开两条 WebM SourceBuffer）：

```
· 产物：vh-mse-Video Hunter MSE 测试页-20260921-013748.webm｜276280 字节｜时长 6.02 秒
✓ WebM 画面产物 ffprobe：vp9 320x180｜opus 48000Hz｜6.00 秒
  · 真解一遍：150 帧画面｜音频 RMS 0.0626｜峰值 0.089｜估频 441 Hz
```

「真解一遍」这一步是刻意的：ffprobe 只能证明"容器里有轨、编码名对"，
**轨里有没有内容它不管**。所以画面走 `framemd5` 数真解出来的帧数，
音频解成 PCM 之后按过零率估频 —— 素材是 440 Hz 正弦，估出来 441 Hz，
说明"落到文件里的确实是那段声音"，而时间戳对齐那条（音频人为延后 1 秒 →
产物里 `start_time` 就是 1 秒）说明两条轨的相对位置没被吃掉。

### 两个被用例抓出来的真 bug（都值得记）

**一、`sanitizeSegment is not defined`。** 给 `titlePart()` 加了
`sanitizeSegment(...)` 却忘了在 `pipeline.js` 里 import。语法检查过、导入导出检查也过
（那一节只查"import 的名字存不存在"，不查"用到的名字有没有 import"），于是错一路溜到
运行时：**抓流收尾全线失败**，而报错发生在离屏文档里，界面上只看到"保存部分产物失败"。

修完顺手补了一节静态检查（只查一件事：**某个名字是项目里某个模块导出的、在这里被当函数调用、
而这个文件既没 import 也没定义**）。判据收得很窄，是为了不误报
（`console` / `Math` / 方法简写定义 `get(key) {` 都不算）。**并且自测过**：

```
# 临时去掉那行 import
✗ src/offscreen/pipeline.js 调用了 sanitizeSegment()，但这个文件里既没有 import 它、也没有定义它
# 临时去掉用例里的 import
✗ test/pipeline.test.mjs 调用了 partialCaptureFileName()，但这个文件里既没有 import 它、也没有定义它
```

**二、错误信息被整个丢掉。** `explainStorageError()` 返回的字段叫 `text`，
而调用方读的是 `res.error` —— 摊开对象时**没把它改名**，于是
`retryable=true` 但 `error=undefined`，界面只能显示兜底的"抓流收尾失败"。
这条是用例断言"提示必须说清数据没丢"时抓出来的：

```
✗ 提示必须说清"数据没丢"和怎么办：undefined
```

**同一类问题连着出现两次**（少 import、字段名对不上），共同点是"代码跑得通、看着没问题"。
所以这一轮的教训写在这儿：**新增一条链路时，先写出会让它失败的断言，再让它通过**。

### 测试环境自己也会骗人（顺手修的一条）

跑回归时突然 15 条用例全红，报的是「页面受限，注入不了内容脚本」。查下来是
**上一次运行留下的标签页**：那一轮 fixture 服务没起，标签页停在 Chrome 的错误页上，
而每一节都是"新开测试页 → 让扩展按 URL 去 `chrome.tabs.query` 找" ——
于是扩展被武装到了**旧标签**身上（URL 一模一样）。

修法：`runExtensionExtras` 一进来先清掉同源的残留标签，并且把那句误导人的错误
改准（区分"页面没加载成功"和"chrome:// 这类受限页面"）。**测试环境的脏数据会让功能
看起来坏掉** —— 这条同样是"别相信一次失败的表面结论"。

## 第四个需求（用户提的）：自动保存已录到的部分

用户看着抓流状态卡提的：「这里也可以加一个，自动保存已录制的部分勾选按钮哦。」
手动那份（「先保存已录到的部分」）靠"想起来才点"，靠不住 —— 他自己就连点了三次。

**先问清了一件事再动手**：这份快照每次写的是"当前整个缓冲"，所以
「每次都留一份」会让体积成倍涨（2 小时的视频按 10 分钟一存≈ 6 倍），
而"配额满"正是这功能要防的事。用户选了**滚动覆盖，只留最新一份**，
间隔在界面上可选（5 / 10 / 30 分钟，默认 10）。

实现上的几个判断：

| 决定 | 为什么 |
| --- | --- |
| 名字带 `-自动部分`，和手动的 `-部分` 分开 | 自动那份会被覆盖，手动那份**谁都不许动**。用户要留检查点就手动点一次 |
| **先写新的、再删旧的** | 中间任何一步失败只是多占一份空间；反过来（先删后写）一失败就什么都不剩 |
| 写**完整**产物之后把滚动那份删掉 | 它的内容是完整产物的子集，留着只会让用户犯嘀咕"怎么多一个更短的" |
| 内容没变（播放暂停着）时跳过 | 重复写一份一样的文件纯属白占空间（手动那份也是同一套判据） |
| 写不进去时**当场**提示，不打断抓流 | 这是"配额要满了"的早期信号，比收尾时才失败好得多 |
| 间隔允许 0.05 分钟 | 界面上只给 5/10/30，但自动化测试要把间隔调到 3 秒才验得了"到点真的会存、而且只留最新一份"。**验不了的功能等于没有** |

验证（`--extras` 第 8g 节，测试页加了 `?slow=1` 一段一段慢慢喂，模拟"数据一直在进来"）：

```
✓ 自动保存已触发：vh-mse-…-082637-自动部分.mp4
✓ 到点又存了一份、并把上一份覆盖掉：…-082637-自动部分.mp4 → …-082641-自动部分.mp4
  · 收尾之后：完整产物 1 份｜剩下的自动保存 0 份
```

### 用例一开始是"错"的，值得记一笔

第一版用例断言"任何时刻只能存在一份自动保存"。跑出来失败：

```
✗ 自动保存应该滚动覆盖，却同时存在 2 份：…-082237-自动部分.mp4、…-082234-自动部分.mp4
```

**这次是期望错了，不是代码错了**：先写新的、再删旧的，中间必然有几十毫秒的重叠
（那是故意的取舍）。所以改成"**静下来之后**只剩一份 + 名字确实换过"。
判据要盯的是稳态，不是那一瞬间 —— 否则测试会逼着实现去做一个更危险的顺序。

### 顺手挖出来的两个真 bug（都不是用户报的）

**一、离屏文档里没有 `chrome.storage`**（Chrome 153 实测：只有 `chrome.runtime`
外加 `loadTimes` / `csi`，一共 3 个）。

这一条炸出两个后果：

- 我这版自动保存**一开始根本没生效** —— 它在离屏文档里读设置，抛异常，而我又
  写了个 `.catch(() => {})` 把错误吞了。**沉默的兜底是最贵的**。
- 更早的问题：**产物索引（media index）从来就没写进去过**。原来离屏文档直接调
  `mediaIndex.remember()`，`chrome.storage` 是 undefined，而 `media-index.js`
  内部把读写都包在 try/catch 里 —— 所以**调用不报错、索引一条都没写**。
  它一直靠管理页的回退路径（读文件头）撑着，直到这一轮加了 WebM 产物：
  **WebM 没有 mvhd 可读**，于是列表里永远显示"时长未记录"。

修法：索引写入挪到 service worker（它有 storage）——
请求-响应那条路（收尾 / 切段 / 手动快照 / 录制停止）由 SW 拿到返回值时直接记，
离屏文档自己发起的滚动保存则通过 `MSG.INDEX_REMEMBER` / `INDEX_FORGET` 转发。
自动保存的配置同理：由 SW 读好、随 `OFFSCREEN_MSE_START` 传进去，
设置变更走 `chrome.storage.onChanged` 转发，用户改完间隔立刻生效。

验证（这一段专门盯"索引真的写进去了"）：

```
· 索引里这一份：时长 6.021｜体积 276280
· 管理页那一行：vh-mse-…-082628.webm 时长 00:06 · 270 KB · 2026/9/21 08:26:28 [保存到磁盘][体检][删除]
```

体积是 SW 那条路才有的（离屏文档写不进索引，回退路径只能补时长），
而 **WebM 那一行能显示时长**就是最直接的证据 —— 它没有 mvhd，只能靠索引。

**二、同一个对象字面量里重复的键。** 我给会话对象加自动保存配置时，
上面写了 `autoSnapshot: {...}`、下面还留着旧的 `autoSnapshot: null` —— 后者静默覆盖前者，
于是 `s.autoSnapshot.enabled` 读的是 null，**每一条抓流启动都直接抛异常**：

```
✗ 续播用例里启动抓流失败：Uncaught TypeError: Cannot read properties of null (reading 'enabled')
✗ WebM 画面用例里抓流启动失败：已经在抓流中
…13 条用例一起红
```

语法检查发现不了（合法 JS），运行时报的又是一句跟"重复键"毫不相干的类型错误。
所以又加了一节静态检查（见下）。

### 两节新的静态检查，都自测过

第 7 节的兄弟问题连着出现了两次（少 import、重复键），共同点是
**"代码跑得通、看着没问题"**，所以都做成了 `npm run check` 的一部分：

| 检查 | 抓什么 | 自测 |
| --- | --- | --- |
| **跨模块调用** | 某个名字是项目里某模块导出的、在这里被当函数调用，而这个文件既没 import 也没定义 | 去掉 `pipeline.js` 的 `sanitizeSegment` import → 报；去掉用例里的 `partialCaptureFileName` import → 报 |
| **重复键** | 同一个对象字面量里出现两次同名键 | 把 `autoSnapshot: null` 加回去 → 精确报出 `offscreen.js:263`，并指出第 253 行已经有一个 |

写这两节的过程本身也踩了"检查会撒谎"的坑，都记下来：

- 跨模块检查第一版**误报**：`store().get(key)` 这种**方法简写定义** `get(key) {`
  被当成调用（`test/media-index.test.mjs`）。加了"行首缩进 + 参数表后跟 `{`"的排除。
- 重复键检查第一版**误报 15 处**（dash.js 的 DRM 名单）。两个原因：
  ① 单/双引号字符串**不能跨行**，我的字符串剥离器没在换行处收手，于是一个撇号
  会把后面真正的代码当成"字符串内容"放过；② 三元表达式 `a ? b : c` 里的 `b :`
  也被当成键（`t: Number.isFinite(t) ? t : null` 就这么中招）。
  修法是"键必须在 `{` / `,` / 行首之后"，外加一串关键字白名单。
- **一个动不动就报错的检查最后只会被绕过** —— 所以这两节都先把整个仓库跑干净再收工。

## 第五个需求（用户提的）：从当前进度开始抓 + 两条界面要求

用户原话：「抓流…只有点击抓流的时候自动刷新并将视频从头播放，可以加一个功能抓流可以根据
当前播放的进度开始抓流但是依旧要刷新一下浏览器界面…还有就是插件的介绍可以放在鼠标放在
两者区别的那个问号的时候再显示…还有一个就是管理要放在抓流的右边这样方便点。」

### 一、从当前进度开始（仍然刷新）

**先说结论：刷新不能省。** 钩子必须在播放器 `addSourceBuffer` + 第一次 `appendBuffer`
（初始化段）**之前**就位，否则只捞得到没有 `moov` 的分片。试过想绕开（`video.load()`、
强制重建 MediaSource），都是站点相关的赌博，不能作为默认行为。

所以做法是**刷新 + 回到你那一秒**，而且要教会"起播看护"这件事 —— 它原来的职责**恰好相反**：
把站点自己的续播扳回 0（那是"产物中间横着几百秒空洞"的成因）。现在它看住的是**你要的那一秒**，
而且**只往一个方向使劲**：

| 情况 | 看护的动作 |
| --- | --- |
| 站点刷新后从头播（位置 0） | **往前拨**到目标 |
| 站点自己续播到目标附近 | 不动（容差 2.5 秒，不为 1 秒去和播放器抢） |
| 站点续播到**目标之前**（中途重置回 0、位置落后） | 往前拨到目标 |
| 播放位置**跑到目标前面**（正常播放、快进、倍速） | **不动**（见下面第六节：这条写成"偏离目标就拉回"就是"一直往后退"） |
| 目标就是 0（用户关掉了这个功能） | 老行为：只在"往前跳"时扳回 |

另外两处细节：

- **目标往前退 3 秒**：扫页面、注册钩子、刷新页面都要花时间，接缝处宁可多一点也不要缺；
- 位置是**点下去那一刻现扫的**（面板可能是几秒前打开的）。实测：点按钮之后面板要真扫一次
  页面才拿得到位置，这期间视频还在往前走（本轮实测：页面 7.35 秒时点下去，最终记下的
  是 8.43 秒 = 那一刻读到的位置 − 3 秒），所以"记下的位置"比"点下去的位置"晚一点点，
  但**只要它不早于你点下去的位置**就不会漏内容（看护会把你拨回目标，重放一点点比缺一段好）。

顺带一个好处：这同时**缓解了超长视频的内存问题** —— 3 小时的视频抓后半段，产物只有 1 小时。

### 二、说明收进问号里 + 「管理」挪到「抓流」右边

- 底栏现在是：`抓流 管理 录制 ? 清空 设置`（用户要求"管理放在抓流右边，方便点"）；
- 两种模式的对比**默认完全不显示**，鼠标移到「?」上（或键盘 Tab 聚焦）才浮出来一张卡片。
  用 CSS 的 `:hover` / `:focus-within` 实现，**没有 JS 切换** ——
  顺带解决了老实现的两个问题：点开之后把媒体列表往下挤、以及两个面板互相挤。
  （一开始我以为"悬停"在无头浏览器里验不了，试了一下才发现 CDP 的
  `Input.dispatchMouseEvent` 会走 `:hover` 的命中测试 —— 于是它现在是断言的一部分。）

### 验证

在真浏览器里量 DOM 和位置（`--extras` 第 1b 节 + 5b 节）：

```
· 面板底栏：capture → manage → record → mode-help-q → clear → settings-toggle
  ✓ 「管理」就在「抓流」右边
· 说明卡：问号="?"｜默认 display=none｜position=fixed｜含对比内容=true
  ✓ 说明收在问号里：默认不显示、是浮层，不会把列表挤下去
· 展开后卡片范围：left 8 → right 397（弹窗宽 420）｜top 52 → bottom 539（高 600）｜需要滚动=false
  ✓ 说明卡完整落在弹窗里，不会被裁（这条是第六节那个 bug 的断言）
· 页面在 7.35 秒时点「抓流」→ 后台记下的 startAt=8.4257
  ✓ 「从当前进度开始」整条链路通了：页面位置 → 面板 → 后台
· 带 startAt=6 武装：从 0 秒 → 7.40 秒（内容脚本回报 startAt=6）
  ✓ 从当前进度开始抓：位置被拨到了目标那一秒
· 站点把位置设到 6.5 秒之后：7.65 秒
  ✓ 站点续播到目标附近时，看护不会多事把它扳回开头
· 设了 startAt=6 之后正常播放 4 秒：6.06 → 10.3（最大回退 0.00 秒）
  ✓ 抓流不会把正在往前播的视频往回拽（第六节的 bug，修之前这里只有 1.32 秒）
```

### 用例之间的一个坑（记一笔）

新加的"带 startAt=6"用例和原有的"6 倍速不该被打断"用例**在同一个页面上互斥**：
前者的目标留在 6 秒，后者从 0 开始以 6 倍速往前播 —— 看护会一路把它拉回 6 秒
（那是它的职责），于是"位置不该回退"的断言**误报**成"被扳回 4.18 秒"。

这不是产品 bug，是**用例污染**：所以我在这两条之间加了一句"把目标复位成 0"。
判断依据是看日志里的方向（回退 4.18 秒 = 从 10 秒被拉回 6 秒，而不是被拉到 0）——
**失败信息里的数字要能解释得通，解释不通就别改代码。**

得在真站点上抓一次、对着产物开头看。已列进下面的未验证清单。

## 第六个需求（用户提的）：三处收尾 —— 说明卡显示不全 / 一直往后退 / 进度条落点

用户原话（一次报了三件）：「他这个根据当前进度抓流，它一直往后退呀…播放 3 秒一直往后退，
播放 3 秒就相当于它不会往后走了」「我点进度条中间一半的位置，它实际播放的位置是我鼠标位置
的前一段…抓流是通过完整从头录制这种抓流，还有还有就是根据当前录制抓流。这两个文件都是
这样的」「问号说明卡点击问号显示不完全」。

三件事里只有第一件是"新功能没做好"，另外两件**都是我上一轮自己写出来的 bug**，所以下面
每一件都按"先做出能抓住它的用例/探针，再改代码"来办。

### 一、说明卡「显示不完全」：它其实一直糊在弹窗外面

对比卡片原来挂在「?」旁边，用的是 `position: absolute; right: 0; width: 420px` ——
而**弹窗本身宽 420 px**，所以卡片是从问号往左铺出去的：左半边被弹窗边界裁掉，
看起来就是"点开显示不全"。

修法不是去调那几个像素，而是换定位坐标系：改成 `position: fixed` + 四边内缩
（`left/right: 8px`、`top: 52px`、`bottom: 46px`），高度不够时**卡片自己滚动**，
永远落在弹窗里。

真浏览器里量的（`--extras` 第 1b 节，弹窗按 420×600 模拟）：

```
· 展开后卡片范围：left 8 → right 397（弹窗宽 420）｜top 52 → bottom 539（高 600）｜需要滚动=false
```

也就是四边都在弹窗内、而且这个尺寸下连滚动都不需要。

### 二、「根据当前进度抓流」一直往后退（真 bug，我写的）

**现象**：设了目标那一秒之后，视频每播 2.5 秒就被拽回去一次，于是"播放 3 秒相当于没往后走"。

**根因**是上一轮我写的判据：目标是"你要的那一秒"时，我用的是
`Math.abs(当前时间 − 目标) > 容差(2.5 秒)` —— **绝对值**。正常播放当然会不断远离目标
（目标固定，时间在涨），于是每一次轮询都判定为"漂移"，把位置拉回目标。**目标越老，
拽得越频繁**，用户看到的就是"一直往后退"。

**修法**：分方向。目标大于 0 时：

| 判据 | 动作 |
| --- | --- |
| `t < 目标 − 2.5`（落后了） | 往前拨到目标 |
| 位置在涨、而且已经跑到目标前面 | **不动**（这是正常播放/快进/倍速） |
| 第一次观测就落后 | 往前拨 |

目标等于 0（功能关掉）时保持老判据不变 —— 那条路已经验过，不能顺手改。

**验证**：在浏览器里给页面武装 `startAt=6`，然后让它正常播 4 秒，量最大回退量。

```
修之前：6.06 → 7.38（最大回退 2.78 秒）     ← 4 秒只前进了 1.32 秒
修之后：6.06 → 10.3 （最大回退 0.00 秒）     ← 4 秒真的走了 4.24 秒
6 倍速的用例：0.3 → 9.43（最大回退 0.00 秒） ← 倍速没有被当成"漂移"
```

（这条也提醒了一件事：**"容差"配"绝对值"是危险的组合** —— 只要参考点在动，
容差再大也会被追上。方向上必须写清楚。）

### 三、进度条落点：产物时间轴开头横着一截空白（真 bug，我写的）

**现象**：PotPlayer 里点进度条中间，播放位置落在鼠标位置**之前**一段；而且用户强调
"从头完整录制"和"从当前进度开始"两种产物都是这样。

**先量清楚**再用结论。上一轮写过一个**临时**探针（跑完就删，做法留在这里：往抓流会话里
灌**源流第 6 秒之后**的分片来模拟"从中间开始抓"，再把产物摊开看盒子和 ffprobe）：

```
修之前（从 5.92 秒处开始抓的 6 秒素材）：
  mvhd.duration = 12000ms                     ← 内容是 6 秒，却声称 12 秒
  elst = [{segmentDuration=5920, mediaTime=-1（空编辑）}, {…6080…}]
  Chrome 里 seek 到 3.0 秒 → 落到第 5.92 秒的帧   ← 用户报的"落在鼠标前面"
```

**根因**在 `mergeFmp4` 写 elst 的那一行：它把**源流的绝对原点**照抄进了产物
（"影片 0 秒 = 源流媒体时间轴的哪一点"）。源流从 0 开始播时这是对的（差值是几十毫秒级的
B 帧呈现领先量），但抓流**可以从中间开始** —— 源流的原点还在第 0 秒，而我们的样本从第
5.92 秒才开始，于是每条轨都得到一个"开头空 5.92 秒"的空编辑：进度条按 `mvhd` 铺满 12 秒，
前 5.92 秒**一个样本都没有**，拖进去只能退回第一个样本。

**修法**：不再用源流的绝对原点，改成**"所有轨里最早的那个样本就是产物的 0 秒"**：

```
firstInMovie_i = (本轨第一个样本的 DTS − 源 elst 的 media_time) / 本轨 timescale
earliest       = min(firstInMovie_i)
elst_i         = earliest − firstInMovie_i      （负数 = 空编辑 = 这条轨晚开始）
```

两个要点：

- **轨与轨之间的相对位置一个字节都没动**（音视频对齐靠的正是这个差量），整体只是平移；
- 晚开始的轨写成**空编辑**（推迟），而不是用正数 `media_time`（裁掉开头）——
  后者会真的丢样本。判据是 `firstInMovie > 1` 秒时给出提示（说明这段是中途开始抓的）。

**验证一（真抓流，不是单测）**：同一个探针，修完之后：

```
mvhd: duration=6006（6.006 秒）
trak#1 视频：没有 edts/elst，起点 0.08
trak#2 音频：elst = [{segmentDuration=11, mediaTime=-1}, {segmentDuration=5995, mediaTime=0}]
             ← 空编辑从 5920 ms 降到 11 ms（这 11 ms 是源流两条轨自己的零点差）
关键帧时刻：0.08, 2.08, 4.08
Chrome 里 seek 到 3.03 秒 → 实际画出来的是第 3.00 秒的帧
```

**验证二（单测，先证明它能抓住 bug）**：`test/merge.test.mjs` 新增
"从中间开始的一段（源 6 秒之后）"：取 dash-split 的第 4~6 片（源 6.000~12.000 秒）
合并，断言时长约 6.08 秒、两条轨起点都贴近 0、**样本一帧不少**（视频 150、音频 285 =
94+93+94+4）。把代码改回旧规则跑一遍，它确实红：

```
中途开始的一段：时长 6.091 秒（源片段 6.08 秒） · 视频起点 5.920000 · 音频起点 5.931000 · 帧 150/285
AssertionError: 视频起点应贴近 0，实际 5.920000
```

修完之后整个套件 192/192 通过（这个文件里从 0 开始的那个用例也一并改了断言，
见下面那条）。

**验证三（真实站点，确认这条路没被带坏）**：改完重跑 `--site` 探针（YouTube 上的
Big Buck Bunny 4K，40 秒）：

```
· 抓流：收到 53 段｜1.60 MB（video/mp4 av01 35 段 + audio/webm opus 18 段）
· 收尾产物：av1 640x360｜aac｜40.00 秒
· 两条轨的起点：视频 0.000000｜音频 0.000000（差 0.000 秒）
```

真实站点的 init 里 `elst` 的 `media_time` 就是 0，所以新规则对它是**恒等变换**：YouTube
这条路（抓流 + WebM/Opus 转码）新旧结果一模一样。会变的是"源流 elst 自带 composition
领先量"那类素材（比如本仓库的 DASH 夹具），差别是下面这条。

### 这一轮里"改了对的期望，而不是改代码"的一次

改完之后，原有用例 `合并产物：ffprobe 同时读到 h264 视频轨和 aac 音频轨…` 红了一条：
`视频起点应约 0，实际 0.080000`。

**这条期望本来就是错的**（更准确地说：它断言的是旧规则下的现象，而不是源流的事实）。
源 init 的 elst 写的是 `media_time = 1024/12800 = 0.08` 秒，**正好等于视频第一个样本的
composition 领先量** —— 它的意思是"第一帧就呈现在影片 0 秒"，而不是"裁掉开头 80 ms"。
旧代码把 elst 当裁剪刀用，所以那条轨的 `start_time` 恰好是 0；新规则不改写源流的意图，
只把"谁先开始"整体挪到第一个样本上，于是 ffprobe 读到：

```
视频起点 0.080000（B 帧呈现领先量）
音频起点 0.059000（= 源流 elst 说的 0.0213 秒，加上整体的 0.0587 秒平移）
两条轨的差 0.0213 秒 —— 和源流 elst 里的差一模一样
```

所以断言改成"**两条轨的相对偏移必须等于源流的 21.3 ms**"（比原来的"都等于 0"更严格：
原来的产物把音轨往前挪了 21 ms 才对齐，那才是丢掉的精度）。另外补一条"时长不能变长"，
把"绝对原点被算进时长"这个形状钉住。

**代价要说清楚**：从 0 开始的产物现在开头有 80 ms 没有画面（`mvhd` 12.011 秒 → 12.091 秒），
换来的是"从中间开始抓"不再产生几千秒的空白 —— 同一个函数、同一条规则，不可能只对一种形状生效。
两条路（TS/mux.js 那条和 DASH 这条）现在**行为一致**了，而 TS 那条是用户拿 PotPlayer 验过的。

### 还没有做到的：PotPlayer 的"按关键帧定位"

用户报的"落在鼠标位置前一段"里，有一部分**不是文件的问题**：只按关键帧定位的播放器
（PotPlayer 默认如此）会落到请求位置之前最近的那个关键帧，差多少取决于**源流的关键帧间隔**
（本仓库夹具 2 秒；B 站/YouTube 常见 2~10 秒）。产物的样本表是完整的：Chrome 里
拖到 3.03 秒画的就是第 3.00 秒的帧。所以这条只能如实写进 README 的已知限制，并给出
"在 PotPlayer 里把定位方式改成精确"这个出路 —— 不能靠改文件元数据解决。

## 第七个真 bug（用户报的）：合并提示条"写着能合，点了说不能"

用户原话：「这里要真真正正做一个检测，因为有些没有双轨道或者是多个独立轨道。比如说哔哩哔哩
那种视频的格式，它也会显示这几个字儿，检测到多个独立轨道，然后合并下载。然后，但是我点合并
下载的时候，它又提示要需要有两条轨道才能合并，这明明就是你没有做一个判断的逻辑。而且这个
这个页面上的字是写死的，它不是动态的。」

两句话正好指向两个独立的错，都得修，而且**第二句（字是写死的）才是真正的根因**。

### 一、`hidden` 属性从来没生效过（根因）

`.mergebar` 在 CSS 里写着 `display: flex`。**作者样式永远压过浏览器默认样式表里的
`[hidden]{display:none}`** —— 这跟选择器优先级无关，是"作者来源 vs 用户代理来源"。
于是 `bar.hidden = true` 是**静默失效**的：这条提示条从打开面板那一刻起就一直挂着，
上面显示的是 HTML 里写死的那句话，跟实际嗅到了什么毫无关系。而它旁边的按钮一直是可点的，
所以点下去才会走到那句 `if (standalone.length < 2) → toast('至少要有两条轨道才能合并')`。

同一个原因坏掉的不止一条，一共四处（用脚本把"带 hidden 属性的元素"和"CSS 里有 display 的
选择器"对了一遍）：

| 元素 | class 的 display | 后果 |
| --- | --- | --- |
| `#mergebar` | `flex` | 永远显示，文字写死 —— **用户报的这个** |
| `#mse-hint`（抓流提示条） | `grid` | **不是 MSE 的页面**也显示 |
| `#recbar`（录制条） | `flex` | 没在录制也显示"录制中" |
| `#settings`（设置面板） | `flex` | 默认就是展开的，"设置"按钮点了没反应 |

用户那张截图（目标页是**新标签页**）上四条全中：录制条、合并条、抓流条一起挂着，列表是空的。

修法是一行，两个 CSS 文件各一份：

```css
[hidden] { display: none !important; }
```

`!important` 是必需的：要压过上面任意一种 `display` 声明。

### 二、判据本身是错的：它数的是"分片条数"，不是"有没有东西可合"

原来的判据 `standalone.length >= 2`（没有配套播放列表的**分片** ≥ 2 条）。B 站的形态是：

```
视频轨：GET .../xxx.m4s   Content-Type: video/mp4   → 分类成 SEGMENT（进 standalone）
音频轨：GET .../yyy.m4s   Content-Type: audio/mp4   → 分类成 AUDIO（**不进 standalone**）
```

`classify.js` 先看 MIME，而 `audio/*` 的分支在前面 —— 于是音频轨被判成"音频文件"，
压根没被算进"独立轨道"。面板认为只有 1 条，判据不成立，合并必失败。

新的判据抽成了纯函数 `src/core/merge-plan.js`（可单测），它按"看出来是什么轨"分三类，
并且**和解析器真正做的事对齐**（解析器要一条视频轨，音频可有可无）：

| 形态 | 提示条 | 按钮 |
| --- | --- | --- |
| 视频 N + 音频 M | `检测到 N 条视频轨 + M 条音频轨（约 X） · 可合并成一个 MP4` | 有 |
| 只有视频 | 1 条：`只看到 1 条视频轨，没有音频轨（约 X） · 合并出来会是没有声音的 MP4`；多条：`检测到 N 条视频轨，没有音频轨（约 X） · 合并只用体积最大的那条` | 有 |
| 只有音频 | `只看到 M 条音频轨，没有视频轨（约 X） · 合并至少需要一条视频轨` | **没有** |
| 只有 `.m4s`、没有 MIME | 1 条：`检测到 1 条独立轨道（约 X） · 看不出是视频还是音频，合并时按内容识别`；多条：`检测到 N 条独立轨道（约 X） · 合并后自动识别音视频` | 有 |
| 都没有 / 有播放列表 | 不显示 | — |

配套的三处：
- `startMerge` 用**同一个函数**重算一遍（面板显示到点击之间，B 站可能才把音频轨请求出来），
  送进任务的轨道也从 `standalone` 换成 `plan.tracks` —— **音频轨这才第一次进了合并任务**；
- HTML 里那句写死的文案删掉了（留空，由 JS 填）；
- 「抓流提示条」的判据里加了一项 `plan.canMerge`：真能合并时不再劝用户去抓流。

### 验证（先让用例红，再修）

## 第八个真 bug（用户报的）：暂停之后再点「停止并保存」，34.7 MB 全没了

用户原话：「这个是我先暂停播放中的视频，然后再点击停止并保存，就会出现这个错误，然后导致我
发现录制的东西都没有了」。面板上的报错是：

```
停止失败
addVideoChunkRaw's third argument (timestamp) must be a non-negative real number.
```

状态卡还停在「334 段数据 · 已存 0 个 · 34.7 MB」，然后就没有然后了。

这是**两个**问题叠在一起：一个让收尾必然失败，另一个让失败变成"全丢"。

### 一、根因：采集到的分片**不一定按时间顺序到**

先复现再改。用 dash-split 的两片（源 0~2 秒、2~4 秒）拼出三种到达顺序，直接喂
`mergeFmp4`：

```
正序（正常情况）：✗ 抛错 → ENOENT（这是我探针自己的问题，合并本身是成功的）
倒序（第 2 片先到，然后才补第 1 片）：✗ 抛错 → addVideoChunkRaw's third argument
                                             (timestamp) must be a non-negative real number.
音频倒序 + 视频正序：              ✗ 抛错 → addAudioChunkRaw's third argument ...
```

**一字不差就是用户看到的报错**。

为什么会倒序：抓流采的是 `appendBuffer` 的原始分片，拼的时候按**到达顺序**接。
而播放器**重新缓冲、往回拖一点、暂停再继续，都会把已经送过的分片再送一次**。
`groupBuffers` 按"整块字节的内容指纹"判重 —— 字节不完全一样就漏过去了
（Range 分段、预取、重建 SourceBuffer 之后补的那一份都会这样）。

归零用的是**第一个样本**的 DTS，于是后面那些时间更早的样本算出来就是负数时间戳，
muxer 当场拒绝；即便不是负数，DTS 回退也会撞上另一句
`Timestamps must be monotonically increasing`。

**修法**（`normalizeTrackSamples`，纯函数、导出可单测）：合并前把每条轨的样本整理一遍

1. **按 DTS 排序**（已经有序时一次都不动，下载/HLS 那两条路完全不受影响）；
2. **丢掉完全被已收内容覆盖的重复样本**，以及起点与前一个样本相同的；
3. 起点用排序后的第一个样本 —— 保证没有任何时间戳是负的；
4. 负的**呈现时间戳**（B 帧重排的边角情况）就近纠正为 0 ——
   和音频转码那条路对"时间戳回退"的处理一致。

三件事都会**如实上报**（"顺序是乱的…已重新排好" / "有 N 个重复样本…已去掉"），
因为这是我们动了用户的样本，不能静默。

### 二、为什么"失败"会变成"全丢"

`mseStop` 里原来是：

```js
const built = await assembleMseCapture(s);
if (!built.ok) { releaseMse(); return { ...built, durationMs }; }
```

- `assembleMseCapture` 内部的 `mergeFmp4` **抛异常**时，`built` 根本不存在 ——
  异常一路飘出去，会话停在"出错"，而**那 334 段没有任何出口**：既写不出来，
  也重试不了，界面上的「重试保存 / 放弃这一份」只对"写盘失败"显示。
- 这就是用户说的"录制的东西都没有了"。

写盘失败那条路早就改成"保住数据 / 可重试 / 可放弃"了，合并这条路是漏的。
现在合成一个 `safeAssemble()`（异常转成返回值，**绝不外抛**），并把四个调用点
全部改过去：

| 调用点 | 合并失败时的行为 |
| --- | --- |
| 收尾（停止并保存） | `retryable: true` + `awaitingRetry`：**原始分块留在内存里**，界面给「重试保存 / 放弃这一份」 |
| 先保存已录到的部分 | 如实报错，抓流不受影响 |
| 滚动自动保存（定时器） | 跳过这一次，**绝不打断抓流** |
| 换集切分（边界事件） | 不切、不清空缓冲，下次收尾还会把它一起写出去 |

`mseStatus()` 里 `awaitingRetry` 也把"合并失败"算进去（否则界面不会给那两个按钮），
自动保存也会在等重试时停下（再抄一份只会多占内存）。

### 验证

**单测**（`test/merge.test.mjs` 新增）：同一段内容按**正序 / 倒序 / 重复**三种方式到达，
产物必须**完全一致**：

```

        视频轨收到的分片顺序是乱的（播放器把已经送过的部分又送了一遍），已按时间戳重新排好
  产物 ffprobe：h264｜4.00 秒｜100 帧

  ✓ 合并失败时数据留在内存里、状态可重试（不再是一句英文报错 + 全丢）
· 「放弃这一份」之后：丢弃 150 KB｜还在抓流=false｜还等重试=false
```

第二条用例是**故意造一个必然失败**的输入：把 `avc1` 样本描述项里的宽高改成 0

### 核实后**不是** bug 的（记下来，免得下次再被报一遍）

- 「MV3 service worker 被回收后，重试入口就丢了」：**不成立**。`retryable` 是从
  `getRecording()`（`chrome.storage.session`）里读的，SW 重启后还在；离屏文档的生命周期
  也不跟着 SW 走，`pending` 里的字节还在。
- 「录制收尾失败没有重试出口」：成立，但**数据在 OPFS 文件里**（录制是边录边写盘），
  不是"全丢"；而且 `stop()` 里先置 `session = null` 是为了防止重复收尾双击。
  没有为它加"重试"—— 拿不到"第二次 finalize"的语义，加了反而是假的。
- 「终态上报后 1200ms 关离屏文档，会打断正在进行的重试」：`ERROR` 上报只来自**录制**
  那条路；抓流的可重试失败是走"停止"那条响应，那条路明确**不关**离屏文档（`awaitingRetry`）。
- 「自动保存滚动覆盖会丢文件」：新文件先写成功、再删旧的，删失败只是留个孤儿文件，
  而列表是直接枚举 OPFS 的，孤儿照样看得见。

### 这一轮**没有做**的两件事（都是产品决定，不是技术问题）

1. **fMP4 直播也走收尾组装**（让产物可拖）：能实现（TS 那条路已经是现成的模板），
   但要新建 live fMP4 夹具 + 端到端用例，而且为了内存必须设上限 —— 属于新功能，先如实
   把限制写出来（本轮已做），要做再单独一轮。
2. **抓流的"攒到多大就自动切成一段"**：这是**剩下最大的一个真风险**。实测（在渲染进程里）
   单次 ArrayBuffer 分配 1536 MB 还行、2048 MB 会失败，而合并产物要靠 muxer 输出一整块
   （内部还会翻倍），所以**抓到的数据超过 ~1 GB 就很难收尾**；而滚动自动保存写的是
   "当前整个缓冲"，同样会在超过这个量之后开始失败（只写 console.info，界面上看不出来）。
   现在没有任何按体积的判据。**问过用户要做哪种**（见下一节），没得到答复前不动。

### 用户选了之后：实现了「提醒 + 自动切段（默认开）」

用户选的是 `提醒 + 自动切段（默认开）`。做完的样子：

- **判据**（`src/core/capture-limits.js` 里的 `captureCutPlan`，纯函数、5 条单测）：
  每秒心跳里看体积，`bytes >= threshold` 就切；`off / retry-pending / cutting / empty / below`
  五种"不切"的理由各有名字（等重试时绝不能切 —— 只会再失败一次）。
- **动作**：复用「换集切分」那条已经验过的 `mseCut()` —— 写出一段**完整文件**、清空缓冲、
  抓流继续（`s.parts` 递增，所以文件名是 `…-2`、`…-3`，按顺序就是完整内容）。
- **阈值**：默认 **600 MB**（抄直播那条路已有的 `LIVE_MEMORY_LIMIT`，同一个"内存吃不下"
  的判断，不另立标准），可选 300 / 600 / 1200，能关。
- **说出来**：切段是"把用户的一个视频变成两个文件"，所以①切之前在 75% 处提醒一次；
  ②切完把「已经攒到 X MB，先存下一段完整文件（…），接着往下抓」推给**面板**（弹一次）
  和**管理页**（提示条 + 日志）。关掉这个功能时，提醒换成"再大下去收尾会失败，建议现在
  手动存一份"。

**真浏览器验证**（`--extras`，阈值走真实设置通道调到 0.05 MB；管理页**在抓流期间开着**）：

```
· 管理页上的那一句：「抓流进行中 已经攒到 150 KB，先存下一段完整文件（vh-mse-Video Hunter MSE 测试页-20260921-233844.mp4），」
· 阈值 0.05 MB：切了 1 次｜之后缓冲 0 段 / 0 B｜抓流还在跑=true
  切出来的那一份：vh-mse-…-233844.mp4｜ffprobe：h264｜2.00 秒｜50 帧
  ✓ 自动切段：切出来的那一份是完整 MP4，切完继续抓、最后还能正常收尾
  最终产物：2.00 秒（切段之后的这一段）
```

这个用例本身也踩了两个坑，都记在这儿（都是"用例写错、不是代码错"）：
① 第一版引用了不在作用域里的 `mseTabId`（那段代码不在第 8 节的 try 里），而且
"阈值已改小、恢复却写在 try 末尾" —— 一抛错就把 0.05 MB 留在设置里，后面几个抓流用例
的数据全被提前切走，连报了好几个看着毫不相关的错（"没有捕获到任何数据"）。
**改全局设置的用例，恢复必须写在 `finally` 里**；
② 第一版等抓完才打开管理页去读提示 —— 那条提示是"抓流进行中"推过去的、只显示一次，
早被"抓流完成"覆盖了。要验渲染就得**页面在场**。

### 顺手做的一次结构性整理：把纯规则从"封装器模块"里搬出来

查这次改动的影响面时发现：`service-worker.js` 与 `recorder.js`（管理页）都在

那种"第二份版本号"删掉）；`package.json` 的版本与它不一致时会打印一句提醒。

### 为什么打包也值得写脚本（这一步最容易漏）

零构建的项目，"能跑"一直靠"目录里什么都有"。打成包之后，**漏一个文件就是运行时才炸**，
而且最容易漏的三处症状都很远：

| 漏了什么 | 什么时候才发现 |
| --- | --- |
| `vendor/mux.min.js` | 解析器页点「开始下载」才报"mux.js 没有加载" |
| `src/content/mse-hook.js` | 抓流一个字节都收不到（钩子没注入到主世界） |
| `src/offscreen/offscreen.html` | 录制和抓流全废，报错在离屏文档里，界面上只有一句兜底 |

所以脚本做的不是"压缩"，是**检查**：manifest 的图标/入口、每个 HTML 的
`script/link/img`、每条 JS 的相对 `import`、每个 CSS 的 `url()`，全部必须落在包内
（解析相对路径、跳过绝对 URL）。白名单之外的东西混进来也会当场拦下 ——
多带 `tools/`、`test/`、`node_modules/` 平时**没有症状**，但这正是"包不干净"的来源。

### 验证：三层，最后一层才是真的

**① 打包器自己的检查**：`npm run pack` 先跑完整静态体检，再反查引用（见上）。

**② 解压出来的包与源逐字节比对 + 换一个独立工具读 zip**：

```
源 51 个｜包内 51 个｜漏 0｜多 0｜内容不一致 0
✓ 解压出来的包与源逐字节一致，且没有任何多余文件
tar -tf dist/video-hunter-0.1.0.zip → 51 个条目（Windows 自带 bsdtar 能正常读）
```

**③ 从包里加载，跑完整浏览器回归**（这是唯一能证明"包装对了"的一步）。
为此给 `browser-check.mjs` 加了 `--extension <目录>`：默认加载仓库根目录，
指到哪就从哪加载。

```
node tools/browser-check.mjs --port 9333 --extension dist/video-hunter-0.1.0 --e2e … --extras …
✓ 扩展已加载，ID = jaccmcjnhnlhagaibfbohmmnbjcbigjd     ← 与从仓库根目录加载的 ID 不同
✓ popup / 解析器 / 抓流管理 / 离屏文档 全部渲染正常
✓ 自动切段：切出来的那一份是完整 MP4，切完继续抓、最后还能正常收尾
✗：0｜✓：43
```

扩展 ID 变化本身就是证据：Chrome 的未打包扩展 ID 由**路径**决定，
三个不同路径（仓库根、`.tmp/packed`、`dist/video-hunter-0.1.0`）跑出三个不同 ID，
说明它确实是从"包"里加载的，不是又跑了一遍仓库。

### 顺带记两个自己踩的坑

- `0o100644 << 16` 在 JS 里是**有符号**的（负数），直接 `writeUInt32LE` 抛
  `ERR_OUT_OF_RANGE` —— zip 的 external attributes 必须 `>>> 0`。
- 第一次的验证目标是**临时解压目录**（`.tmp/packed`）。那不算错，但我交给用户的是
  `dist/` 里那份，所以最后又用 `dist/video-hunter-0.1.0` 原样跑了一遍 ——
  **验证的必须是真正交付的那一份**。

## 第十一轮：按「视频内容时长」自动保存 + 产物自动导出（用户提的，0.2.0）

用户这一轮的反馈里，两件是明确需求、一件我**故意没做**（原因见最后）。

### 一、「每 N 分钟」到底按什么算 —— 现在可以选

用户的疑问很具体：「这个应该是物理的 10 分钟，而不是我通过抓流在视频流中的 10 分钟…
然后可以添加一个视频流中的 10 分钟」。他**开着倍速插件**用，所以这两个数能差好几倍
（4 倍速下"录制 10 分钟"= 内容 40 分钟）。

做法：
- 新增 `autoSnapshotBasis`：`wall`（录制时间，默认） / `media`（视频内容时长），
  面板设置和管理页抓流卡上都能选；
- 内容时长从**分片自己的 tfdt** 推出来（`readFragmentMediaTime`：只走
  `moof→traf→tfhd/tfdt` 那几个字节，不解样本、不拷数据）；
- 判据抽进 `autoSnapshotPlan`（纯函数）：「不到点」必须和「该写」一样有名字；
- ⚠️ **量不出来时回落成挂钟**（WebM 没有 tfdt），并当场说明 ——
  绝不能因为"量不出来"就永不保存，那等于把安全网拆掉。

### 二、产物自动导出到下载目录（用户说"这个按钮没生效"）

用户描述的是：产物进了「抓流文件」之后，希望能自动落到本地下载目录；
同时**保留**私有存储那份和「保存到磁盘」按钮（本地误删了还能再导一次）。

做法：`autoExportCapture`（默认开）+ `downloadSubdir`。完整产物
（收尾 / 换集切分 / 手动快照）写完之后，离屏文档从 OPFS 文件建一个 **blob URL**，
交给 service worker 走 `chrome.downloads` 落到下载子目录。

**这里有一条约束必须写清楚**：blob URL 属于**创建它的上下文**，
所以离屏文档必须活到下载写完为止 —— 收尾流程因此改成
`closeOffscreenWhenIdle()`（有导出在跑就等着，最多 120 秒），
而不是原来那个"终态 1200ms 后无脑关"。关早了就是下载断在半路。

### 三、验证（以及这一轮被用例抓出来的三个真 bug）

**单测**：`readFragmentMediaTime` 对真实夹具（视频 timescale 12800：0/2/10 秒；
音频 48000：1.94 秒；init 段与垃圾输入返回 null）；`autoSnapshotPlan` 的两种口径
（含"内容够了但挂钟没到"和"量不出内容时长时回落挂钟"）。

**真浏览器**（`--extras`）：间隔设 9 秒、口径设"内容"，飞快喂 12 秒内容：

```
· 口径=视频内容（间隔 9 秒）：挂钟只过了 3 秒，内容已有 10 秒 → 自动保存的那份 vh-mse-…-自动部分.mp4
  ✓ 「按视频内容时长自动保存」真的按内容算（挂钟远没到点也存了）      ← 按挂钟绝不可能触发
· 自动导出：%USERPROFILE%\Downloads\VideoHunterAutoTest\vh-mse-…-020301.mp4（958 KB）
  下载到本地的这份 ffprobe：h264｜12.00 秒
  ✓ 自动导出：本地产物能播、私有存储那份还在、索引记了"已导出"
```

用例抓出来的三个真 bug（都是"看着没问题、跑起来才发现"）：

| # | 现象 | 根因 |
| --- | --- | --- |
| 1 | 内容时长一直是 `null`，自动保存永不触发 | 分组的键用的是**整条 mime 字符串**，而播放器重建 SourceBuffer 时 init 与分片带的 mime 不一样（`video/mp4; codecs="…"` vs `video/mp4`）→ init 的 timescale 和分片的 tfdt 各进一组。改成按**大类**（video/audio）分组 |
| 2 | 文件落到了下载目录，索引里却没有"已导出" | `mediaIndex.remember()` 只认 name/kind/seconds/size，多传的 `exportedAt` 被**静默丢掉**。补一个 `patchProduct()` 走 `patch()` |
| 3 | 收尾产物**不会**自动导出（切段和快照会） | `runAutoExport` 只接在切段/快照两条路上，**最常走的收尾那条忘了接** |

另外还有两条是**用例自己的问题**（改的是用例，不是代码）：
`run is not defined`（收摊代码引用了 try 作用域里的变量，声明要提到外面）；
9d 那条「清理已导出的 1 个」断言被新功能搅乱（自动导出会给别的用例也留下"已导出"，
复用的 profile 里还有历史遗留）—— 现在测试环境**默认关掉自动导出**，
那条断言也从写死 1 改成"按钮出现、数字与存储行对得上"。
**一个会撒谎的断言比没有断言更糟。**

### 四、播放列表「下一集自动刷新并从头抓」：**用户确认不需要，已关闭这条需求**

用户提过这条（还希望设置里给播放列表一套单独的"从头 / 从记忆位置"选项），
但他随后自己给了结论：「其实第二段自动录制可以不加的，我到了第二段就把第一段导出，
然后在第二段的时候，重新开始抓流就好了」。

而顺着这句话去核对代码，发现**两件事**：

1. **他的流程其实已经是自动的了**：换集时第一段已经收尾成完整文件，
   现在又多了「产物自动导出到下载目录」——所以"到了第二段把第一段导出"这一步不用他做；
   抓流本身也**没有停**，缓冲已清空、正在抓第二段。也就是说他**不需要再点一次「抓流」**。
2. **但"再点一次"会出事** —— 这正是他描述的动作，所以去验了：

   ```
   换集之后再点一次「抓流」：ok=false｜alreadyCapturing=true
     「抓流还在进行中，不用再点一次：已经存好 1 段（都在管理页的「抓流文件」里，
       可以随时「保存到磁盘」），正在等下一段的数据进来。」
   ✓ 再点一次「抓流」：只说"不用再点"，正在进行的这一段没被弄没
   ```

   修之前这里有两个问题，**第二个是数据丢失级的**：
   - `mseStart` 只回一句"已经在抓流中"，用户不知道"其实不用点"、也不知道已经存了几段；
   - service worker 在把失败回执往回传时，**顺手 closeOffscreen()** —— 而那个离屏文档
     里正装着他正在抓的第二段。也就是说：**用户在换集时按自己的习惯点了一下「抓流」，
     正在抓的那一段会连同缓冲一起被销毁**，界面上只有一句"已经在抓流中"。
     现在这条路径**绝不关离屏文档**，并且回执带上 `alreadyCapturing`，
     面板把它当**信息**（不标红）显示。

   用例第一次还写错了位置（放在 `mse-stop` 之后 —— 那时会话已结束，点下去当然会正常开新的），
   第二次判据也写错了（拿"缓冲字节 > 0"当判据，而刚切完缓冲本来就是 0）。
   现在判据是"这次会话还记得切过 1 段"（新会话的 `parts` 会是 0）——
   **两处都是用例的问题，不是代码的问题**，记在这里免得下次重犯。

所以这条需求的最终状态是：**不做**（用户确认），但顺手把它暴露出来的
"再点一次会弄没正在抓的那段"修掉了。

### 这一轮的版本与打包

- 版本升到 **0.2.0**（`manifest.json` 与 `package.json` 同步，打包时会校验一致性）；
- 用户这轮说**先别打包**，所以只把打包脚本按他的要求改好了（下次打包时生效）：
  **每个版本的文件夹里写一份 `版本说明.md`**（这个版本有哪些功能），
  并且**旧版本不删** —— `dist/` 里同时留好几个版本，靠文件夹名区分。
  "打包只替换同名那一份、不碰其它版本"这条**当轮就用假的老版本目录验过**。

## 第十二轮：设置页排版（用户提的界面问题）

用户发了一张面板截图，红框圈着「抓流：自动保存已录到的部分」——那行的**标签被挤成了竖排**，

### 先量，再选（两个方案都有数字）

在 420×600 的弹窗里量每一行（脚本临时写、只读、跑完删）：

| 行 | 标签宽×高 | 控件宽 | 行高 |
| --- | --- | --- | --- |
| 默认画质 | 48×17 | 170 | 28 |
| **抓流：自动保存已录到的部分** | **24×122** | **376** | **122** ← 用户报的这行 |
| 抓流：攒太大自动切一段 | 132×17 | 198 | 28 |

根因：`.field select { width: 170px }` 是按"**一行一个控件**"定的，而这一行塞了
**两个下拉 + 一个复选框**（间隔 + 口径 + 开关）＝ 376px，标签只剩 24px。

- **方案 A（标签独占一行）**：宽不变；这一行 122 → 51px，**设置面板总高 398 → 351px**
  —— 不占地方，**反而矮了 47px**；
- **方案 B（把面板拉大）**：一行放得下需要宽 ≈ 580px（420 → 580，+38%），

  代价是媒体列表每一行、说明卡、合并条的比例都跟着变，标签再写长又会挤。

**用户选了 A**（"标签独占一份，然后空间往下放一行"）。

### 改了什么

- `popup.css` 新增 `.field.stack`：标签一行、控件一行；控件用 `.controls` 包一层；
  下拉平分这一行、**上限 190px**（只有一个下拉的那行若自由拉伸会变成 360px 宽的"600 MB"下拉，很怪）；
- `popup.html`：把「自动保存已录到的部分」「攒太大自动切一段」两行改成 `.stack`
  （判据：**这一行的控件是一个组、两个以上**），顺手把原来的内联样式换成 `.controls`；
- **没有动下载目录那套**（用户明确说"文件目录那个不用管"）。

面板检查里加了一条断言：控件扎堆的那两行，**标签高度必须 ≤ 22px（一行读完）**、
下拉不能窄于 110px（否则长选项被截断）。改完量到：

```
· 设置行 s-autocut：两行式｜标签 392×17｜行高 51｜下拉 190
· 设置面板总高（展开时）：351px（弹窗上限 600）                    ← 原 398
✓ 说明卡完整落在弹窗里，不会被裁（没被这次改动带坏）
✗：0｜✓：46
```

### 顺带记下"下载目录"那套规则（讨论过、决定不改，但知识留着）

用户问"这里默认是保存到 C 盘的对吗"。查清楚了：

| 路径 | 落点由谁定 | 能选任意盘/目录吗 |
| --- | --- | --- |
| 解析器页下载（HLS/DASH/直播） | 系统「保存到哪儿」对话框 | ✅ 能 |
| 管理页「保存到磁盘」 | 同上 | ✅ 能（用户说"这个就非常好"） |
| 直链下载 / 抓流产物自动导出 | **Chrome 下载目录 + 子目录** | ❌ 只能相对路径 |

- 所以默认确实落在 C 盘 —— 因为 Windows 上 Chrome 的下载目录默认是
  `C:\Users\<你>\Downloads`；**换个盘不用改我们**，改 `chrome://settings/downloads`
  的「下载内容保存位置」，子目录跟着走；
- 技术上只能给相对路径：`chrome.downloads` 的 `filename` 必须是"相对下载目录"的路径；
- 实测一个**静默的坑**（写进文档，免得以后有人再试）：在「下载子目录」里填盘符
  **不报错，但也不会生效** —— `D:\视频` 会变成 `…\Downloads\D_\视频\`，
  `C:/Users/me/Downloads` 会变成 `…\Downloads\C_\Users\me\Downloads\`；
  `..\..\Windows` 会被中和成 `Windows/`（不会越界）。用户决定不改，所以先留着。

## 第十四轮：补"静默失败"（用户提的「检查一下哪里有问题就修改一下，保持现有功能不变」）

用户的原话是"保持现有功能不变"——所以这一轮**只修问题、不加功能**：抓流/录制/下载的

### 修的问题：自动切段那条路**没人接导出句柄**（A1）

自动切段是**离屏文档自己发起**的（体积到阈值是它每秒在算），没有"请求-响应"这条路可借，
所以它把导出句柄塞进状态推给 SW（`offscreen.js` 的 `post({ …, autoExport: r.autoExport })`）。

而 SW 的 `onOffscreenState` **从来没读过这个字段** —— 只有换集切段 / 停止收尾 / 手动快照
三条路各自调了 `runAutoExport`。后果不是报错，是"什么都没发生"：那段产物永远不落到下载目录，
界面上也看不出任何区别。**用户以为文件在下载目录里，实际只在扩展私有存储里。**

修法（同时也是把这类漏接变成结构上不可能）：

- 新增 `autoExportProduct(handle)` —— **唯一**的自动导出入口，四个发起方都走它；
- 新增 `patchRecording(patch)` —— 收尾那条路上会连着写好几次状态，而每次用的 `cur` 都是
  函数开头读的快照；导出要等下载器（耗时以秒计），中间心跳还在写状态，用旧快照拼下一个状态
  会把"导出结果"悄悄抹掉。所以改成"读最新状态再合并"。

### 修的问题：导出结果只写在控制台里（A2）

以前成功失败都只有 `console.info`。现在 `autoExportProduct` 把结果写进录制状态
（`exportNotice` + `exportOk`），**面板弹一条、管理页日志记一行**；失败那条还会说清
"产物没丢，去管理页点『保存到磁盘』可以再导一次"。

### 顺手修的两处

- **内容脚本的 1.5 秒去重窗口不再吃信号**（`content.js` 的 `reportBoundary`）：
  以前不管上报成没成功都占着窗口。而"第一条被后台拒了（这一段数据还不够收尾，`skipped`）"
  时，几百毫秒后那几条信号正是**唯一的补救机会**。现在上报失败（`ok === false`）或消息
  发不出去时把窗口放开 —— 后台那边本来就只在**切成功**之后才去重（`cutMseCapture`）。
- **两个数分开写**：状态卡上的「已存 N 个」只数"完整收尾"的产物、不含滚动快照，
  用户实测把它读成"什么都没存"。现在写成「**完整 N 段 · 快照 M 份**」+ 悬停解释；
  管理页每行标注它属于哪一类（新增纯函数 `captureFileKind()`：
  `complete` / `partial` / `autoSnapshot`，只看文件名、不依赖内存记录）。

## 第十五轮：自动切段之后那一段**没有声音**（用户报的）

用户的原话：「当视频达到 600 兆之后，它会做一个切片、自动保存、然后开始下一段录制 ——
这个下一段录制它是没有声音的。」

### 为什么现有用例抓不到它

自动切段那条 E2E **只喂了视频轨**（`init-stream0` + `chunk-stream0`），而且只检查了
"切出来的那一段还能播"（ffprobe 看时长/编码），**从没检查过它有没有音轨**。
所以怎么跑都是绿的 —— 这正是"用户的站点上必现、测试里永远看不到"的典型。

### 先复现，再修

把用例改成"按真实站点的形态喂"，一次就复现了。关键是**两个条件同时成立**：

1. **mime 是空的，只有 sbId** —— `mse-hook` 的注释里写着这是实测存在的：
   那条 SourceBuffer 的 `addSourceBuffer` 没经过我们的补丁，于是每次 append 都报空 mime；
2. **第二段只送分片、不送 init** —— 切段清空缓冲之后，播放器不会重发 moov。

```
· 切段之后那一段（…-192909-2.mp4）：h264 640x360｜**没有音频轨**｜2.00 秒
  回执提示：初始化段用的是本次抓流里先前收到的那一份（video、video）；
           抓到了 2 条视频轨，只用了最先出现的那一条
```

提示里那个「（video、**video**）」就是铁证：**两个组都借到了视频的初始化段**。

### 根因

"借哪一份初始化段"是**按 mime 猜**的：`seenInit.get(a.contentType || 'video')`。
mime 一空，`contentType` 就推不出来，于是回退成"当视频用" —— 音频那一组借到了视频的
init；合并时按 trackId 挑样本，借来的 init 里没有那个 id，**整条音轨被丢掉**。

切段前每组自带 init，所以一切正常；**切段之后才暴露**（那时只剩"借"这条路）。

### 修法：两条线索，缺一不可

1. **这条流先前是什么** —— 按分组键（mime 或 `sb:<编号>`，和 `groupBuffers` 里的键
   **一字不差**）记住它上一次被分析出来的大类。分组键在整个会话里稳定（同一个
   SourceBuffer 的编号不会变），这是最准的线索；
2. **分片自己的 `tfhd.track_ID`** 能在哪份 init 里找到。

⚠️ 第 2 条**单独用不够**：单测第一版就是在这里翻车的 —— **实测（就是仓库里那两份夹具）
ffmpeg 产的两条独立轨都写 track 1**，`assert.notEqual(v[0].id, a[0].id)` 当场失败。
撞号时只能再按大类定。这条"会撞号"的事实现在用断言钉在
`test/mse-assemble.test.mjs` 里，免得以后有人以为 trackId 是万能钥匙。

顺带把"借初始化段出的岔子"从**静默**改成提示：借不到、或者借来的 init 里没有这个
trackId 时，会写进产物提示（"哪一条轨没进产物、多少字节"）—— 以前用户只看到"这一段没声音"。

### 验证

```
单测 216/216（新增 9 条）
浏览器端到端 --e2e --extras：0 个失败
  · 切段之后那一段（…-194127-2.mp4）：h264 640x360｜aac 48000Hz｜2.08 秒
  ✓ 切段之后那一段有画面也有声音（初始化段复用成功）
```

### 这一轮自己踩的三个坑（都记在这儿）

1. **阈值压得太低，把要验的东西自己切走了**：第一版用 0.05 MB，第二段刚喂进去就被
   第二次切段吃掉，收尾时报"没有捕获到任何数据" —— 看着像 bug，其实是用例把现场毁了。
   改成 0.3 MB（第一段超阈值、第二段不超）。
2. **反引号又把模板字符串截断了**：用例脚本是**发给页面执行**的模板字符串，注释里写了
   `` `sb:<编号>` `` → `node --check` 直接报 `missing ) after argument list`。
   **上一轮刚记过这个坑，这轮又踩了一次** —— 模板字符串内部的注释里不要用反引号。
3. **启动 Chrome 时漏了 `--disable-*-throttling`**：录制那两条用例立刻报"产出 4 帧 /
   编码 3 帧""停摆识别成 4999 毫秒"，看着像代码回归，其实是 headless 把后台标签页的
   定时器节流了（"3 秒只出 3 帧"）。仓库文档里早就写着"这三个参数不是可选的"。

## 第十六轮：切段之后"依旧没有声音"—— 音频是 WebM/Opus 时走的是**另一条路**

用户第二次报的：「第二段视频依旧没有声音」。上一轮（第十五轮）修的是 **fMP4** 那条路上
"借初始化段借错了"，那个修复是必要的，但**不够** —— 他那个站（YouTube 4K）的音频是
**WebM/Opus**，走的是"拆包 + Opus→AAC 转码"那条路。

### 这次是**先看用户的真实产物**，一眼定位

用户 21:14 那次留下的两段（只读检查，没动他的文件）：

```
…-211419.mp4（604 MB，513 秒）   轨 vide 15218 个样本｜轨 soun 24844 个样本   ← 第一段：有声音
…-211455-2.mp4（350 MB，289 秒） 轨 vide  8680 个样本｜**没有 soun 轨**        ← 第二段：没声音
```

和上一轮那两段（19:11 的 607 MB / 92 MB）是同一个形状：**第一段有、第二段没有**。
而"第二段只有 vide 轨"说明不是"音轨静音"，是**整条音轨没了**。

### 根因：WebM 这条路**没有"借头部"的地方**

- 抓流的两条音频路：fMP4（moov + moof 分片）和 **WebM（Tracks 头部 + Cluster）**；
- 自动切段会把缓冲清空，而**播放器不会重发头部**：
  - fMP4 那条有 `seenInit`（借 moov），上一轮补上了"按 trackId / 按这条流先前的大类认"；
  - **WebM 那条压根没有借的地方** —— `webmGroups` 只收"init + fragments 都在"的组，
    只剩裸 Cluster 的组落进 `a.missingInit && a.raw` 分支后，被当成 fMP4 去借 moov，
    借到的是一份**没有 moov 的 WebM 头部**（`listInitTracks` 读出空数组）→ 变成一条
    没有轨道的组 → **静默消失**。
- 结果：第一段自带头部所以声音正常，**只有第二段丢音频** —— 和用户看到的完全一致。

### 修法

1. **WebM 头部单独记一份**（`seenWebmHeader`，键和 `groupBuffers` 的分组键一字不差：
   mime 或 `sb:<编号>`）；
2. 遇到"只有裸 Cluster"的那一组：按这个键借回头部，借到就交回 WebM 那条路（拆包 + 转码）；
   键对不上（播放器重建过 SourceBuffer）时，退一步按"这条流先前的大类"找；
3. **fMP4 的候选项里不再混入 WebM 头部**（它没有 moov，混进去就会造出一条没有轨道的组）；
4. 借不到时**不再静默**：写进产物提示（哪一组、多少字节没进产物）。

### 验证：先跑红，再跑绿

用例按真实形态喂（视频 fMP4、音频用夹具里现成的 `webm-vp9/audio-init.webm` +
`audio-clusters.webm`；第一段头部 + Cluster 都送 → 触发切段，第二段**只送裸 Cluster**）。

**先把新分支临时禁用，确认用例不是空转**：

```

✗ WebM/Opus 音频那一型：切段之后那一段**没有声音** —— 头部丢了、又没有借回来的地方
  收尾回执里的提示：…初始化段用的是本次抓流里先前收到的那一份（video、video）；
                   抓到了 2 条视频轨，只用了最先出现的那一条
```

注意那两处和用户实报完全对得上：**「（video、video）」**和**「抓到了 2 条视频轨」**。

**打开修复之后**：

```
· 切段之后那一段（WebM/Opus 音频）：h264 640x360｜aac 48000Hz｜6.02 秒
✓ WebM/Opus 音频那一型：切段之后那一段照样有声音
```

单测 216/216（这一轮没加单测：这条判据跨"分组 → 借头部 → 拆包 → 转码"四步，
只能在离屏文档里跑，所以钉的是浏览器用例）。

### 教训（写给自己）

   但那只是**一条**路；用户报的站点走的是另一条。**同一个症状可能有两条互不相干的成因**，
   "我复现了一个"不等于"我复现了他的"。

## 第十七轮：切段之后"画面没了" —— 借头部不能依赖"分组键"

### 先把"是不是动了核心"用他的话回答清楚

- **不切段的正常抓流一路没动**：新加的分支只在"这一组**没有头部**"时才走到，而正常抓流
  （点「抓流」本来就会刷新页面）头部一定在。这一点在完整的浏览器回归里也验着（8c 那条
  WebM/Opus 抓流用例依然是 `h264 + aac` ✓）。
- **同一个视频两次容器不同，是 YouTube 自己换的编码**：

```
19:11  607 MB   video av1 2560x1440 + audio aac    ← 那次给的是 AV1(MP4)
22:32  49.9 MB  video vp9 3840x2160 + audio opus   ← 这次给的是 VP9(WebM) → 产物 .webm
```

  画面是 WebM 时出 `.webm` 是**设计**（零转码，不重编码），不是 bug。
- **22:33 那份的 540 秒不是坏数据**：25313 帧 aac × 1024 / 48000 = 540 秒，帧数自洽；
  用户当时开着倍速（73 秒挂钟 ≈ 540 秒内容）。它显得小（12.5 MB）是因为**只有声音**。

### 真正的根因：借头部时"身份"选错了依据

```
22:33  …-223355-2.mp4   只有 aac 声音，**画面没了**
```

借 WebM 头部时是按**分组键**（mime 或 `sb:<编号>`）去查的。而**播放器换清晰度会重建
SourceBuffer —— 编号就变了**：画面那条查不到（键变了）、音频那条还在，于是产物只剩声音。
（试过按 WebM 的轨道号认：实测两条独立轨**都写 track 1**，也分不开。）

### 修法：排除法

这次组装里"**哪个大类还没有着落**"，那一组就是它 —— 键变了、但两条轨不同时变时就能分开。
fMP4 那条路共用同一个判据（`resolveGroupType`）。仍然分不开时**不猜**，如实写进产物提示。

### 验证：先红后绿（两次跑）

用例（`8b-6`）：两条轨都是 WebM，第一段头部 + Cluster 都送 → 触发切段；第二段只送 Cluster，
而且**画面那条换了一个 sbId**（模拟换清晰度重建缓冲区）。

```
修复前：
  · 切段之后那一段（两条轨都是 WebM）：**没有视频轨**｜aac 48000Hz｜6.02 秒
  ✗ 缺轨（画面没了）
    收尾回执：…初始化段用的是…（audio）；有一组只有 WebM 的裸 Cluster、没有头部（Tracks），
             本次会话里也没有可借的 —— 这一组 167116 字节没有进产物
    （167116 字节 = 画面那条 Cluster，和用户那份"只剩声音"的产物一模一样）

修复后：
  ✓ WebM 两条轨那一型：切段之后画面和声音都在
  ✓ 浏览器验证通过：扩展能加载，所有页面无控制台报错（exit 0）
```

单测 216/216；`--e2e --extras` 全套 0 失败。

### 这一轮的教训

1. **"是不是动了核心"要用他的文件回答，不是用我的自信回答**：把他的旧产物和新产物都
   `ffprobe` 一遍，容器/编码/时长/帧数摆出来，"同一个视频两次为什么不一样"立刻清楚 ——
   这一次答案是"YouTube 换了编码"，上一次答案是"另一条容器路径"。
2. **"没得借"要写出声**：上一轮加的 `reuseNotes`（"这一组 N 字节没有进产物"）这次直接
   指认了被丢掉的是哪一组、多少字节，省掉了整轮瞎猜。
3. **同一处逻辑会因为"身份怎么定义"栽两次**：fMP4 那次栽在"按 mime 猜大类"，WebM 这次栽在
   "按分组键查身份"——**键/编号都是会变的东西，能不变的是数据自己的属性**（trackId、
   或者"这次还缺哪个大类"）。

## 第十八轮：同页换集把两集焊在一起 —— 用户要「最起码给我一个完整的第一集」

### 用户的原话

> 「第一段尾巴和第二段开头，它在混在一起的……只要我不停，它就一直是一个视频，这不扯淡吗？
>   我感觉一集一集还是要一集。」
>
> 「你要是做不好这个分片功能，那你就把第一段视频让我完整保存起，最起码让我有一个完整的
>   第一段视频，对吧？然后第二段视频我再重新开启那个抓流程就好了呀。」

### 先看清形状：这不是"丢数据"，是"多数据"

同页平滑换集（地址栏不变、同一个 `SourceBuffer` 里接着 append）时，四个边界信号一个都不来，
第二集的样本就接着进缓冲。把两条时间轴摆出来：

```
第一集样本    0 ──────────────────────────── 1380 秒
第二集样本    0 ──────────────────────────── 1380 ─── 1980 秒
              └────── 判重：这一段和第二集重叠 → 丢掉 ──────┘
                                                 └── 超出末尾的 600 秒 → 接在第一集后面
```

两种形状的后果完全不同，而**只有一种看得见**：

| 第二集比第一集 | 合并前判重的结果 | 用户看到的 |
| --- | --- | --- |
| **短** | 全部重叠、全丢 | 产物恰好是"干净的第一集" —— **看着挺对**，所以这个坑藏了好几轮 |
| **长** | 重叠的丢掉、**超出的接上** | "第一段尾巴和第二段开头混在一起"，而且**不报任何错** |

第二条路径原来在 `test/merge.test.mjs` 里就有一条用例（当时的标题是"当前真实行为"），
也就是说**这个行为是被记录过的**，只是没人把它当成 bug —— 直到用户拿产物说话。

### 做法：放在合并那一步，做成纯函数

上一轮试过"录制中途按心跳判定并切割"（做了大半、没并进来）：要在离屏文档里边收边判，
还要处理"这一刻缓冲里已经混了两集"的收尾，现场情形太多。

这一轮换成 **合并时的一道纯函数** `truncateAtTimelineRestart(samples, timescale)`
（`src/parser/mp4-merge.js`）：

- 按**到达顺序**走（"换集" = 后来的片从接近 0 重新开始）：先前已经录到 **≥ 60 秒**，
  而这一片的第一个时间戳 **≤ 3 秒** → 判为换集，**从这一片往后的样本全部不要**；
- 只在**抓流**这条路上开（`mergeFmp4(..., { cutOnRestart: true })`，offscreen 一处）——
  下载/合并那条路的"时间戳重来"可能是别的东西，不动它；
- 切掉多少**写进产物提示**，不静默：

```
视频轨的时间轴又从头开始了（录到 90 秒之后，又回到第 0.0 秒）—— 那是新的一段，
它的 120 个样本没有进这一份产物：这一段（上一集）保持完整。要抓新的一段，请重新点一次「抓流」。
```

**为什么放这一步是对的**：到合并时 fMP4 / WebM / TS 三种容器**都已经统一成样本**了，
判据只看样本自己的时间戳 —— 不认容器、不读包、不做 UI 切割。这让它可以纯单测，
而这正是上一轮那个方案做不到的。

### 验证

```
✓ 静态体检（37 个 JS 文件）
✓ 单测 218/218
  · 换集（时间轴重启）：只保留重启之前那一段，第一集保持完整
  · 反面一条把四种"不许切"一起钉住：接着播（换清晰度）/ 往回拖几秒 / 刚开始就拖回开头 / 空输入
✓ 浏览器端到端 --e2e --extras：0 失败
  （而且是从**打包好的** dist/video-hunter-0.2.2 加载跑的）
```

那 60 秒 / 3 秒两个阈值是**被反面用例逼出来的**：一开始只想"往回退了就算重启"，
反面用例会把"往回拖 20 秒重看"和"刚开抓就拖回开头"都判成换集 —— 两个数就是在这两条上试稳的。

### 代价（写进注释、README、CHANGELOG、界面提示，四处一致）

**中途把进度条拖回最开头**在数据上和换集长得一模一样，兜底那一刀会把拖回之后的内容切掉
（保住的是拖回之前那一段）。这是有意的取舍：**宁可少收一段，也不要把两集焊在一个文件里** ——
用户原话就是"第二段我重新开启那个抓流程就好了"，这一版给的就是这个。

### 还没验的一条（别当成已验）

**真实站点上"换集那一刻"的端到端用例还没写。** 判据与切法有单测（含四种反面）、
切段后有声/有画面的那几条回归全绿，但"真实站点换集时到底哪些样本会到、时间戳长什么样"
只有现场才知道。补上它之前，README / CHANGELOG / 这一节都写着"真实站点现场还没验过"。

### 这一轮的教训

1. **用户说"你动了核心东西"时，先看他的文件，不要先自证清白**：三个产物 `ffprobe` 摆在一起，
   "同一个视频两次容器不同"是 YouTube 自己换的编码（AV1/MP4 ↔ VP9/WebM），真正坏的只有
   "切段之后那一段"。
2. **"看着挺对"是最危险的形态**：判重把第二集的重叠部分吃掉之后，产物恰好像"干净的第一集"，
   于是同一个坑能连着躲过好几轮验证 —— 要按**"如果它更长会怎样"**去想。
3. **能放到"纯函数"那一步解决的，不要放在"边跑边判"那一步**：同一个需求，
   合并时切 = 83 行纯函数 + 2 条单测；录制中途切 = 一整套状态机，还没做完。

## 第十九轮：WebM 抓流"画面只有开头几十秒" —— 播放器在原地重新初始化，被我们整段吞掉

### 先看文件，不看描述

用户说"不支持 YouTube 这种视频格式"。先把他的产物摊开（定档 4K、**没换过清晰度**）：

| 文件 | 容器声明 | 视频实际 | 音频实际 |
| --- | --- | --- | --- |
| `…-130537.webm` | 930 秒 | **0 → 23.2 秒**（696 包 / 8 关键帧 / 18.5 MB） | 0 → 930 秒（46500 包 / 13.4 MB） |
| `…-131353.webm` | 750 秒 | **0 → 23.2 秒**（696 包 / 8 关键帧 / 18.5 MB） | 0 → 750 秒（37500 包 / 10.8 MB） |

三条硬证据，每一条都能单独定案：

1. **音频一包不缺**（每 20 ms 一包、整段连续）→ 抓流一直活着、一直在收数据，不是"卡住了"；
2. **两个产物的视频流 md5 完全相同**（`0fb1b73b…`），音频却各不相同 → 两次写进去的是同一段画面；
3. 界面 banner 写着缓冲**已经攒到 302 MB**，写出来的文件只有 **32 MB** → 抓到的数据约 90% 没进产物。

播放器里的表现是"开头能放、往后一拖就是空白占位图"：顺序解码不需要索引，所以开头看着正常。

### 根因：不是"读不动"，是**照着一个过期的长度跳过去了**

MSE 允许播放器在**同一条** SourceBuffer 里重新初始化自己（`changeType()`、拖进度条重新预取、
码率自适应都会再 append 一份 init）。抓到的字节流于是变成 `init + clusters + init + clusters`。

第二份 init 里的 `Segment` 元素声明的是**它原来那个文件的长度**（几百 KB 到几 MB）。
`walk()` 按这个长度往下跳 —— 后面真实抓到的 Cluster 就被**整段吞掉**了：

```
单个坏元素 → walk() 的 readHeader 失败 → return          ← 这是 A2，会"读不动"
这次是     → readHeader 成功、长度也"合法" → 跳过头了      ← 静默，且看起来一切正常
```

所以现象是"产物少了 90% 内容，而 `skippedBlocks=0`、`warnings=[]`、`analyzeGroup.error=null`"。
判据是规范级的、不用猜：**Segment 不允许嵌 Segment**，EBML Header 也不允许出现在 Segment 里 ——
在这一层看到它们，只有一个解释：这里又来了一份 init。

**两个前置问题，答案是靠数据定的，不是猜的：**

1. **为什么第二份 init 没被指纹去重挡掉？** 去重只挡**逐字节相同**的重复 append（对的行为）。
   换码率/换编码时新的初始化段本来就变了（分辨率、编码配置都变），于是躲过去重、走到拆包器。
2. **为什么不是"播放器重建了 SourceBuffer"那条路（多分组、只取第一条）？** 重建会触发我们的
   边界信号 → 自动保存会切一刀 → 产物被切成两段。而用户这两份产物各自含着 750 / 930 秒的
   **连续**音频，说明中途根本没切过 —— 所以是**在原地重新初始化同一条 SourceBuffer**。

### 修法（只动 `src/parser/webm-demux.js`）

1. cluster 层认出"又一份 init" → **不认它声明的长度**，改看它自己的子元素
   （Tracks / SeekHead / Info…）逐个跳过 → 在**下一个 Cluster** 处接着读；
2. 同源的第二种静默丢失一起处理：**Segment 声明的长度比实际数据短**（借来的头部、
   重发 init 之后继续 append）—— 声明范围走完之后，只要后面确实还是 Cluster 就接着读；
3. 读不动了不再静默收场：把"还剩多少字节没读"写进产物提示；
4. **只多不少**：改动只做"多认出来一些数据"，不跳过任何 Cluster，新结果一定是旧结果的超集。

### 复现（先红后绿）

**单元层**（`test/repro/known-defects.test.mjs` 的 P1）：`init + clusters + init + clusters`，

```
修复前：150 帧（第二份之后的 167 KB 全没）｜skippedBlocks=0｜warnings=[]｜analyzeGroup.error=null
修复后：300 帧 ｜并报出「播放器中途又发了一份初始化段（1 处）：已经跳过它、接着读后面的内容」
```

**浏览器层**（`--extras` 8f-2，新增）：测试页喂到一半时**再 append 一次 init** ——
按 EBML 长度字段从某个 **Cluster 边界**切开（不猜字节：猜错就切在 Cluster 内部，验的就不是
这条路径了），第二份 init 用 EBML `Void` 填充过（所以它"变了"，和现场一样躲得过指纹去重），
然后断言产物里的画面**覆盖整条时间轴**：

```
修复前：产物 …-140708.webm｜276280 字节｜vp9 320x180｜opus｜真解出 75 帧（只有前半段）
        ✗ 画面没有覆盖整条时间轴：重新 init 之后的内容被静默丢掉了
修复后：真解出 150 帧（6 个 Cluster 全在）✓
```

> ⚠️ **这条用例第一版是我写错的，记在这儿**：当时让测试页重发**一模一样**的 init，
> 结果它被指纹去重挡掉了（那是对的行为），拆包器压根没看到重发 init —— 用例"红了"，
> 但红的原因是我的断言写错（把 150 帧当成了错误），**根本没有复现到 bug**。
> 是拿 offscreen 那一串函数（`groupBuffers → analyzeGroup → demuxWebm → mergeWebm`）
> 在 Node 里离线复刻了一遍，看到"喂进去 167964 字节、分组只剩 167540"才发现少掉的
> 正是那份重复 init。
> 教训：**用例红了不等于复现到了那个 bug** —— 先确认它红的理由和你以为的是同一个理由，
> 否则你会拿一条谎报军情的用例去"证明"修复有效。

**MP4 / fMP4 那条路实测不受影响**（这条很重要，用户最怕"修一个坏一个"）：
拿 `dash-split` 造"六片分片、中途重发 init、后面时间戳继续"，正常喂法与重发 init
**产物都是 300 包 / 12.00 秒、字节完全相同** —— 它本来就能扛，所以这次一行没碰。

### 验证

**"红→绿"是拿同一个脚本跑出来的**（把 `webm-demux.js` 临时 stash 起来跑一轮、恢复再跑一轮）：

| 层次 | 修复前 | 修复后 |
| --- | --- | --- |
| 单元（P1 / P1-b / A2） | 三条**全红**（9/9 红） | 三条**变绿**（其余 6 条是另外几个已知缺陷，仍红） |
| 浏览器 8f-2 | 收到 `video(init 424/片段 167543)` —— **数据收全了**，产物却只解出 **75 帧**、零警告 ✗ | 同样输入 **150 帧** ✓ |

```
✓ 静态体检（37 个 JS 文件）
✓ 单测 218/218（没有回归）
✓ 复现层：P1、P1-b、A2 变绿
✓ 浏览器 --e2e --extras 全套，从打包好的 dist/video-hunter-0.2.3 加载：0 个失败
```

那行 `video(init 424/片段 167543)` 是这次最有价值的一行诊断：**抓流收全了 167543 字节**，
问题百分之百在拆包那一侧 —— 以前这个区分（"没收全"还是"收了没用"）只能靠猜。

### 这一轮的教训

1. **"静默丢数据"的根因不一定是解析失败**：这次恰恰相反 —— 元素头读得好好的、
   长度也"合法"，只是那个长度是**上一次生命周期的**。以后遇到"内容少了一截却毫无提示"，
   除了"读不动"，还要怀疑"照着一个不该信的长度跳过去了"。
2. **规格里"不允许出现"的结构，是最好的判据**：Segment 里出现 Segment/EBML Header
   在规范上是非法的 —— 用它当"重新初始化"的探针，比任何启发式都稳。
3. **改一处之前先量"另一条路"**：先证明 fMP4 那条路本来就扛得住（300 包 / 12.00 秒），
   才敢说"这次只动 WebM"。用户最怕的就是修一个坏一个，而"我量过了"比"我觉得不会"值钱。

### 还没验的一条

"真实站点上播放器**什么时候**会重发 init"（换码率？拖进度？重新预取？）没有单独埋点统计过 ——
现在的结论是"产物形状 + 浏览器用例"反推出来的。所以这一版把**重发次数写进了产物提示**，
下次在真实站点上抓一次就能把现场数据收回来（提示里会写"N 处"）。

## 第二十轮：字节流错位之后剩下的 175 MB 被整段丢掉 + 管理页时长虚高

第十九轮修好之后（用户确认点过 ⟳），他抓的新产物提示卡上出现的是第十九轮新加的那句告警：

```
读到第 3 个 Cluster 之后读不动了（还剩 175780230 字节没读）：
这一段后面的内容没有进产物，这一份可能少了一截
```

产物实测：音频 0 → 600 秒，画面只有 0 → 17.37 秒。也就是说**换了个原因，症状一样**。

### 根因：不是"读不动"，更多时候是"读歪了"

抓到的字节是 `appendBuffer` 首尾相接；真实站点上这一串会因为**某一段丢了或重叠了**而错位。

调试时发现一个反直觉的事实：把损坏样本喂进去，`resync` 计数是 0、`unparsed` 是 0、
**连警告都没有** —— 因为错位点读到的往往不是"读不动"，而是一个**看起来合法**的元素
（id 不属于 Segment 的合法子元素、声明一个超大长度），它把后面**一口吞掉**，
循环"正常"结束。所以只补"失败时重新对齐"是不够的。

### 修法（仍然只动 `src/parser/webm-demux.js`）

1. **错位就往前找下一个真 Cluster**（`1F 43 B6 75`）：校验元素头自洽 +
   Cluster 第一个子元素必须是 `Timestamp`（规范要求，各家 muxer 都写在最前面）；
2. **按规范判"这个 id 该不该出现在这里"**：Segment 的子元素只有
   SeekHead/Info/Tracks/Cluster/Cues/Chapters/Tags/Attachments/Void/EBML/Segment，
   出现别的就是错位 —— 比"长度太大就怀疑"之类的启发式稳，也不会误伤正常文件；
3. **把"静默结束"的口子全堵上**：长度未知的元素、声明范围走完还剩字节、
   循环自然结束却还有没读的字节 —— 一律上报还剩多少。

### 顺带修的：管理页时长虚高（A7）

用户报"录了 7 分钟只有 6.8 MB" —— 文件没错，是**显示错了**：管理页写 18:31，
而容器自己声明 29.98 秒。`webmDurationSeconds` 忘了减起点偏移（`mergeWebm` 减了、它没减），
从中间开始抓流时就把"源流时间轴长度"当成了产物时长。现在两边同一套口径。

### 验证

| 用例 | 修复前 | 修复后 |
| --- | --- | --- |
| P2（损坏输入：某个 Cluster 内删 40 字节） | 25 帧 + **零警告** | **100 帧** + 「有 1 处字节流对不齐（共跳过 N 字节）」 |
| A7（起点偏移 3600 秒） | 报 3606 秒 | 报 6.000 秒 |

```
✓ 静态体检；单测 218/218（没有回归）
✓ 复现层：A2 / A7 / P1 / P1-b / P2 五条变绿（其余 5 条是另外几个已知缺陷）
✓ 浏览器 --e2e --extras 全套，从打包好的 dist/video-hunter-0.2.3 加载：0 个失败
```

### 这一轮的教训

1. **"同一个症状"可以有好几个互不相干的原因**：第十九轮修的是"照过期长度跳过头"，
   这一轮是"字节流本身错位"。修完第一个不能就宣布这个症状消失了 —— 用户的新产物
   直接打脸，而**新加的那句告警**正是把第二个原因揪出来的东西。
   这也是"静默失败一律要报出来"的价值：它不只是给用户看，也是下一轮排查的入口。
2. **调 bug 时先看"为什么它没报错"**：这次卡住的原因是我以为"错位必然导致解析失败"，
   实际上错位更容易导致"解析成功但读歪了"。**把'没报错'本身当成一个要解释的现象**，
   才找到了 id 判据。

## 独立代码审查

主链路跑通之后，另外派了一个独立 agent 做代码审查（逐行读完全部 20 个文件，只报有具体证据的缺陷）。它报了 13 条，全部核实为真，均已修复。其中三条值得单独说：

**第一条是致命的**：`page-bridge.js` 用了 `MSG.PAGE_SCAN`，而 `constants.js` 里**根本没有这个键**。`import { MSG }` 完全合法（MSG 确实被导出了），所以导入导出检查过得去；但 `MSG.PAGE_SCAN` 是 `undefined`，于是 `chrome.tabs.sendMessage(tabId, {type: undefined})` 一路飘到内容脚本，静默落在 `default` 分支上，没人回应。结果是「页面视频列表」「页面内视频按钮」「GET_TAB_INFO」三条链路**全部静默失效**——没有报错，只是点了没反应。

这类错误（常量表里的键缺失）在这一轮之后有了专门的静态检查：

```
· 常量表属性访问
  ✓ 校验了 160 处常量表属性访问，全部存在
```

**这条检查是自测过的**：临时把 `PAGE_SCAN` 从 constants 里删掉，确认它确实报 `✗ src/background/page-bridge.js 用了 MSG 里不存在的键：PAGE_SCAN`，然后还原。一个永远通过的检查比没有检查更糟。

**第二条**：编码失败后，离屏文档的每秒心跳会**无条件**上报「正在录制」，把刚上报的 ERROR 在一秒内覆盖回去，同时错误字段也被清空。表现是界面一直显示「录制中」，用户等一个永远不会来的收尾；而且失败路径从不释放采集流和 AudioContext。

**第三条**：直播的轮询循环把「上层处理失败」（写盘出错、磁盘满）和「拉取失败」放在同一个 `try` 里，于是写盘失败被当成网络抖动吞掉，继续下一轮——录制看起来一直在跑，实际一个字节都写不进去，也永远不会停。

> ⚠️ **这一条当年只修了一半，我（作者）在文档里写成"全部修复"是错的。**
> 当时改的是 `live.js`（轮询库自己把「拉取」和「交给上层处理」分成两段，并在注释里
> 写明了这个教训），可**调用方** `parser.js` 的 `onPlaylist` 回调里，
> `sink.write(data)` 仍然和分片下载共用一个 `try` —— 也就是说库学会了，调用方又把
> 它们合回去了（外加 fMP4 直播那条路根本不经过 `liveFragments` 收尾组装，
> 却一路上写着"收尾时组装成带索引的 MP4"）。
>
> 是用户让我"自己检查一下"那一轮的独立审查把它翻出来的，现在**真的修了**：
> 下载（可跳过）与写入（致命）分成两段；写入失败往外抛，让这次录制判失败并如实报错。
> 教训：**"库里写对了"不等于"调用方用对了"** —— 改完要看调用点，
> 而且文档里的"已修复"要指得出具体行号。

其余十条分布在：消息类型同时承担「拉」和「推」导致两个页面互刷状态、`store.clear()` 不参与串行写链导致 SW 重启后已清空的条目复活、解析器页永远拿不到 `sourceTabId` 使第一级抓取策略成为死代码、`#EXT-X-MAP` 的 BYTERANGE 被忽略导致整个源文件被当成初始化段、`classify()` 收了 `Content-Disposition` 却从不用它导致无扩展名的下载响应被丢弃，等等。

审查报告同时明确了它**没有发现问题**的类别（MV3 权限覆盖、`onMessage` 死锁、未捕获的 promise 拒绝、资源泄漏、mux.js / mp4-muxer 的用法），以及它**不确定**的三点。其中一点我已经用上面那条真实 CDN 测试间接验证了（Referer 注入对扩展页面 fetch 是否生效），另一点（`chrome.tabs.reload` 是否打断 tabCapture）仍未验证，已列进上面的未验证清单。

## 怎么复现

```bash
cd video-hunter
npm install
npm run build          # 图标 + vendor + 静态体检
npm run fixtures       # 需要本机有 ffmpeg
npm test               # 第 2、3 层

# 第 4 层
npm run serve &        # 后台起 fixture 服务（127.0.0.1:8791）
# 另开一个带调试端口的 Chrome（独立 profile，不影响你正在用的那个）
chrome --headless=new --disable-gpu --no-sandbox \
       --autoplay-policy=no-user-gesture-required \
       --disable-background-timer-throttling \
       --disable-backgrounding-occluded-windows \
       --disable-renderer-backgrounding \
       --enable-unsafe-extension-debugging \
       --user-data-dir=/tmp/vh-profile --remote-debugging-port=9333

npm run browser-check:all   # fixture 端到端 + 扩展内部链路（含 3 秒采集停摆的防空洞用例）
npm run browser-check:real  # 真实 CDN 上的公开 HLS 流（需要能联网）
```

### 单独查一个文件的「拖不动」问题

```bash
node tools/seek-diag.mjs 某个视频.mp4              # 体检：样本表、时长、关键帧、空洞
node tools/seek-diag.mjs --fix 某个视频.mp4 输出.mp4  # 把死气空洞原地压掉（另存）
```

体检逻辑同时被扩展页面用（管理页里的「拖不动进度条？体检一下」），
两边是同一份 `src/parser/seek-check.js`，不会跑偏；它有 `test/seek-check.test.mjs` 覆盖，
其中「注入空洞 → 修复 → 和原文件逐段对比，样本数据一个字节没动」是最关键的那条。

### 拿一个真实站点探一探

```bash
node tools/browser-check.mjs --port 9333 --site "https://www.youtube.com/watch?v=..."
```

打开真实页面、等它播起来，然后如实报告**六件事**：页面在不在播、扩展嗅到了什么、
**Chrome 实际发了哪些媒体请求**、抓流**按 mime 分别收到了多少**、抓到的**每一组**
是什么容器/什么轨（包括没被采纳的组和不采纳的原因）、以及收尾产物的
**每一条轨**（ffprobe + 两条轨的起点差）。

第三个是关键：只看扩展嗅到了什么，分不清「站点压根没用普通请求取媒体」和
「我的嗅探层有 bug」。两个数字摆在一起，结论就没法含糊 ——
YouTube 那次就是靠它定案的（媒体是 `application/vnd.yt-ump`，嗅探天生无效，
而抓流收到 136 段）。

第五、六件是**后来补上的**，起因是用户报「抓 YouTube 有画面没声音」：
当时探针只会说"收到 105 段 / 2.94 MB"，而**这恰恰是这个 bug 唯一看不出来的东西** ——
音频那 0.8 MB 明明收到了，只是没进产物。现在探针会把每一组都摊开、并把产物真的
落盘交给 ffprobe 看轨。加完之后第一轮就定案了（音频组是 `webm`，容器认不出）。

这个模式**不判通过/不通过**：真实站点行为千变万化，它只给事实。
唯一的例外是「页面明明在播、却一条媒体都没嗅到」和
「Chrome 发了媒体请求、扩展一条都没记下」，那两种会标成问题；
「产物有画面没声音」现在也会明确标出来。

`--disable-*-throttling` 那几个参数不是可选的：headless 默认节流后台标签页的定时器，合成测试流会 3 秒只出 3 帧，从而让"帧有没有被编码"这个断言失去意义。
