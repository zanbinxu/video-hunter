# Video Hunter 0.2.6 典型实战场景与发布示例手册

本文档为 **Video Hunter 0.2.6** 的实战案例手册，详细介绍本版本在五大极端复杂流媒体场景下的工作机制、输入形态、预期产物规格及验证方法。

---

## 快速上手

### 1. 安装加载
1. 打开 Chrome / Edge 浏览器，访问 `chrome://extensions/`；
2. 开启右上角「**开发者模式**」；
3. 点击左上角「**加载已解压的扩展程序**」，选择解压后的目录 `dist/video-hunter-0.2.6`（或仓库根目录）；
4. 插件图标将出现在浏览器工具栏，点击可唤出操作面板。

### 2. 核心操作
- **常规直链嗅探**：访问任意音视频网站，插件自动嗅探 MP4、HLS (m3u8)、DASH (mpd) 并在弹窗提供一键下载与音视频自动合并。
- **MSE 动态抓流（核心功能）**：对于无直链、自适应切片、长视频或极端推流站点，在播放页点击插件面板中的「**抓流**」按钮，插件接管 MediaSource 推流并在后台自动拼装、转码与落盘。

## 五大典型实战场景示例

### 案例 1：YouTube 4K AV1 + Opus 抓流（双编码混装与起播前段分离）

#### 场景特征
- **输入特征**：YouTube 播放器在起播或码率自适应时，前几秒可能先推送低分辨率 WebM (VP9)，随后稳定在 4K 超高清 fMP4 (AV1)；音频则全程为单轨 WebM (Opus)。
- **旧版痛点**：旧逻辑在合并时误伤主音轨，导致 3 分钟的视频只有前几十秒有声音、后半段完全静音；且起播时主线程同步 base64 导致播放器长时间卡死转圈。

#### 0.2.6 运行流程与示例
1. 打开 YouTube 4K 视频，点击插件弹窗中的「**抓流**」；
2. 页面就绪后，`mse-hook` 采用异步微任务让出主线程，播放器秒开流畅播放，无卡死转圈；
3. 音轨解耦转码管道：全量 WebM/Opus 音轨送入后台 Web Audio 转码为标准 AAC，音画起点精确对齐（误差 < 1.5s 自动平移对齐）；
4. 起播低清缓冲段被识别为前置缓冲，自动另存为附属文件；
5. **预期产物**：
   - 主产物：`[标题]-4K.mp4`（约 150MB~500MB，画面 4K AV1 流畅播放，音画全程同步且 100% 有声）；
   - 附带产物：`[标题]-前段.webm`（约几 MB，起播前几秒缓冲段，独立可播放）。

### 案例 2：2x ~ 12x 极速推流抓流（真实媒体时长精准统计）

#### 场景特征
- **输入特征**：用户开启视频倍速（如 2x、3x、6x，乃至通过脚本开启 12x 极速推流），视频在几十秒内刷完整集。
- **旧版痛点**：悬浮录制卡片「抓取内容」仅以物理挂钟耗时统计，录了 30 秒物理时长实际下载了 3 分钟视频，界面错误显示「抓取内容：00:00:34」，用户误以为抓取不全。

#### 0.2.6 运行流程与示例
1. 在视频播放页开启 4x 倍速播放，点击「**抓流**」；
2. 底层 `readTraf` 与 `sidx` box 精确解析每个分片的实际 `durationTicks` 与真实 `timescale`（如 90,000），脱离物理挂钟累加；
3. 悬浮录制卡片每秒动态高频刷新：
   - `录制用时`：显示实际耗时（如 `00:00:35`）；
   - `抓取内容`：精准展示捕获的视频真实时长（如 `00:03:12`）；
4. 点击「**结束抓流**」，保存完整 03:12 时长的视频文件，时间戳单调连续无跳跃。

### 案例 3：单页 SPA 播放列表连播自动切集与单集真实标题抓取

#### 场景特征
- **输入特征**：在单页应用（SPA）连播站点中，用户观看电视剧/合集列表（如 Joanna 等单页播放站点），播放完第 1 集后无刷新直接连播第 2 集，URL 不变或通过 pushState 无缝换集。
- **旧版痛点**：无法感知换集导致多集全部混进同一个大文件且音画时间轴混乱；或者换集瞬间生成几 KB 的无效残片；第二集标题未更新且开头被跳过。

#### 0.2.6 运行流程与示例
1. 在连播播放列表页开启抓流并播放第 1 集；
2. 第 1 集播放完毕瞬间，后台捕获到单页换集事件与时间戳归零信号；
3. **自动动作**：
   - 瞬间冻结第 1 集缓冲区，以第 1 集的独立标题自动落盘保存为完整文件；
   - 自动丢弃换集过渡瞬态的极小残片（< 64KB）；
   - 提取列表 DOM 中第 2 集真实标题，重置捕获缓冲区；
   - 控制器自动触发寻道回跳，确保第 2 集从 00:00:00 完整起播；
4. **预期产物**：
   - `第01集-[单集标题].mp4`（第 1 集完整文件）；
   - `第02集-[单集标题].mp4`（第 2 集完整独立文件，开头完整，音画同步）。

### 案例 4：超长视频大文件分段与 10 秒首份安全快照

#### 场景特征
- **输入特征**：长达数小时的超长会议、直播录制或超大 4K 视频，录制体积迅速超过浏览器单文件内存安全上限（默认 600MB）。
- **旧版痛点**：达到分段阈值时直接清空缓冲池，未送入 muxer 的残余分片被整批遗弃，导致分段交界处画面黑屏截断 2~5 秒；且长时间未落盘若遇页面崩溃全盘皆失。

#### 0.2.6 运行流程与示例
1. 开启抓流录制长视频，设定切段阈值为 600MB；
2. **前 10 秒首份安全快照**：录制达到 10 秒时自动在磁盘落地首份兜底快照 `[标题]-自动部分-01.mp4`，之后按 5 分钟设定间隔滚动覆盖；
3. **大文件切段平滑交接**：当主视频体积达到 600MB 时，触发无损切段：
   - 当前分段安全落盘为 `[标题].mp4`；
   - 未消费的尾部分片（remainder）被无缝递交至下一段缓冲池头部；
4. 第二段继续录制并保存为 `[标题]-2.mp4`，交界处经播放器验证画面无缝衔接、时间轴连续。

### 案例 5：网络抖动导致 WebM 重发 Init 与字节流错位自动救援

#### 场景特征
- **输入特征**：网络波动、切换清晰度或播放器重置解码器时，播放器在数据流中途重新注入一份带有新参数的 EBML / 初始化段；或因网络丢包导致分片拼接处丢失了几十个字节。
- **旧版痛点**：旧拆包器信赖旧的 Segment 声明长度直接跳过后续字节，导致后半段画面被整段吞掉；或者遇到错位元素头时静默退出，百兆后续画面丢失。

#### 0.2.6 运行流程与示例
1. 抓取过程中播放器中途重发 init 或发生网络分片错位；
2. `webm-demux.js` 启动双校验容错救援机制：
   - 遇到合法子元素之外的字节错位，自动以字节为步长向后滑窗扫描合法的 Cluster 标识（`1F 43 B6 75`）；
   - 严格校验 Cluster 头部自洽与首个子元素为 `Timestamp`；
3. 跳过错位区，将后续全部音视频 Cluster 成功救回；
4. 产物提示明确标注：「播放器中途重发初始化段，已自动平滑跳过并救回后续 150 帧；有 1 处字节错位已自动纠正」；
5. 最终产物时长完整覆盖整部视频，视频帧数无缺失。

## 产物健康度独立验证指南

你可以使用项目自带的工具或系统安装的 `ffprobe` 对产出的 MP4 / WebM 进行独立体检：

```bash
# 1. 使用内置体检脚本检测 MP4 时间轴与空洞
npm run check-product -- "下载路径/生成的视频.mp4"

# 2. 使用系统 ffprobe 检查音视频轨道与编解码规格
ffprobe -hide_banner "下载路径/生成的视频.mp4"
```

**健康产物判定标准**：
- 视频轨与音频轨时长差值在 1.5 秒以内；
- `start_time` 从 `0.000000` 开始；
- 播放器任意拖拽进度条不卡顿、画面无花屏与马赛克；
- 全程音画同步，后半段无静音断流。
