# 架构说明

这份文档记录的是**为什么这么分层**，不是代码在做什么。想了解功能看 [README](../README.md)，想看实测证据看 [verification.md](verification.md)。

---

## 一、四个运行上下文

MV3 扩展的困难几乎全部来自一个事实：**不同的运行上下文能力差异极大，而且其中一个会随时被杀。**

```
┌──────────────────────────────────────────────────────────────────┐
│ service worker（无 DOM，随时被杀）                                │
│   · webRequest 嗅探（唯一能拿到请求头的地方）                      │
│   · 下载调度、Referer 会话规则、录制编排                            │
│   · 不含任何重活：不做解封装、不持流、不存大对象                    │
└───────┬────────────────────────────────────┬─────────────────────┘
        │ 消息                                │ 消息
┌───────▼──────────────┐            ┌────────▼─────────────────────┐
│ 扩展页面（标签页）    │            │ 离屏文档（无 UI，不抢焦点）   │
│  · popup 面板         │            │  · 持有 tabCapture 的 MediaStream│
│  · 解析器页           │            │  · WebCodecs 编码 + mp4-muxer │
│  · 录制控制台         │            │  · 写 OPFS                    │
│  有 DOM、大内存、       │            └──────────────────────────────┘
│  File System Access   │
└───────┬──────────────┘
        │ executeScript（按需注入）
┌───────▼──────────────────────────────────────────────────────────┐
│ 内容脚本（页面隔离世界）                                           │
│   · 在页面上下文 fetch（Referer/Cookie 天然正确）                  │
│   · 扫描 <video>、给视频挂下载按钮                                 │
└──────────────────────────────────────────────────────────────────┘
```

### 为什么重活放在扩展页面而不是 service worker

1. SW 没有 DOM，`<a download>`、`Blob`、`showSaveFilePicker` 全都用不了。
2. SW 会在 30 秒空闲后被系统杀掉。一个正在下载 2 GB 视频的任务不能挂在它身上。
3. 解析器页是个**真实标签页**——它有完整的内存配额、能调 File System Access API、能开 Web Worker。

所以 SW 知道自己该干什么：**它只负责"知道有什么"和"派活"**，不负责执行。

### 为什么采集必须放在离屏文档

`chrome.tabCapture.getMediaStreamId()` 要求被采集的标签页**当前是活动标签页**。任何我们自己的页面一打开，就会把目标页顶掉，采集直接起不来。

这不是可以绕过的限制，它决定了整个录制流程的形状：

1. 用户必须**在目标页面上**打开扩展面板（此时目标页仍是活动的）
2. 面板立刻向 SW 请求 `getMediaStreamId`，SW 转交给离屏文档
3. 离屏文档不是标签页，不抢焦点，采集得以持续
4. 之后用户去点播放按钮、刷新页面，扩展弹窗关了也无所谓

离屏文档还顺带解决了第二个问题：弹窗会在用户点击页面时自动关闭。

## 二、状态放在哪里

| 状态 | 存放位置 | 为什么 |
| --- | --- | --- |
| 嗅探到的媒体列表 | 内存 Map + `chrome.storage.session` | 一个 HLS 会话能刷出几千个分片请求，全量写 `local` 会把自己写死；`session` 是内存后端且能扛 SW 重启 |
| 用户设置 | `chrome.storage.local` | 要跨浏览器重启保留 |
| 录制状态 | 内存 + `chrome.storage.session` | 同嗅探列表 |
| 录制文件本体 | OPFS（源私有文件系统） | 离屏文档里没有用户手势，弹不出保存对话框，只能先落私有存储 |
| 正在下载的分片 | 解析器页的 reorder buffer | 只在该页存活期间有意义 |

`store.js` 里写入做了 250ms 防抖，但提供 `flush()`：面板查询前会先 flush，保证不丢刚嗅到的条目。这个组合是有意的——高吞吐路径走防抖，低延迟路径走显式 flush。

## 三、抓取的三级策略

同一个 m3u8 地址，用三种方式去抓，保真度依次下降、可用性依次上升：

| 级别 | 在哪抓 | 带什么 | 什么时候用 |
| --- | --- | --- | --- |
| 1 | **内容脚本**（页面上下文） | Referer / Cookie / Origin 全部天然正确 | 首选。抓播放列表这种小文本，成本可以忽略 |
| 2 | **service worker** | 有 `host_permissions`，不受 CORS 限制；但没有 Referer | 页面关掉了 / 注入不了时 |
| 3 | **declarativeNetRequest 会话规则** | 给扩展页自己的请求补上 Referer | 扩展页要直接下载分片时 |

第 3 条是实现里最巧妙的一处。扩展页面发出的请求默认没有 Referer，而 CDN 上的 `.ts` 几乎都校验它。解法是给**发起方标签页**挂一条会话规则：

```js
{ condition: { tabIds: [parserTabId], resourceTypes: ['xmlhttprequest','media','other'] },
  action: { type: 'modifyHeaders', requestHeaders: [{ header: 'referer', operation: 'set', value: pageUrl }] } }
```

规则 ID 由 tabId 直接算出（`9000 + tabId % 2000`），不依赖任何内存表——这样 SW 被杀掉再唤醒后，仍能算出同一条规则去清理，不会留下孤儿规则。解析器页 `beforeunload` 时会主动撤销。

**没能验证的部分**：这条路径只在代码里成立，还没有在真实校验 Referer 的站点上跑过。

**没走的路**：`chrome.debugger` + `Fetch` 域能改写任意请求头，是万能解。但它会在页面顶部挂一条"Video Hunter 正在调试此浏览器"的横幅，还得单独申请可选权限。会话规则能解决的事不该动用它。

## 四、HLS 下载管线

```
m3u8 ──parsePlaylist──▶ { variants } 或 { segments, encryption }
                           │
              选码率 ──────┘
                           │
        ┌──────────────────▼──────────────────┐
        │ downloadSegmentsInOrder             │
        │   worker 池并发下载                  │
        │   ↑ 抢下一个序号                     │
        │   ring buffer 按序号吐出              │
        │   每个分片下载后立即 AES-128 解密      │
        └──────────────────┬──────────────────┘
                           │ 按序的明文
        ┌──────────────────▼──────────────────┐
        │ 有 #EXT-X-MAP ?                      │
        │   是 → 直接写 init + 分片（fMP4）     │
        │   否 → createTsRemuxer（mux.js）     │
        └──────────────────┬──────────────────┘
                           │
                    FileSystemWritable
                    或内存 Blob
```

### 保序是怎么做到的

并发下载和顺序消费是两个矛盾的需求：分片必须并发拉（否则一个大视频要下到天荒地老），但重封装必须按顺序喂。

实现是「worker 池 + 环形缓冲」：worker 随便抢序号下载，结果放进 `Map<index, data>`；消费者永远只取 `nextToYield` 那一格，没轮到就等唤醒。这样**并发度不受顺序约束，而输出严格有序**。

### mux.js 的写盘回调为什么要串行化

mux.js 的 `Transmuxer` 通过事件回调吐数据，回调是**同步**的；而写盘是**异步**的。如果直接把 `sink.write()` 丢进回调，这些 promise 会在 `close()` 之后才落地，表现为"文件写完了但最后几帧没了"——一种极难查的问题。

所以所有写入都排进一条 promise 链（`queueWrite`），`remuxer.end()` 之后 `await writeChain` 再 `close()`。

### 前端丢帧 vs 队列爆炸

视频泵里有一条判断：`if (videoEncoder.encodeQueueSize > 6) { 丢帧 }`。

编码跟不上时，让队列无限涨会直接吃光内存并卡死整个进程。录制要的是"跟得上"，不是"一帧不落"——丢帧并如实计数，比卡死好。

### 直播为什么单独拆一个模块

直播和点播的差别只有一件事：**播放列表会变**。没有 `#EXT-X-ENDLIST`，列表是滑动窗口——老分片沉出去、新分片浮进来。

于是下载直播不是"拉一次列表然后下完"，而是"反复拉列表，每次只下没见过的那几个"。`live.js` 把这个循环拆成两层：

- `createLiveTracker` —— **纯逻辑**：喂一份播放列表，返回这一轮的新增分片，并记录滑动窗口跳过头导致的漏片区间。不碰网络、不碰定时器。
- `runLivePolling` —— 只负责节拍和网络。

这么拆的理由是**可测**。直播的 bug 有个恶劣特点：短时间跑完全正常，跑半小时才开始丢片。拆开之后就能用手工构造的滑动窗口快照序列去压它，而不是真的等半小时。11 个测试里有 6 个是纯逻辑的窗口场景。

几个刻意的决定：

- **漏片必须如实记下来**，不能静默。窗口跑得比下载快时产物会跳帧，用户有权知道跳了多少。
- **单批分片下载失败不终止整场录制**。直播里"分片已经过期被删了"是常态，不是异常；让它打断录制的话，用户会得到一个录到一半就停了的文件。
- **单次拉取失败也不终止**，但节拍要沿用上一轮算好的值，不能打回默认——否则一次网络抖动会把整个轮询节奏搞乱。
- **abort 要立刻生效**，不能等完当前轮询周期，否则用户点了停止还要干等几秒。

## 四之二、DASH 与音视频分离

DASH 和 HLS 的差别不只是清单格式。**DASH 的常态就是视频轨和音频轨各自独立**（两条 AdaptationSet），而 HLS 大多数时候把两条复用在一路 TS 里。但 HLS 也允许拆分（`#EXT-X-MEDIA:TYPE=AUDIO`），Apple 的官方示例流就是这么做的。

所以真正需要的能力是同一个：**把两路独立的流合并成一个 MP4**。

```
视频路 ─┐
        ├─→ 各自收成 { init, segments } ─→ mergeFmp4 ─→ 一个标准 MP4
音频路 ─┘
```

`mergeFmp4` 只认 fMP4，不认 MPEG-TS、也不知道 DASH 的存在。TS 那一路先经 mux.js 重封装成 fMP4 再喂进去。这样同一个合并器同时服务三条路：

| 来源 | 视频路 | 音频路 |
| --- | --- | --- |
| DASH | fMP4（`initUrl` + 分片） | fMP4 |
| HLS 分离音轨 | TS → mux.js → fMP4 | TS / fMP4 |
| 只有一路 | fMP4 | 省略 |

### 为什么这条路不能边下边存

合并要把两条轨的样本**按时间戳交错**排布，所以必须同时拿到两边 —— 没法像单路那样"下完一片写一片"。

这条路径的数据全在内存里，日志会如实打出「两路共 X MB 已收在内存里」。这是明确的取舍，不是疏忽：要好内存就得先落成两个临时文件再二次读取，复杂度和磁盘 IO 都不划算。

### 合并器里几个不得不自己做的事

底层库做不到的部分，`mp4-merge.js` 自己补了：

- **`edts/elst` 后处理**：mp4-muxer 不写编辑列表，而 MP4 的 `stts` 只能表达*样本间距*，表达不了「这条轨从 0.059 秒才开始」。两轨起始时间不同时，必须靠 `elst` 的空编辑把其中一条推后，否则音画会整体错位。
- **末样本时长对齐**：mp4-muxer 的 `stts` 没地方放最后一个样本的时长，会拿前一个间隔顶上。AAC 尾巴常见 512 vs 1024 tick 的差异，导致 `mdhd.duration` 和 `Σstts` 对不上，ffmpeg 就会把尾帧截掉 10.7 ms。
- **自己走 box 树**：mux.js 的 `findBox` 把每个 box 的 payload 当平铺 box 继续扫，对 `stsd`（前面有 8 字节 version/flags + entry_count）和 `avc1`（前面有 78 字节 VisualSampleEntry）不成立，所以 `['stsd','avc1','avcC']` 永远返回空。
- **自己解 AudioSpecificConfig**：mux.js 的 esds 解析结果不对（读出的 `esId` 是垃圾值），AAC 的 ASC 按 tag 走 esds、描述符长度是 base-128 变长。

这些都不是"重造轮子"，是底层库在这几个具体位置上确实不对，而它们每一个都会让产物出问题（音画偏移、尾帧被截、轨道切不出样本）。

## 四之三、录制

录制这条链路是这样切开的：

```
offscreen.js（编排）              拿到 tabCapture 的流 → 交给管线 → 上报状态 → 处理意外结束
      │
      ▼
pipeline.js（引擎）                协商编码器 → 建封装器 → 两个泵 → 收尾落 OPFS
```

**为什么中间要有一层 `pipeline.js`：为了可测。**

原本这段代码和 `chrome.tabCapture` 绑死在离屏文档里。而 tabCapture 有个硬约束——**扩展必须被用户主动调用过**（点工具栏图标）。自动化环境给不了这个授权，于是整条录制链路一行都验不了，"帧有没有被正确编码"这种最容易出错的地方只能靠读代码确认。

切开之后，"编码封装对不对"和"能不能拿到 tab 流"成了两件独立的事：前者可以用 `canvas.captureStream(0) + requestFrame()` 合成的流在真实浏览器里跑完整流程，产物交给 ffprobe；后者是 Chrome 的安全边界，自动化测不了，如实记录。

收尾顺序在这里很讲究，写反了就会丢最后几帧或者写进一个还没 finalize 的文件：

```
停泵 → 停轨道 → 关 AudioContext → flush 编码器 → finalize 封装 → 关/补写目标文件
```

还有两条刻意的行为：

- **编码跟不上就丢帧，并如实计数。** 让编码队列无限涨会吃光内存并卡死整个进程。录制要的是"跟得上"，不是"一帧不落"。
- **出错立刻停心跳并主动收尾。** 心跳每秒无条件上报"正在录制"，不停掉的话会把错误状态在一秒内覆盖回去，用户看到的是一个永远不结束的录制，而采集流和 AudioContext 还挂在那儿。

## 五、消息协议

所有跨上下文消息都带 `vh:` 前缀，定义集中在 `src/core/constants.js`。

| 消息 | 方向 | 作用 |
| --- | --- | --- |
| `vh:get-tab-media` | popup → SW | 取某标签页的媒体列表（SW 会先 flush） |
| `vh:start-download` | popup → SW | 直链下载，或转解析器 |
| `vh:open-parser` / `vh:open-recorder` | popup → SW | 开扩展页面 |
| `vh:set-referer` / `vh:clear-referer` | 扩展页 → SW | 挂/撤 Referer 会话规则 |
| `vh:fetch-resource` | 扩展页 → SW | 借源页面的上下文抓取（降级路径） |
| `vh:page-*` | SW ↔ 内容脚本 | ping / fetch / 扫描视频 / 开关按钮 |
| `vh:record-start` / `vh:record-stop` / `vh:record-state` | UI ↔ SW | 录制控制（`record-state` 是**查询**） |
| `vh:record-state-push` | SW → 广播 | 录制状态**推送** |
| `vh:offscreen-*` | SW ↔ 离屏文档 | 采集启停 |
| `vh:media-updated` | SW → 广播 | 媒体列表变化，实时刷新 UI |

**「拉」和「推」必须用不同的消息类型。** 这两件事共用过一个类型，结果是 popup 每秒查询状态时，录制台页把别人发出去的请求当成推送（消息里没有 `state`）→ 界面刷成「空闲」；反向也一样，录制台刷新状态会把 popup 的录制条清掉并停掉它的轮询。一个消息类型不该同时承担两种语义。

**另一个容易踩的坑**：`chrome.runtime.sendMessage` 会把消息发给**除发送者以外**的所有扩展上下文。所以每个监听器都必须对自己不处理的消息返回 `false`，否则会出现"多个响应者、第一个赢"的竞态；而如果某个监听器返回 `true`（表示"我会异步回"）却从不调用 `sendResponse`，发送方的 promise 会**永远挂起** —— 这种死锁排查起来非常费劲，所以我们逐条审计过所有监听器的所有分支。

## 六、失败模式与处理

| 失败 | 处理 |
| --- | --- |
| 分片 403（缺 Referer） | 已捕获 Referer 则注入会话规则；仍失败则提示"试试用解析方式下载" |
| 分片下载失败 | 指数退避重试（默认 3 次），仍失败则整个任务失败并报出**是第几个分片** |
| 分片超时 | 每个分片独立 45 秒超时，不靠外部 signal——一个卡住的分片不该让整条流水线停住 |
| 容器与播放列表声明不符 | 首个分片用魔数嗅探，不符立即报错，而不是产出一个坏文件 |
| DRM | 解析出 `drm` 字段后立刻停止，向用户解释为什么浏览器层面做不到 |
| 没有 H.264 编码器 | 逐个问浏览器 `isConfigSupported`，全不支持才报错 |
| 标签页没有音轨 | 带 audio 约束的 getUserMedia 失败后，退成纯视频重试一次 |
| 保存对话框被取消 | 识别为 `AbortError`，静默返回，**不偷偷换条路继续** |
| 离屏文档没响应 | 报出明确错误并关掉离屏文档，不让它变成僵尸 |
| 轨道意外结束（用户关了标签页） | 自动收尾，别把半个文件留在那儿 |

## 七、我们**没有**做的事

- 没有用 ffmpeg.wasm。见 README 的"技术选择"。
- 没有用 `chrome.debugger`。理由同上。
- 没有做代码混淆 / 反检测。这个工具是给用户自己用的，不是用来对抗站点的。
- 没有 DRM 绕过，也不打算做。
- 没有后端。所有数据只在本机。
